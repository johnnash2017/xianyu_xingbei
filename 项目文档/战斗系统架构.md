# 战斗系统架构

> 面向：要改战斗规则、加状态、加技能、查“这个现象从哪来”的开发。
> 本文讲**系统怎么分层、数据怎么流、状态怎么走**；单个技能/选项的写法规范看 [技能维护约定](技能维护约定.md)，两者不冲突。
> 名词（士气 / 治疗 / 星石 / 星杯 / 盖牌 / 指示物 / 形态）见 [AGENTS.md](../AGENTS.md) 第 15 节。
>
> 文档按当前代码整理，**与代码冲突时以代码为准**。关键结论都标了 `文件:行号`，方便顺着查。

**快速跳转：** 想先看懂全貌 → 第 0、1 节；查某个状态做什么 → 第 4.6 节、附录 A；查询问 / 回复字段 → 第 6 节、附录 C；加技能 / 加字段 → 第 9、13 节；踩坑清单 → 第 14 节。

## 0. 一页纸速览

| 问题 | 答案 |
| --- | --- |
| 规则在哪算 | 房主进程里的 `BattleEngine`（`RefCounted`，每个房间一个实例，不挂场景树） |
| 谁在驱动它 | `LocalServer.poll()` 每帧调 `battle.tick()`；玩家消息经 `battle.on_message()` 进入 |
| 一步操作怎么走 | 服务端 `CmdReq` → 客户端点选 → 上行 `Action` / `Respond` → `engine.on_message` → 状态机 `run()` |
| 回合骨架 | `SCheckTurnStart` → `SActionPhase` → 行动结算 → `STurnEnd` → `SNextPlayer` → … |
| 技能怎么插进流程 | 角色脚本覆写 `p_*` 钩子；引擎用 `SHook` 按座位顺序逐个调用 |
| 额外行动是什么 | `BattlePlayer.additional_actions` 里的一条“行动资格”，带 `uid` / `order` / `spec`，由 `SAdditionalAction` 消费 |
| 伤害怎么结算 | `push_harm()` 压入时间线 3/4/5/6：广播 → 治疗抵挡 → 按点数摸牌 → 超限弃牌掉士气 |
| 客户端做什么 | `battle_mobile.gd` 读 `Game` 快照与 `Data`、渲染 `CmdReq`、收集点击；**不判规则** |
| 代码规模 | `battle_engine.gd` 5226 行 / 35 个状态类；`battle_role.gd` 49 个 `p_*` 钩子 / 18 个 `v_*` 校验；54 个角色脚本；6 个借用 helper；62 个自检用例 |

## 1. 分层与职责边界

### 1.1 三层

```text
┌─ 客户端（每个玩家各一份）──────────────────────────────────┐
│  scenes/BattleUIMobile.tscn + scripts/ui/battle_mobile.gd    │
│      ↑ 信号                    ↓ Logic.send_action / send_respond
│  scripts/client/client_logic.gd（收包分派、连接/重连、房间上下文）│
│      ↑ 帧                    ↓ Net.send                     │
└───────────────────────────────┬─────────────────────────────┘
                                │ 局域网 TCP / Steam P2P
┌─ 房主进程（同时也是玩家 1）────▼─────────────────────────────┐
│  scripts/net/local_server.gd                                 │
│    · 房间、座位、准备、选角、开局倒计时、心跳、重连、解散        │
│    · room["battle"] = BattleEngine.new()                     │
│         ↓ send_cb 注入                                       │
│  scripts/battle/battle_engine.gd（规则 + 状态机）             │
│    ├─ BattlePlayer（玩家状态：手牌/资源/额外行动…）            │
│    │    └─ BattleRole（角色脚本：钩子 + 技能）                 │
│    └─ BattleDeck（牌库/弃牌堆）                               │
└──────────────────────────────────────────────────────────────┘
```

### 1.2 四条边界规则

1. **引擎不碰网络**：`BattleEngine` 只持有 `send_cb: Callable`（`battle_engine.gd:75`），由 `LocalServer` 在建房时注入（`local_server.gd:434`）。`send(target, msg_type, data)` 里 `target = -1` 表示广播、`GConst.GUEST`（9）表示只发观战者（`battle_engine.gd:1718`、`local_server.gd:1103`）。
2. **引擎不碰界面**：没有 Node、没有 `get_node()`、不读场景。所有“给人看的东西”都是消息（`Gossip` / `Card` / `Skill` / `HurtFloat`…）。
3. **客户端不判规则**：客户端的置灰、白名单、自动选中都只是**体验过滤**；合法牌、合法目标、资源是否足够，最终由服务端 `v_*` 校验与 `resolve_action` 总闸决定。
4. **数据只从 `Data` 读**：角色、技能、卡牌、指示物上限、提示文案全部来自设计表（`DataTables.gd`），角色脚本里不写死数值。

### 1.3 一条操作的全链路（以“出攻击牌”为例）

```text
玩家点手牌 + 点敌方头像 + 点“确定”
  → battle_mobile._发送行动()（battle_mobile.gd:6583）
  → Logic.send_action(action_type=1, action_id=0, dst_ids, card_ids, args, extra_uid)（client_logic.gd:519）
  → Net.send(GConst.Msg.Action=103, {...})            // proto_schema.gd:396
  → LocalServer._on_message → battle.on_message(pid, 103, data)（local_server.gd:337）
  → BattleEngine.on_message：校验 _await_id/_await_kind → 写入 _reply → run()（battle_engine.gd:1079）
  → SActionPhase.handle → take_reply → resolve_action(1, data)（battle_engine.gd:3226、4667）
  → _do_attack：v_attack / v_attacked / 额外行动限制 → 记录行动 → push(SAttackCard)
  → SAttackCard → SHook(p_before_attack) → SHook(p_timeline_1) → SAttacked → SAttackedAsk
  → 下发 CmdReq（cmd_type=Respond, respond_id=ReplyAttack=10）并 wait_for()
  → 服务端广播 Game 快照；客户端画应战界面
```

## 2. 对象模型

### 2.1 关系

```text
LocalServer
 └─ _rooms[房间号] : Dictionary
      ├─ "battle" : BattleEngine         ← 规则本体（一房一个）
      ├─ "conn_of" : { player_id: conn_id }   座位 → 连接
      ├─ "watchers" : [conn_id, ...]
      └─ 其他房间字段（名字/人数/选角策略/倒计时…）

BattleEngine
 ├─ players : { player_id: BattlePlayer }
 ├─ order : [player_id, ...]            座位顺序（顺向）
 ├─ deck : BattleDeck                   牌库 + 弃牌堆
 ├─ _states : [状态实例, ...]            状态栈（后进先出）
 ├─ _进度表 : { 状态实例: { player_id: step } }
 ├─ team_morale / team_gem / team_crystal / team_grail : [红, 蓝]
 ├─ current_id / first_id / round_id / phase
 └─ 等待态：_await_id / _await_kind / _await_state / _reply / wait_seq …

BattlePlayer
 ├─ role : BattleRole  ── 一个玩家一个角色实例（弱引用 engine / player）
 ├─ hand_cards / cover_cards / basic_effects / exclusive_effects
 ├─ gem / crystal / cross_num / tokens
 ├─ additional_actions : [{uid, order, cause, allow_action, spec…}]
 └─ 行动计数 / 形态 / 掉线标记 / ping

BattleRole
 ├─ player / engine（WeakRef，避免循环引用）
 ├─ step（代理到引擎的“当前状态进度槽”）
 └─ p_* 钩子 / v_* 校验 / available_skills / p_*_skill
```

### 2.2 `BattleEngine`（房间级）

| 分组 | 字段 | 说明 |
| --- | --- | --- |
| 房间 | `room_id` / `room_name` / `room_max_player` / `room_debug` / `room_watchers` / `room_picking` / `pick_ready` | 由 `LocalServer` 写入；也随快照下发 |
| 座位 | `players` / `order` / `current_id` / `first_id` / `round_id` / `host_seat` | `pre_id` / `post_id` 由 `arrange_seats()` 建好 |
| 队伍 | `team_morale` / `team_gem` / `team_crystal` / `team_grail` | 下标 1 红、0 蓝 |
| 牌 | `deck` | `BattleDeck` |
| 推进 | `phase`（Idle / Playing / Over）、`winner`、`_states`、`_running` | `_states` 是状态栈 |
| 等待 | `_await_id` / `_await_kind` / `_await_state` / `_reply` / `_has_reply` / `wait_deadline_ms` / `wait_seq` | 见 §4.5、§6 |
| 额外行动 | `当前额外行动数据`、`首选额外行动/卡/目标`、`行动允许` / `行动可放弃` / `行动额外` / `行动额外来源` / `行动禁特殊` | 行动阶段上下文，每次 `SActionPhase` 重设 |
| 额外回合 | `额外回合玩家` / `额外回合攻击加伤` / `额外回合来源` / `当前额外回合玩家` / `当前额外回合攻击加伤` | 见 §5.4 |
| 扫描缓存 | `_hand_counts` / `_hand_maxes` / `_token_counts` / `_gems` / `_team_energies` | 供状态边界比变化、写日志 |

### 2.3 `BattlePlayer`（玩家级）

| 分组 | 字段 / 方法 | 说明 |
| --- | --- | --- |
| 身份 | `id` / `role_id` / `color` / `player_name` / `online` / `ping_ms` | 阵营 `GConst.RED=1` / `BLUE=0` |
| 手牌 | `hand_cards` / `hand_cards_max` | 默认上限 6（`HAND_CARDS_MAX`），开局 4 张（`START_HAND`） |
| 盖牌 | `cover_cards` / `cover_cards_max` | 上限来自角色表「指示物」槽 2 |
| 基础效果 | `basic_effects: [{card, src}]` | 圣盾 / 虚弱 / 中毒 / 封印 / 赐福… |
| 专属效果 | `exclusive_effects` / `exclusive_owners` | 挑衅等，带放牌者 |
| 资源 | `gem` / `crystal` / `cross_num` / `cross_max` / `energy_max` | 治疗上限默认 2、个人能量上限默认 3 |
| 指示物 | `tokens[0..1]`（`{name,max,num}`）、槽 2 = 盖牌上限 | 由 `BattleRole._按表初始化标识物()` 建 |
| 形态 | `tap`（横置）、`xue_qiang_wei`、`sheng_huang_side`、`dream_tier` | 形态同时也是客户端状态图标来源 |
| 额外行动 | `additional_actions` / `add_action()` / `额外行动按ID()` / `撤回额外行动()` / `改写额外行动()` | 见 §9.6 |
| 行动计数 | `attack_action_count` / `magic_action_count` / `special_action_count` / `extra_action_count` | `record_action()` / `undo_action()` / `reset_action_counts()` |
| 校验 | `v_allow_action` / `v_attack` / `v_reattack` / `v_block` / `v_shield` / `v_weaken` / `v_missile` / `v_buy` / `v_extract` / `v_attacked` / `v_basic_effect_target` | 先问角色，角色不覆写（`V_NOT_OVERRIDE`）再走 `base_v_*` |

几个容易读错的点：

- `add_cross_num()` **只加不减**：超上限后再加不会把现有治疗拉回上限；所以治疗要经它（或引擎 `add_cross`），不要直接写 `cross_num`，否则治疗会倒退。
- `set_gem()` / `set_crystal()` 会**把另一项算进去再截断**（照抄服务端行为）：已有水晶时再加宝石，宝石会被压到 `上限 − 水晶`。
- `remove_energy(n)` 先扣水晶、再扣宝石。
- `has_hand_card()` 含“盖牌视同手牌”的形态；`has_discard_card()` **只认真实手牌**。弃牌、超限、技能代价一律用后者。
- `ping_ms` 用 `GConst.PING_未测`（65535）表示未测，**0 是合法值**（房主自己那一路）。

### 2.4 `BattleRole`（角色脚本）

- 一个角色 = `scripts/battle/roles/role_*.gd` 一个类，`BattleRole.create(role_id, player, engine)` 实例化（角色表「脚本」列决定用哪个）。
- 基类定义全部钩子空实现 + 常用工具（`询问()` / `take_skill_reply()` / `notice_skill()` / `施加治疗()` / `安排额外回合()` / `hand_ids_where()` …）。
- `step` 不是角色自己的字段：读写都代理到引擎的“当前状态进度槽”（`battle_role.gd:40`），离开钩子流程才落到 `_持久进度`（见 §4.4）。
- 6 个跨角色 helper 在 `scripts/battle/skills/`，只负责校验与结算，借用者必须转发触发钩子（见 §9.8）。

### 2.5 `BattleDeck`

`battle_deck.gd`（94 行）：只有 `pile` / `discard` 两个数组，牌库顶是数组末尾。

| 接口 | 说明 |
| --- | --- |
| `init_full()` | 填 `0..CARDSUM-1`（150 张）并洗牌；洗牌用全局 `randi()`，不走引擎的 `_rng` |
| `draw(n)` | 从顶抽 n 张；**牌库空时会把弃牌堆洗回**再抽，仍不够则返回实际张数 |
| `remove_top(n)` | 只从牌库顶取，**不洗回弃牌堆**（“只看牌库顶”的技能用） |
| `peek_top(n)` | 只看不动（目前全库无调用者） |
| `push_discard(cards)` | 进弃牌堆；引擎 `to_discard` 在有角色拦截时不会立刻调它 |

> 注意：角色脚本可以绕过封装直接 `engine.deck.*`（现有个别角色这么写），所以“牌库变化一定会写日志/广播”这个假设不成立。

### 2.6 `LocalServer` 在战斗里做什么

它不属于战斗规则，但战斗离不开它：

| 职责 | 入口 |
| --- | --- |
| 建房时创建引擎、注入 `send_cb` | `local_server.gd:402-435` |
| 每帧推进回复超时 | `poll()` → `battle.tick()`（`local_server.gd:92-110`） |
| 把 `Action` / `Respond` 转给引擎 | `_on_message` → `battle.on_message(pid, msg_type, data)`（`local_server.gd:337`） |
| 开局：排座 → 选角 → `start_with_roles()` | `_开始本局` / `_start_battle`（`local_server.gd:776`、`1090`） |
| 按人推送快照（只有本人能看到手牌） | `_broadcast_game` / `_engine_send`（`local_server.gd:1184`、`1103`） |
| 重连补发当前询问 | `battle.重发当前询问(pid)`（`local_server.gd:459`、`517`） |
| 掉线标记 / 观战降频 | `battle.set_offline()` / `_请求观战快照()`（`local_server.gd:268`、`1159`） |
| 终局后解散房间 | `poll()` 检测 `battle.phase == Over` → `_解散房间`（`local_server.gd:99`） |
| 调试指令 | `DebugReq` → `battle.debug_key()`（`local_server.gd:342`） |

### 2.7 卡牌身份：实例号与牌面

同一张牌面在场上**可能同时有多份**（测试指令发牌会克隆；正常对局是一张牌面一张），所以卡牌有两条 id：

| 概念 | 值 | 用途 |
| --- | --- | --- |
| **牌号（牌面）** | 卡表 `卡牌#N`（0~149，虚拟牌 1000+） | 规则判定、白名单、日志、卡面 |
| **实例号** | `序号 × GConst.实例步长 + 牌号`（步长 10000） | 手牌 / 盖牌 / 牌堆 / 弃牌堆 / 基础效果区的存取；客户端选中与节点身份 |

- 牌库里原来那 150 张序号为 0，**实例号 == 牌号**，所以正常对局的数据与原实现等价；克隆牌序号 ≥ 1。
- `GConst.牌号(id)` / `GConst.实例号(牌号, 序号)` 是唯一的换算入口，两端都不维护映射表。
- 分层：**区域存实例号；规则比较、下发白名单、`Card` 消息用牌面**。
  - 上行 `Action.card_ids` / `Respond.card_ids`：实例号（`_do_attack` / `_do_magic` 里拆成 `提交号` 与 `cid` 两个变量）。
  - 下行 `CmdReq.commands[].card_ids` / `option_card_ids` / `ask_skill.cards`：牌面（`_牌面表()` 折面）。
  - `Card` 消息：`send()` 里统一折面（展示 / 音效 / 动画只认牌面）。
  - `Game` 快照的 `hands` / `covereds` / `basic_cards`：实例号（只有本人拿真实牌）。
- 移动牌必须带实例号：`BattlePlayer.取出实例 / 取出一张手牌`、`BattleDeck.取出实例`；
  直接「删一张再 `add_hand_cards(牌号)`」会凭空补一张同牌面新牌，和场上原件撞号（审计时实测过）。
- 弃牌类询问（超限 / 指定弃牌 / 弃盖牌 / 弃已选）用 `BattleEngine._认一张()` 按份数认副本，
  不能按牌号去重，否则两张同牌面只能选出一张。

## 3. 一局战斗的生命周期

```text
建房 CreateRoomReq
  └─ BattleEngine.new()，phase = Idle，房间挂进 _rooms
进房 EnterRoomReq / 分队 JoinTeamReq / 准备 ReadyForGameReq
  └─ battle.add_player / set_color / set_ready；人数满 + 全准备 + 队伍平衡 → 开局倒计时
选角（Random 策略跳过；其余下发 RoleReq → PickBan）
  └─ 名单锁定 → _start_battle(room, 角色表)
开局 battle.start_with_roles(role_map)
  ├─ 洗牌、发 4 张、建座位邻接、按角色表初始化指示物
  ├─ phase = Playing；广播 Game + TurnBegin
  └─ push(SCheckTurnStart) → run()          ← 从这里开始完全由状态机推进
对局中
  ├─ 玩家消息 → on_message → run()
  ├─ LocalServer.poll 每帧 → tick()（超时兜底）
  └─ 每次数据变化 → _broadcast_game()（run 期间合并）
终局
  ├─ 士气 ≤ 0 或 星杯 ≥ 5 → _game_over → phase = Over、清空状态栈、_清空等待()
  ├─ 广播最后一帧 Game（over = true）+ 公告
  └─ LocalServer.poll 下一帧发现已结束 → 解散房间；客户端留在结算界面
```

### 3.1 开局初始化（`start_with_roles`，`battle_engine.gd:503`）

按顺序做这些事，顺序本身有意义：

1. `_rng.randomize()`、重建 `BattleDeck` 并 `init_full()`；
2. `balance_colors()`（队伍平衡）、`_rebuild_links()`（建 `pre_id` / `post_id`）；
3. `current_id = first_id`、`round_id = 1`、`phase = Playing`；
4. 清空额外回合状态、`team_morale = [15, 15]`、星石/星杯清零；
5. 清手牌/盖牌/基础效果、`ready = true`；
6. 按 `role_map`（选角结果）或 `role_pool`（随机）分配角色；
7. 没有脚本的白板角色按角色表初始化指示物；
8. 对每个角色跑一次 `p_before_turn_begin({"init": true})`（角色做开局初始化）；
9. 每人发 `START_HAND = 4` 张；
10. 清空状态栈与进度表、`_清空等待()`；
11. 广播快照 + `TurnBegin`，`push(SCheckTurnStart)`，`run()`。

> 座位顺序不在 `start_with_roles` 里排：`LocalServer` 定完队后先调 `arrange_seats()`，这里只按已排好的 `order` 建邻接。

### 3.2 进行中：谁在推进

- **玩家操作**：`on_message` 写入回复后调 `run()`，状态机一路跑，直到又停在某个 `WAIT`。
- **时间**：`LocalServer.poll()` 每帧调 `tick()`，只负责“回复超时”，不推进正常流程。
- **掉线/重连**：`set_offline(pid, true)` 只影响之后 `wait_for` 的超时时长（5 秒），不影响当前这一次等待；重连后 `重发当前询问` 把同一份询问再发一次。

### 3.3 终局

`_game_over(win_color)`（`battle_engine.gd:5214`）：

- `phase = Over`、`winner = win_color`、`_states.clear()`；
- `_清空等待()`：等待、回复、分步应答、倒计时、弃牌拦截标记全部复位；
- 广播快照（客户端据 `over` 留在结算界面）与“游戏结束”公告；
- 之后的 `push()` 一律被拒（`battle_engine.gd:721`），避免残留流程又被压回来。

## 4. 状态机内核

### 4.1 `run()` 循环（`battle_engine.gd:665`）

```text
while _states 非空:
    st = _states[-1]                  // 栈顶
    _当前状态 = st；_当前进度槽 = _进度表[st]
    r = st.handle(self)
    if phase == Over: break
    if r == WAIT: break               // 停在这里等回复
    if r == SUSPEND: continue         // 先跑刚压入的新状态，之后再回来
    // CONTINUE：本状态完成
    _check_hand_overflow()
    _check_cover_overflow()
    _check_hand_change()
    _check_token_change()
    _check_energy_change()
    if 栈顶仍是 st: 弹出
```

几个细节：

- **安全阀**：单次 `run` 最多处理 20000 个状态，异常状态链不会把主线程卡死（`battle_engine.gd:670`）。
- **终局即停**：`handle` 期间可能已分出胜负，`run` 在 `phase == Over` 时立刻 break，不再补压/结算。
- **`WAIT` 时不做边界检查**：否则会在等待者之上补压新状态，玩家回复回来时被新状态错取。
- **`SUSPEND` 不弹栈**：`continue` 后栈顶是刚压入的新状态，跑完再回来继续本状态。
- **快照合并**：`_running` 期间的 `_broadcast_game()` 只置 `_快照待发`，`run` 收尾统一发一次（`battle_engine.gd:2181`）。不合并的话一次推进能发几十份全量快照，客户端整体重建界面会卡到个位数帧率。
- **进度清理**：`run` 结束时把不在栈里的状态实例的进度表删掉。

### 4.2 三种返回值

| 返回值 | 值 | 语义 | 谁会返回 |
| --- | --- | --- | --- |
| `CONTINUE` | 0 | 本状态完成，出栈，继续下一个 | 大多数状态 |
| `WAIT` | 1 | 正等某个玩家回复，停在这里；收到回复后再次 `handle()` | 询问类状态、钩子（`SHook`） |
| `SUSPEND` | 2 | 先跑刚压入栈顶的新状态，跑完再回来继续本状态 | 压了子流程的状态、角色钩子返回 `URGENT` 时 |

角色钩子里的 `SUCCESS / WAIT / URGENT` 与引擎的 `CONTINUE / WAIT / SUSPEND` **语义**一一对应，但**数值不同**（角色 `WAIT=2 / URGENT=3`，引擎 `WAIT=1 / SUSPEND=2`）；`SHook` 负责转换，`SkillRun` 直接比较角色返回值（`battle_role.gd:14-17`、`battle_engine.gd:15-17`）。

### 4.3 状态边界检查

每个状态 `CONTINUE` 出栈后，引擎统一扫一遍：

| 检查 | 触发 | 目的 |
| --- | --- | --- |
| `_check_hand_overflow` | 有人手牌 > 上限 | 压 `SHandOverflow`（`battle_engine.gd:732`） |
| `_check_cover_overflow` | 有人盖牌 > 上限 | 压 `SCoverOverflow` |
| `_check_hand_change` | 手牌数量变化 | 压 `SRunHandChange` → `p_hand_change` |
| `_check_token_change` | 指示物变化 | 写日志（不改流程） |
| `_check_energy_change` | 个人/队伍星石增加 | 写日志（先获得才写） |

这样做是为了兜住“角色脚本直接改字段/直接加牌”的情况。引擎自己 push 的那几处照旧，重复的会因“栈里已排着一次结算”而跳过。

### 4.4 进度表与 `step`

`_进度表: { 状态实例: { player_id: step } }`，`_当前进度槽` 指向当前状态那一份（`battle_engine.gd:644-662`）。

- 每个状态实例新建时进度从 0 开始；等待 / 挂起后回来继续同一实例，进度自然保留。
- `BattleRole.step` 在钩子流程里读写引擎的进度槽，在流程外落到 `_持久进度`（`battle_role.gd:40-49`）。
- 这取代了早期“每轮把所有人 step 清零 + URGENT 时快照/恢复”的补丁：以前角色在 `p_timeline_*` 里压了伤害，回来时 step 已被别的轮次清零，表现为“同一回合反复询问同一个技能”。

> **但跨钩子轮次的流程仍不能用 `step`**：一轮结束进度就销毁。剑圣的圣剑收尾、烈风技/疾风技推进都用自己类的成员变量（`role_jiansheng.gd:29-39`、`60-64` 有注释说明）。

### 4.5 等待与回复归属

`wait_for(pid, kind)`（`battle_engine.gd:1003`）：

- 记录 `_await_id` / `_await_kind` / `_await_state = _当前状态`；
- 计算截止时刻：正常 60 秒（`RESPONSE_TIMEOUT_MS`），掉线玩家 5 秒（`OFFLINE_TIMEOUT_MS`）；
- `wait_seq += 1`，客户端据此判断“是不是新的一次等待”，避免重复弹提示；
- 广播一次快照，让所有人知道在等谁、还剩多久。

`has_reply()` / `take_reply()` **只认等待归属的那个状态**（`_当前状态 == _await_state`）：等待期间被补压到栈上的其他状态取不到这份回复，也不会顺手清掉它。

`prepare_reply(pid, r)` 允许角色把“下一次应战询问的答复”先攒起来（客户端攒操作的场合），轮到该询问时 `take_prepared_reply()` 直接取用（`battle_engine.gd:1049`）。

| 分组 | 状态类 | 作用 |
| --- | --- | --- |
| 回合骨架 | `SCheckTurnStart` / `SActionPhase` / `STurnEnd` / `SNextPlayer` | 回合开始、行动、结束、轮转 |
| 钩子与通用 | `SHook` | 按座位跑一轮同名钩子 |

## 5. 回合骨架

```text
SNextPlayer（轮转到下家 / 额外回合）
   └→ SCheckTurnStart
        ├ 清额外行动、行动计数、启动标记、跳过标记
        ├ p_before_turn_begin → p_turn_begin
        ├ SPoison（中毒）→ SWeaken（虚弱询问）
        ├ p_between_weak_and_action → p_before_action → p_boot
        └ SActionPhase
             ├ 发 ask_action，等 Action
             ├ resolve_action → 攻击/法术/特殊/技能/放弃
             └ 行动结算完 → (额外行动?) → STurnEnd
STurnEnd
   ├ 还有额外行动 → SAdditionalAction（同回合继续）
   └ p_turn_end → p_after_turn_end → SNextPlayer
```

### 5.1 `SCheckTurnStart`（`battle_engine.gd:3093`）

- `cur.clear_additional_action()`、`跳过额外攻击行动 = false`、`_基础效果额外行动已确认.clear()`；
- `reset_action_counts()`（F2 行动计数从零开始）、`boot_skill_used = false`；
- 收集当前玩家面前的中毒牌，准备 `SPoison`；
- 按**后压先执行**的顺序压入：`SActionPhase` → `p_boot` → `p_before_action` → `p_between_weak_and_action` → `SWeaken` → `SPoison` → `p_turn_begin` → `p_before_turn_begin`；
- 回合上下文 `{player, extra_turn, attack_bonus}` 随钩子下发，角色可区分普通回合与额外回合。

### 5.2 `SActionPhase`（`battle_engine.gd:3205`）

字段：`允许`（ActionType）、`可放弃`、`额外`、`禁特殊`、`额外来源`、`额外数据`、`跳过`。

`handle()` 的分支顺序：

1. `跳过`（挂机超时）→ 直接 `STurnEnd`；
2. `engine.skip_action_phase`（虚弱拒绝 / 跳过行动阶段类技能）→ 记“本回合跳过” → `STurnEnd`；
3. 测试指令“跳过当前回合” → `STurnEnd`；
4. 被【挑衅】→ 强制 `允许 = Attack`、`可放弃 = true`；
5. 把本阶段上下文写进引擎字段（`行动允许` / `行动可放弃` / `行动额外` / `行动禁特殊` / `行动额外来源` / `当前额外行动数据`）；
6. 有回复 → `take_reply()`：
   - `action_type == ChooseExtraAction` → `切换额外攻击()` → `SUSPEND`（重发行动询问）；
   - 否则 `resolve_action(at, r)`；
7. 没回复 → `ask_action(...)` + `wait_for(pid, Msg.Action)` + `WAIT`。

### 5.3 `STurnEnd`（`battle_engine.gd:3366`）

- `回行动阶段 = true`（技能行动被取消）→ 重新压 `SActionPhase`；
- 当前玩家还有额外行动（`contains_action()`）→ 压 `SAdditionalAction`；
- 否则按顺序：`p_turn_end` → `p_after_turn_end`（`after` 里带 `SNextPlayer`）。
  顺序不能反：月女【苍白之月】/ 10803 要在 `p_after_turn_end` 里把额外回合定下来。

### 5.4 `SNextPlayer` 与额外回合（`battle_engine.gd:3394`）

- 先清“当前额外回合”标记；
- 若 `额外回合玩家 >= 0`：不推进 `current_id`、不增加 `round_id`，把行动者切成该玩家，广播 `TurnBegin`（引擎会带 `extra_turn` / `extra_cause` / `attack_bonus`，但这三个字段没进字段表、客户端收不到，见 §11.4），压 `SCheckTurnStart`；
- 否则 `current_id = next_id(current_id)`；当回到 `first_id` 时 `round_id += 1`；广播 `TurnBegin`，压 `SCheckTurnStart`。

安排额外回合的入口是 `安排额外回合(pid, 攻击加伤, 来源)`（`battle_engine.gd:1477`），角色侧有包装 `BattleRole.安排额外回合()`。攻击加伤只由引擎的普通攻击/应战反击统一加（`攻击基础伤害()`，`battle_engine.gd:1501`）；角色自建 `harm` 的攻击技能要自己读这个函数。

## 6. 询问 / 回复

### 6.1 三类询问

| 类型 | 下发 | 上行 | 典型场景 |
| --- | --- | --- | --- |
| 行动询问 | `CmdReq{cmd_type=Action(1), commands}` | `Action{action_type, action_id, dst_ids, card_ids, args, extra_uid}` | 轮到你行动：出牌 / 放技能 / 放弃 |
| 应答询问 | `CmdReq{cmd_type=Respond(2), commands}` | `Respond{respond_id, dst_ids, card_ids, args, partial}` | 应战、魔弹、治疗、弃牌、虚弱、额外行动 |
| 技能询问 | 同上（命令带 `is_skill=true`） | 同上 | “是否发动某技能”，选牌/选目标/选选项 |

所有询问都走 `_询问(pid, cmd_type, commands)`：先记到 `_最后询问[pid]`（供重连补发），再 `send(CmdReq)`（`battle_engine.gd:1738`）。

### 6.2 行动询问的命令表（`ask_action` → `action_commands`）

`commands` 的第 0 项是通用行动：

| 字段 | 含义 |
| --- | --- |
| `respond_id` | 本阶段允许的行动种类（`ActionType`，可能是 `Any=7` / `AttackMagic=8` / 具体种类） |
| `is_extra` / `extra_cause` / `extra_uid` | 是不是额外行动阶段、来源技能号、当前那份额外行动的 `uid` |
| `no_special` | 本阶段禁止特殊行动（发动过“启动”技能后） |
| `card_ids` / `dst_ids` / `extra_element` | 额外行动自带的出牌/目标白名单、限定系别 |
| `extra_attack_causes` / `extra_attack_uids` / `allow_actions` / `extra_attack_cards` / `extra_attack_targets` / `extra_attack_elements` | 本次可切换的额外行动列表，**数组顺序就是显示顺序** |

允许放弃时再追加一项 `respond_id = ActionType.None`。其余项是角色技能按钮：

| 字段 | 含义 |
| --- | --- |
| `respond_id` | `AttackSkill=4` / `MagicSkill=5` / `SpecialSkill=6` |
| `enabled` | 本次能不能用；**不可用也要下发**，客户端置灰 |
| `dst_ids` / `card_ids` / `card_max` / `card_rule` / `card_prompt` | 目标白名单、牌白名单、选牌上限、选牌规则、发动提示 |
| `arg_choices` | 参数选项（每项渲染成一个按钮） |
| `target_max_from_cards` / `card_slot_skill` / `card_slot_element` / `cover_need` | 目标数随牌数变化、逐张选牌条件、盖牌需求 |
| `args` | `[技能号, 最少选牌, 最少选目标, 最多选目标, 选牌来源]` |

“启动”技能每回合只能发一个：`boot_skill_used` 为真时，特殊技能且 `is_free_skill()` 的按钮 `enabled = false`。

### 6.3 应答询问的 `args` 约定（`ask_respond`）

| `respond_id` | 值 | `args` 约定 | `dst_ids` |
| --- | --- | --- | --- |
| `ReplyAttack` | 10 | `[hit_rate, 攻击牌, 应战者, 原攻击者, can_light, 提示伤害]` | 可选的反击目标 |
| `Bullet` | 11 | `[持有者, 当前伤害, 伤害来源]` | 可传递目标 |
| `Heal` | 12 | `[受伤者, 伤害点数, 伤害类型, 可用治疗]` | 无 |
| `Discard` | 13 | `[牌主, cause, 要弃张数]` | `[牌主]` |
| `Weaken` | 14 | `[牌主, 应摸张数, 束缚摸牌数(恒 0), 虚弱牌数]` | 无 |
| `AdditionalAction` | 15 | `args = [causes]`；`dst_ids` = 与 causes 一一对应的可发动 `uid`；`allow_actions` = 每份放行的动作种类；`option_uids` = 全部 `uid` | —（`dst_ids` 位放的是 uid） |
| `DiscardCover` | 16 | `[牌主, cause, 超限张数]` | `[牌主]` |
| `ChooseExtraAction` | 19 | `[uid]`，牌/目标也可放 `card_ids[0]` / `dst_ids[0]` | 目标 |

> `AdditionalAction` 的 `dst_ids` 装的是 uid（历史形状），不是玩家 id；客户端按 `option_uids` 认人。新增应答类型时别照抄这个特例，优先用 `option_uids`。

### 6.4 技能询问（`ask_skill`）

命令形状（`battle_engine.gd:1951`）：

```text
respond_id = 技能号
is_skill   = true
args       = [need_card, need_target, card_source, 选项数, 选项值1, 选项值2, ...]
notes      = [选项文案...]                 // 与选项值一一对应
option_skill_ids / option_card_ids / option_enabled / option_need_cards / option_need_targets / option_targets
default_option / no_parent                 // 行动结束响应用
can_cancel / card_max / card_rule / cover_need / cards / dst_ids
preview_base / preview_kind / preview_ids / preview_damage / can_light / ask_text
```

- `card_source` 取 `GConst.CardSource`：手牌 / 盖牌 / 两者皆可 / 基础效果牌；
- 选项值 0 留给“不选/摸 0 张”这类正常值，取消用空 `args`；
- 选项不可用时写 `enabled = false`，客户端置灰但仍显示；
- 纯“确定/取消”的技能询问也会带 `args`（选项数为 0）。

### 6.5 发送、记录、重发、刷新

- `_询问()` 把最后一次询问写进 `_最后询问[pid]`；玩家重连后 `重发当前询问(pid)` 原样再发（`battle_engine.gd:1746`）。不补发的话客户端手里没有询问，只能干等超时。
- `_刷新技能可用(pid)`：每次发快照时重算这名玩家此刻能放的技能，**有变化才重发**行动询问（`battle_engine.gd:1757`）。手牌、能量、治疗、阵营都会影响技能可用性，所以不盯单个字段，跟着快照走。
- 客户端上行封装：`Logic.send_action(...)` / `Logic.send_respond(...)`（`client_logic.gd:519`、`537`），`extra_uid > 0` 才写进包。

### 6.6 超时兜底（`tick` → `_build_timeout_reply`）

`tick()` 由服务端每帧调用（`battle_engine.gd:1416`）：没在等 / 已有回复 / 没到点就直接返回；到点后构一条“最保守”的默认回复：

| 询问 | 默认回复 |
| --- | --- |
| 行动询问，允许放弃 | `action_type = None`（放弃） |
| 行动询问，不允许放弃（普通行动阶段） | 没有合法兜底 → 把这名玩家的 `SActionPhase.跳过 = true`，直接收尾换人 |
| 技能询问 | 空 `args`（不发动）；已有分步应答就带上它；不可取消且有目标 → 随机打一名合法目标 |
| 应战 / 魔弹 | `GiveUp` |
| 治疗 | `0` 点 |
| 额外行动 | 空 `args`（放弃） |
| 弃牌 / 弃盖牌 / 虚弱 | 空牌，交给状态自己补齐 |

默认回复里带 `is_timeout = true`，角色需要区分“挂机”与“主动取消”时读它。没有兜底的询问只公告“仍在等其操作”，继续等。

### 6.7 分步应答与取消

- `Respond.partial = true`：只报“这一步选好的值”，不算最终回复；引擎记到 `_pending_partial`，继续等目标/牌（如【剑气斩】先选剑气数）。
- 空 `args` + 空 `dst_ids` + 空 `card_ids` 视为“取消”：行动结束响应里取消只结束响应，**不清空、不跳过任何额外行动**（`_处理行动结束取消` 现在是空实现，`battle_engine.gd:1222`）。
- 技能询问的 `can_cancel = false` 表示强制询问，客户端把“取消”置灰，超时也不按取消收尾。

### 6.8 错误与重选

`ErrorInput{error_type, commands}` 表示操作被驳回（`battle_engine.gd:4661` 等）。客户端收到后清掉待选状态并提示“操作无效，请重新选择”，服务端同时重新进入对应阶段（如 `push(SActionPhase.new())`），让玩家重选。**驳回前不扣牌、不扣资源**：校验都在结算之前。

## 7. 行动结算

### 7.1 `resolve_action` 总闸（`battle_engine.gd:4667`）

```text
1. 额外行动阶段：按 Action.extra_uid 换队（_切换额外行动），换完再判合法性
2. v_allow_action 总闸（角色可追加限制，如“审判满 4 时只能末日审判”）
3. 行动禁特殊：发动过“启动”技能后禁止 Special / SpecialSkill
4. match action_type：
   None → STurnEnd
   Unactional → _do_unactional（弃光手牌摸 4 张，不结束回合）
   Attack → _do_attack
   Magic → _do_magic
   Special → _do_special
   AttackSkill / MagicSkill / SpecialSkill → _进入技能行动
   其他 → STurnEnd
```

换队的意义：以前只有出攻击牌会换队，额外行动阶段“先点行动、再点技能”永远消耗服务端当前那一份。现在打牌和技能行动都带 `extra_uid`，先换队再按换后的放行种类判。

### 7.2 攻击（`_do_attack`，`battle_engine.gd:4773`）

1. 取 `card_ids[0]` / `dst_ids[0]`；缺一项按放弃处理；
2. 额外行动阶段：`args[0]` 是选中的 `uid`，与当前不同则 `_直接切换额外攻击()`；
3. `v_attack(cid, dst, players)`：角色可拒绝（牌型/系别/手牌数限制）；
4. `dst_p.v_attacked()`：防守方可拒绝成为目标（潜行）；
5. `校验额外行动限制()`：这份额外行动自带的出牌/目标/系别/命格规格；
6. `_记录行动并收尾()`：记 F2 计数 + 压 `STurnEnd` + 压 `p_after_attack` 与行动聚合器；
7. `p_attack_card`：角色可把这张牌“视为”另一张（如苍炎魔女烈焰形态视为火系【火焰斩】）；
8. 构造 `harm = {src, dst, point: 攻击基础伤害(), cause: CAUSE_ATTACK, type: Attack, card_id: 用牌, is_active: true}`，压 `SAttackCard`；
9. 扣牌、弃牌、广播 `Card{type=Use, as_card_id=视为牌}`。

> 第 8 步先 `push(SAttackCard)`、第 9 步才 `take_from_hand(已展示)`：这样“展示手牌”钩子压在攻击状态之上先结算（封印伤害先于本次攻击）。

### 7.3 法术（`_do_magic`，`battle_engine.gd:4834`）

按牌名分支：

| 牌 | 流程 |
| --- | --- |
| 【圣盾】 | `p_before_magic` 闸 → 额外行动限制 → `v_basic_effect_target` → `v_shield` → 扣牌 → 记录行动收尾 → `add_basic_effect` → `push_show_hand` |
| 【虚弱】/【中毒】 | 同上（`v_weaken`；中毒没有额外校验） |
| 【魔弹】 | 落点候选由 `role.missile_targets()` 给出（默认右手边最近对手，魔导可逆向）→ `v_missile` → 扣牌弃牌 → 记录行动收尾 → 广播 `Card` → `push(SMissileAsk)` → `push_show_hand` |
| 其他 | `_reject_action`（【圣光】只作响应，不能主动施放） |

【圣盾】/【虚弱】/【中毒】在扣牌之前先过 `v_basic_effect_target(dst, card)`：被拒的目标不能白吃一张牌。基础效果变更钩子必须在“行动结束”之后压（LIFO 下先跑），否则天使羁绊这类钩子会被埋在回合结束之下，永远轮不到。

### 7.4 特殊行动（`_do_special`，`battle_engine.gd:5021`）

| 行动 | 校验 | 结算 |
| --- | --- | --- |
| 购买 `Buy=0` | `v_buy(args)` | 战绩区加星石 → 摸 3 张 → 记录行动收尾 → `SHandOverflow` |
| 合成 `Synthesize=1` | `v_synthesize(...)` | 扣星石 → 星杯 +1 → 摸 3 张 → 星杯 ≥ 5 立即终局；否则对方 −1 士气（`lose_morale(..., CAUSE_SYNTHESIZE)`） |
| 提炼 `Extract=2` | `v_extract(args, 队伍星石, dst_ids)` | `p_before_extract` 全员闸 → 从战绩区取出归自己（【冒险者天堂】按标记走另一套分配）→ `p_extract_to` / `p_after_extract` |

特殊行动的摸牌**不走 `push_draw`**：技能表里【水影】等响应写明“除【特殊行动】外”。

### 7.5 技能行动（`_进入技能行动` → `SkillRun`，`battle_engine.gd:4713`、`4556`）

```text
_进入技能行动(kind, data)
 ├ 判断“启动”：kind=special 且 role.is_free_skill(技能号)
 ├ 启动 → push(SActionPhase(…, 禁特殊=true))    // 不结束回合，还能再攻击/法术
 └ 普通 → push(STurnEnd)
 └ push(SkillRun(kind, data, 启动, 行动额外, 行动额外来源))
```

`SkillRun.handle()`：

1. 首次进入做校验：`boot_skill_used` 限制 → `校验额外行动限制()` → `校验基础效果放置目标()` → `v_attack_skill / v_magic_skill / v_special_skill`；任一失败 → `ErrorInput` + 回 `SActionPhase`；
2. 校验通过记一次行动计数（`启动` 不算行动）；
3. 调 `p_attack_skill / p_magic_skill / p_special_skill`（基类默认 `EMPTY_HANDLE`）；
4. 返回 `WAIT` 就等回复；返回 `URGENT` → 先跑压入的结算，回来再收尾（角色覆写 `技能URGENT后重入(action)` 返回 true 的技能除外：回来会重入一次技能本体接着做，如 7802 魔法入门摸牌后先走超限结算）；
5. 收尾：`启动` 只触发 `p_after_*`；普通行动触发 `_push_action_end_hooks()`（`p_after_*` + `p_action_end` + 聚合器）；被取消的行动撤销计数、不触发 `p_action_end`。

### 7.6 放弃 / 无法行动

- 放弃：`ActionType.None` → `STurnEnd`（额外行动阶段放弃即结束本回合）。
- 无法行动：`ActionType.Unactional` → 弃光手牌（亮牌 + 弃牌动画）→ 直接 `draw(4)`（不走 `push_draw`，不触发“摸牌前”响应）→ 压 `SHandOverflow` → 重新进入 `SActionPhase`（不结束回合）。

### 7.7 额外行动的引擎侧

| 环节 | 实现 |
| --- | --- |
| 授予 | `BattlePlayer.add_action(allow_action, cause, direct, skip_notice, spec)`；取 `order`（获取序号）+ `uid`（唯一 ID） |
| 排序 | 只由 `BattleEngine.额外行动序列(pid, 含当前)` 决定（队列按 `order` 升序 + 可选当前），客户端照单渲染 |
| 询问 | `SAdditionalAction`：`direct` 的直接进入；其余发 `RespondType.AdditionalAction` 询问 |
| 进入 | 移除队列项 → 补扣代价（未付过时调 `行动结束确认代价`）→ 基础效果补移除赐福牌 → 广播 `Skill`（`skip_notice` 时跳过）→ 压 `p_additional_action` + `SActionPhase(允许, 可放弃=true, 额外=true)` |
| 切换 | `_切换额外行动(cur, 选中, 作为)`：必须 `direct` + `switchable` + 放行该动作；当前那份退回队列、新的成为当前 |
| 响应 | `S行动聚合器` 收角色选项 + 基础效果 + 队列里未确认的行动；选中后分派回来源 |
| 记账 | 角色在 `p_action_end` 里按 `is_extra` / `extra_cause` 记“本回合已用” |

`spec` 支持的键（`battle_player.gd:390-398`）：

| 键 | 含义 |
| --- | --- |
| `cards` | 出牌白名单；空 = 不限；`[GConst.手牌白名单_全禁]`（-1）= 一张都不给 |
| `skill_cards` | **只对技能行动生效**的白名单，存在时优先于 `cards`（`battle_engine.gd:2905`）；用于“普通法术只能出【魔弹】、技能行动却可用地/风系牌”这类区分 |
| `targets` | 目标白名单；空 = 不限；`[GConst.目标白名单_无]`（-1）= 一个都没有 |
| `element` | 限定系别；**即使 `cards` 为空也是限制**（引擎按卡库现算该系攻击牌） |
| `card_fate` | 限定命格；同样即使 `cards` 为空也是限制 |
| `switchable` | 额外行动阶段能否切走（默认 true） |
| `in_end_response` | 是否作为“行动结束响应”的选项（默认 false） |

> `element` / `card_fate` 是“限制”而不是“提示”，容易误解：写 `{"element": Wind}` 就等于“只能用风系攻击牌”。

### 7.8 行动结束响应（`S行动聚合器`，`battle_engine.gd:3434`）

`push_after_action()` 压栈顺序：`STurnEnd` → `_push_action_end_hooks()`，后者再压：

```text
压栈顺序（后压先执行）：
  STurnEnd
  SHook(p_action_end)
  S行动聚合器                        ← 只在 attack / magic 结束压
  SHook(p_after_attack / p_after_magic)

执行顺序：p_after_* → 聚合器 → p_action_end → 回合结束
```

聚合器只做四件事（收集 / 合并 / 发问 / 分派）：

1. `_收集行动结束选项()`：角色 `行动结束来源()`（默认 `action_end_options()`）+ 基础效果额外行动选项，排序 `_sort`：队列额外行动 0 → 基础效果 1 → 角色响应 2；
2. 全部不可发动时不弹询问；有一项可用就全部列出（不可用置灰）；
3. 发 `ask_skill(pid, 首项, …, no_parent=true, default_option=0)`；
4. 选中后 `_分派行动结束选项()`：`role` → `resolve_action_end_option()`；`extra` → `resolve_queued_extra_action()`；`basic` → `_确认基础效果额外行动()`。

多步技能返回 `WAIT` / `URGENT` 时聚合器进入“待决”，等该技能完全结算完再问剩余选项；中途不会插问迅捷赐福。

**响应阶段不能使用额外行动**：当前那份额外行动按钮、已获得的额外行动/基础效果都置灰，排在响应选项左边；真正使用留到响应结束后的 `SAdditionalAction`。取消响应只结束响应：已确认 / 已获得的额外行动全部保留，但**本次响应里还没确认的选项**（`in_end_response` 且未 `direct`，如女武神【神圣追击】、剑帝【不屈意志】）以及**基础效果授予的行动占位**（迅捷赐福等，确认时才换成 direct 的真行动）由 `S行动聚合器` 出栈时撤回（`_撤回未确认额外行动`）—— 它们只是摆出来让玩家选的选项/占位，留着会漏到额外行动阶段、弹出玩家从没确认过的红色行动按钮。

## 8. 伤害流水线

### 8.1 压栈顺序与执行顺序

`push_harm(harm)`（`battle_engine.gd:2749`）按“后压先执行”压入：

```text
压栈（从下往上，后压先执行）              执行顺序
SHookHarmEnd(p_harm_end)      ──▶  最后：p_harm_end（ctx 按最终目标现算）
SGateTimeline6                ──▶  点数 > 0 才进 Timeline6
SHook(p_timeline_5)           ──▶  p_timeline_5
SAskCross                     ──▶  治疗抵挡询问
SHook(p_timeline_4)           ──▶  p_timeline_4
SHook(p_timeline_3)           ──▶  p_timeline_3
SHarmTimeline3                ──▶  广播 HurtFloat / Hurt
（push_harm 之前 STimeline2Hit 还会压 p_timeline_2_hit，它最先跑）
```

完整一次攻击的路径：

```text
STimeline2Hit
 ├ 广播 Hit{hit=1, src, dst}
 ├ 攻击方战绩区 +1 宝石（应战反击 +1 水晶）
 ├ push_harm(harm)
 └ SHook(p_timeline_2_hit)      // 可改伤害值
      ↓
SHarmTimeline3 → p_timeline_3 → p_timeline_4 → SAskCross
      ↓
SGateTimeline6（点数 ≤ 0 直接结束）
 ├ p_timeline_6                // 可转移伤害
 ├ SHarmTimeline6
 │   ├ p_before_draw
 │   └ SHarmDrawOverload：draw(point) + push_overload_with_harm(harm)
 ├ SHookTimeline6Drawn → p_timeline_6_drawn（ctx 现算）
 └ SHookHarmEnd → p_harm_end（ctx 现算）
```

### 8.2 命中与应战（`SAttackCard` / `SAttackedAsk`，`battle_engine.gd:3695`、`3743`）

`hit_rate` 三档（`GConst.HitRate`）：

| 值 | 含义 | 处理 |
| --- | --- | --- |
| `Normal=0` | 正常应战 | 发 `ReplyAttack` 询问 |
| `NoReattack=1` | 对方无法应战（暗系攻击牌默认、烈风技） | 直接 `STimeline2Hit` |
| `NoMiss=2` | 强制命中（圣剑第三刀） | 直接 `STimeline2Hit` |

普通应战的回复分支：

- **应战 `Reattack.Attack`**：校验反击目标（敌方、不是自己、不是原攻击者）→ 压 `p_reattack` → `SReattackGo`（真牌进弃牌堆、可“视为”另一张、以攻击基础伤害发起新攻击）；
- **格挡 `Reattack.Block`**【圣光】：`v_block` 通过 → 扣牌弃牌 → `STimeline2Miss` → 展示手牌钩子；
- **放弃**：先查【圣盾】/【天使之墙】→ 有则移除并 `Miss`；没有则 `STimeline2Hit`。

代应战（【式神咒束】）：`dst.reattacker` 指向代替者，`defender` 换成他，伤害仍落在原目标；询问的 `args[2]` 必须是“应该由谁来应战”，否则代替者客户端会把询问丢掉。

### 8.3 治疗抵挡（`SAskCross`，`battle_engine.gd:4083`）

- 任何伤害都能用治疗抵挡，类型只用于文案；
- 角色可在 `p_timeline_4` 关掉（`harm["cross_available"]=0`）或限制上限（`harm["cross_max_point"]=N`）；
- 玩家回复 `args[0]` 是使用点数，`clamp` 到可用治疗；
- 扣治疗、扣伤害、写一条 `GossipType.Combat` 日志（“用 N 点治疗抵挡 M 点伤害，治疗 a→b，伤害 c→d”）。

> 【治疗】是角色身上的减伤点数；【士气】是整队共用的血条，两者不是一回事。

### 8.4 超限弃牌与掉士气（`SHandOverflow`，`battle_engine.gd:4385`）

1. 找第一个手牌超上限的玩家，问 `RespondType.Discard`；
2. 玩家选好要弃的牌后，先给月女【新月庇护】一次机会（`p_xin_yue`）：把这几张变成【暗月】且本次不掉士气；
3. 否则 `take_from_hand` → 压 `SHandOverflow`（继续下一个超限者）→ 压 `SOverloadMorale` → `to_discard`（弃牌前拦截钩子 `p_before_discard` 会压在上面先跑）。执行时是**弃牌拦截/弃牌 → 掉士气 → 下一个超限者**；
4. `SOverloadMorale` 依次跑 `p_before_lose_morale → p_xin_yue → p_lose_morale → p_fix_morale → p_true_lose_morale`，最后由 `SApplyOverloadMorale` 扣士气并 `_check_game_over()`。

**伤害上下文必须随身带**：`push_overload_with_harm(harm)` 会把 `cause` / `type` / `no_morale` 记进这次超限结算。原因是 `last_harm_cause` 是全局字段，连续两人受法术伤害时前一个人的掉士气已经把它清零，后一个人就判不出“因法术伤害掉士气”（表现为【神之庇护】只结算一次）。

**`no_morale`**（伤害转移带来的免士气）：超限牌照弃，只跳过扣士气这一步；标志随这次伤害的超限结算一起消费，不做全局开关。

### 8.5 非伤害掉士气（`lose_morale`，`battle_engine.gd:5187`）

用于“不是伤害造成”的士气损失：合成星杯扣对方 1 点、逆反居合斩、暗月诅咒等。同步调用，钩子内不能等待玩家输入；`ctx.harm_cause = cause`、`type = HarmType.None`（**不能沿用最近一次伤害的上下文**，否则按 type 判定的技能会把非伤害惩罚误判成“因伤害掉士气”）。

可等待的掉士气（如天使【神之庇护】要付代价）走 `SOverloadMorale`，只在“干净栈位”压入。

### 8.6 伤害转移（`转移伤害`，`battle_engine.gd:2776`）

- 只能在 `p_timeline_6` 内调用：此时治疗已结算、按点数摸牌还没开始；
- 改 `harm["dst"]`、记 `redirect_from`，可选 `no_morale = true`；
- 之后的摸牌 / 超限 / `p_timeline_6_drawn` / `p_harm_end` 都读新目标（后两个钩子的 ctx 由 `SHookTimeline6Drawn` / `SHookHarmEnd` 在触发时按 `harm` 现算）。

### 8.7 魔弹（`SMissileAsk`，`battle_engine.gd:3896`）

- 打出：基础伤害 `MISSILE_BASE_POINT = 2`；方向由打出时决定（默认顺向 post；有【魔弹掌控】可逆向 pre）；
- 传递：持有者可出【魔弹】继续（伤害 +1）、出【圣光】抵挡（终止、无伤害）、放弃（有【圣盾】/【天使之墙】则挡下，否则受伤）；
- 同一轮每人只参与一次；一轮结束后重置参与记录，新一轮第一个目标不能是刚把魔弹传给自己的人；
- 传递时不能改方向；
- 10603 的“弃 2 张同系牌视为【魔弹】”走 `v_remissile_multi()`，两张牌一起结算、继续传递。

### 8.8 结算与终局

`_check_game_over()`（`battle_engine.gd:5205`）：任一队士气 ≤ 0 → 对方胜；合成时星杯达到 `GRAIL_WIN = 5` 当场终局。终局见 §3.3。

## 9. 技能层

### 9.1 角色 = 钩子集合

```gdscript
extends BattleRole

func p_before_turn_begin(_ctx: Dictionary) -> int:
    return SUCCESS

func available_skills() -> Array:
    return [{"type": GConst.ActionType.AttackSkill, "id": 105, "name": "剑影",
             "need_card": 0, "need_target": 0}]

func p_attack_skill(action: Dictionary) -> int:
    return SUCCESS
```

角色脚本自己保存“本回合已用”“形态”“指示物数量”等状态；引擎只按钩子调用，不替角色记技能状态。

### 9.2 钩子机制（`SHook`，`battle_engine.gd:3059`）

```text
SHook.handle():
  while _iter < order.size():
      r = players[order[_iter]].role.call_hook(hook, ctx)
      if r == WAIT:    return WAIT        // 整个轮次暂停，等这名玩家回复
      if r == URGENT:  return SUSPEND     // 先跑他压入的新状态，回来从这里继续
      _iter += 1
  // 轮次跑完：压 after 数组（逆序，保证 after[0] 先执行）
```

- 每个角色每轮**只调用一次**；同一个钩子里要连续做几件事，就自己用 `step` 推进。
- `ctx` 是**同一份共享 Dictionary**：前一个座位改的 `hit_rate` / `check_shield` / `harm`，后面的座位看得到（应战/烈风技这类“前面的人改、后面的人读”靠它）。
- 返回 `WAIT` 后，引擎用 `wait_for()` 等回复；回复回来 `SHook` 再次 `handle()`，从**同一位玩家**继续（`_iter` 没动）。
- 返回 `URGENT` 前必须先把 `step` 推过该子技能，否则回来会重跑（见 §14 坑 1、2）。
- 技能本体 `p_attack_skill` / `p_magic_skill` / `p_special_skill` 的默认返回值是 `EMPTY_HANDLE`（1），不是 `SUCCESS`；而 `EMPTY_HANDLE` 的数值又恰好等于引擎的 `WAIT`（1）——两套常量不要混用（见 §14 坑 15）。

### 9.3 校验 `v_*` 与技能行动

- `v_*` 只做校验，**不扣资源、不置回合标记**（技能维护约定 §12）。原因：`_选择额外攻击响应` 会先用 `v_attack` 预校验；校验里改了资源，这份行动会当场失效。
- 主动技能入口有三个：`v_attack_skill` / `v_magic_skill` / `v_special_skill`，对应 `SkillRun` 的三类。
- 校验顺序：启动限制 → 额外行动规格 → 基础效果放置目标 → 角色 `v_*_skill`。

### 9.4 主动技能的标准流程（以剑圣【剑影】105 为例）

```gdscript
func action_end_options(_ctx: Dictionary) -> Array:
    var out: Array = []
    if not used_jian_ying and not active_jian_ying and not _contains_action(JIAN_YING):
        out.append({"value": JIAN_YING, "label": "剑影", "skill_id": JIAN_YING,
                    "enabled": player.get_energy() > 0})
    return out

func resolve_action_end_option(cause: int, _reply: Dictionary, _ctx: Dictionary) -> int:
    if cause == JIAN_YING:
        if not _jian_ying_paid:
            if player.get_energy() <= 0:
                return GConst.GE_INVALID_ACTION
            player.remove_energy(1)          # 水晶优先，没水晶扣宝石（脚本里也可手动 set_crystal/set_gem）
            _jian_ying_paid = true
            engine._broadcast_game()
        notice_skill(JIAN_YING, [])
        player.add_action(GConst.ActionType.Attack, JIAN_YING, true, true)
        active_jian_ying = true
        return SUCCESS
    return resolve_queued_extra_action(cause)

func p_additional_action(ctx: Dictionary) -> int:
    ...                                      # 旧路径 / 直接入队时补付
    return SUCCESS

func p_action_end(ctx: Dictionary) -> int:
    if bool(ctx.get("is_extra", false)) and int(ctx.get("extra_cause", 0)) == JIAN_YING:
        used_jian_ying = true
        active_jian_ying = false
    return SUCCESS
```

要点：

- **选项只描述，不发询问**：`action_end_options()` 返回 `value/label/skill_id/enabled`，询问由聚合器统一发；
- **代价在确认时付**：`resolve_action_end_option` 里扣能量；取消响应后直接进入时，`_进入` 发现 `已付费` 为假会再调一次 `行动结束确认代价`；
- **进入时只结算效果**：`p_additional_action` 不写代价、不写一次性效果；
- **结束时记账**：`p_action_end` 按 `is_extra` / `extra_cause` 记“本回合已用”。

### 9.5 行动聚合器接口

```gdscript
func action_end_options(ctx: Dictionary) -> Array
# 返回 [{value, label, skill_id, need_card, need_target, card_source, targets, enabled, card_id, _kind, _sort}]

func resolve_action_end_option(cause: int, reply: Dictionary, ctx: Dictionary) -> int
```

- 基类默认会把队列里 `in_end_response = true` 且非 `direct` 的额外行动也作为选项返回（`battle_role.gd:235`），所以角色通常不用管队列；
- `card_id` 用于“选项对应一张明牌”（客户端悬停直接摊卡面）；
- 纯“结束后自动 +1 攻击行动”的技能**不进聚合器**：直接在 `p_after_attack` / `p_after_magic` 里 `add_action(..., direct=true)`（封印师 406、剑圣 103、魔剑士 901）；
- 特殊优先级：格斗家念弹 `has_priority_action_end() = true` + `p_priority_action_end()`，排在所有普通响应之前；
- 多步技能返回 `WAIT` / `URGENT`，聚合器会等它结算完再问剩余选项。

### 9.6 额外行动（授予 / 确认 / 进入 / 记账）

见 §7.7 的引擎侧表格。角色侧只需要记三件事：

| 时机 | 做什么 |
| --- | --- |
| 授予 | `player.add_action(种类, cause, direct, skip_notice, spec)`；`spec` 一次写清白名单/系别/命格/可切换/是否响应 |
| 确认（响应里点选） | `resolve_action_end_option()` 里扣费、标 `direct`，必要时 `已付费` |
| 进入 | `p_additional_action()` 按当时状态重算规格（`player.改写额外行动(cause, spec)`）或撤单（`撤回额外行动(cause)`） |
| 结束 | `p_action_end()` 里 `is_extra` / `extra_cause` 记“本回合已用” |

**身份是 `uid` 不是 `cause`**：同一技能可以同时挂好几份（连续两张【疾风技】就是两份 101）。客户端选中/提交一律用 `uid`（`args[0]`），引擎按 `额外行动按ID` / `额外行动下标按ID` 认人；`cause` 只用于显示来源技能名和驱动技能侧逻辑。

**排序只在一处**：`BattleEngine.额外行动序列(pid, 含当前)`（`battle_engine.gd:1297`）。行动结束响应的红色快捷按钮、额外行动阶段的技能栏、额外行动选择框，全部按这个顺序渲染，客户端不排序、不重排。

**`order` 只在真正获得时取号**：基础效果（迅捷赐福）的行动可能被祈祷师/借用角色提前垫进队列，那是演员顺序，不是玩家获得时刻；确认时 `_确认基础效果额外行动` 会 `额外行动新序号()` 重新取号（`battle_engine.gd:1259`）。

### 9.7 基础效果

- 放置：`add_basic_effect(dst, card, src, cause)`；放置前统一过 `v_basic_effect_target`（引擎 `_do_magic`、`SkillRun`、`add_basic_effect` 都走它）；
- 触发与移除分开：`p_basic_effect_triggered`（结算完成后）与 `p_basic_effect_change(triggered=...)`；
- 放置类技能用 `basic_effect_placements(action)` 声明目标，`SkillRun` 执行前统一校验；
- 技能行动批量放置时，任一目标被拒就驳回整个技能行动（不扣牌、不挂效果）。

### 11.3 日志（`Gossip`）也是结构化数据

`GossipType`：`Talk=1` / `Notice=2` / `Combat=3` / `Heal=4` / `Discard=5` / `Skill=6` / `Turn=7` / `Token=8` / `Warn=9` / `Hand=10`。

除了文本，客户端还从几个附加字段拿结构化信息：

- `num`：治疗类 = 治疗点数（冒几个“+”）、弃牌类 = 张数（播弃牌特效）；
- `special_action`：购买/合成/提炼（购买 = 0，所以客户端用 `has()` 判断，不能按值判断）；
- `name`：聊天显示名（服务端拼好，观战者不在玩家表里也能显示）。

### 11.4 已知缺口

两处“服务端写了、字段表里没有”的地方，客户端实际收不到：

1. `TurnBegin`：字段表只有 `id` / `round`（`proto_schema.gd:392`），而引擎在额外回合会带 `extra_turn` / `extra_cause` / `attack_bonus`（`battle_engine.gd:3413`）。目前客户端也没用它们（额外回合只能靠“同一玩家 + 同一回合号”认，`battle_mobile.gd:1100-1102`）。如果以后要在界面上区分额外回合，必须先把字段补进 `proto_schema.gd`。
2. `Command`：引擎会写 `extra_element`（`battle_engine.gd:1800`、`1881`）和 `has_extra_options`（`2088`），但字段表只到 42 号，没有这两项。`ProtoCodec` 按字段表编码，所以**真实联机时会被丢掉**。客户端的额外行动系别目前靠按技能号的兜底表（`const.gd` 的 `角色特性` / `额外行动提示`）补上；`has_extra_options` 参与的那条“取消识别”分支因此不会命中（聚合器自身的取消分支仍然有效）。

这是本工程最容易静默失败的一类问题：**字段名写错 / 没进字段表不会报错，只会永远收到默认值**（历史案例见 §14 坑 6）。

### 12.3 询问入口 `_on_command`（`battle_mobile.gd:2009`）

1. 新询问先做一批复位：清技能按钮、清上一条的选牌约束与本地选项层级、清额外行动暂存（只有“紧接着的技能询问”才保留随这一手提交的额外行动）；
2. `cmd_type == Action`：记 `_行动允许` / `_可放弃行动` / `_行动禁特殊` → `_构建技能按钮(cmds)` → `_进入待选()`；
3. `cmd_type == Respond` 且 `is_skill`：`_是技能询问 = true`、`_skill_ask_id = respond_id` → `_进入技能询问()`（不走 `_进入待选`）；
4. 其余 `Respond`：按 `respond_id` 从 `args` 里取“该由谁应答”（应战 `args[2]`、弃牌/治疗/魔弹/虚弱 `args[0]`），不是自己就丢弃；`AdditionalAction` 走 `_进入额外行动(args, dst_ids, allow_actions, option_uids)`。

`_进入待选()`（2112）只做三件事：按询问类型定 `_need_cards` / `_need_players`、写指令提示、把可点判定交给 `_卡牌能点` / `_玩家可选` / `_确定不可用`。

### 12.4 本地选择状态机

`_mode` 是纯本地标签（和服务端的 `CmdType` 不是一套值）：

| `_mode` | 含义 |
| --- | --- |
| 0 | 无询问 / 等待 |
| 1 | 行动阶段（选牌 + 目标，或点技能） |
| 2 | 应答（应战 / 弃牌 / 治疗 / 魔弹等） |
| 3 | 技能询问 / 额外行动 / 本地询问（含治疗分配、二级栏） |
| 4 | 发动技能（已选好技能，等选牌/目标/选项） |
| 6 | 本地选项（特殊行动选星石等） |

选中状态主要落在：`_sel_cards` / `_sel_players` / `_need_cards` / `_need_players` / `_skill_ask_*`（询问通道）/ `_pending_skill_*` + `_skill_*`（发动技能通道）/ `_二级栏` + `_二级选项` + `_已选参数`（二级栏）/ `_额外攻击切换项` + `_当前额外攻击选择` + `_已提交额外行动`（额外行动）。

### 12.5 确定 / 取消

`_on_ok`（4788）按优先级分支：

1. 攒应战（式神咒束 3301 / 阴阳转换 3306）→ 组装参数提交；
2. 本地选项阶段（提炼 / 特殊行动选石 / 特殊行动）→ 对应确认函数；
3. `_mode == 3`：本地询问 → 治疗分配；额外行动单选 → 提交该 `uid`；技能询问 → `_发送应答(_skill_ask_id, _sel_players, _sel_cards, _已选参数 或 [1])`；
4. `_mode == 4`：`_发送行动(技能类型, 技能号, …)`；
5. 行动阶段：不可行动 → `Unactional`；攻击牌 → `Attack`（`args = [额外行动 uid]`）；法术牌 → `Magic`；
6. 其余按 `respond_id` 组装（应战 `Reattack.Attack/Block`、魔弹 Block/Attack、弃牌 `[]`、虚弱 `[1]`、治疗 `[点数]`）。

`_on_cancel`（4944）：强制询问（`can_cancel = false`）直接 return，不提交；技能询问回空 `args` 取消；应战/魔弹回 `GiveUp`；治疗回 `0`；虚弱回 `0`；额外行动回空 `args`（放弃）。

> 取消**不提交 `[0]` 而是空 `args`**：0 要留给正常选项值（如【魔女之怒】的“摸 0 张牌”）。

### 12.6 技能栏 / 二级技能栏 / 额外行动

- 主技能栏来自行动询问的 `commands[1..]`；服务端 `enabled=false` 或本阶段不放行 → 按钮照样摆出、只置灰。
- 二级技能栏（3469）：技能本体 + 父技能 + “这一手要消耗的额外行动”按钮；**只有二级技能栏把父技能强制最左**，主行动技能栏不得复用。
- 额外行动的展示顺序完全按服务端：响应快捷按钮读 `extra_attack_causes` / `extra_attack_uids`（2453~2492），额外行动阶段技能栏读同一组字段（3151~3206），`AdditionalAction` 询问读 `option_uids`；**三处都不排序**。
- 响应阶段的额外行动按钮一律置灰、不选中；真正使用留到额外行动阶段。
- 切换额外行动只改本地高亮 / 白名单 / `_额外行动放行_选择`，不提交、不重发询问；已选的牌和目标只要在新行动下仍合法就保留。

### 12.7 提交

`_发送行动`（6583）把“本地选中的额外行动”随这一手一起提交：`Logic.send_action(..., extra_uid)`；`_发送应答`（6607）走 `Logic.send_respond(...)`。两者最后都 `_清空待选()`。

额外行动 uid 有两个落点：`Action.extra_uid`（字段）和 `Action.args[0]`（出牌时也带）；`RespondType.AdditionalAction` 的提交是 `args = [uid]`。服务端读 `extra_uid` 优先，`_do_attack` 里也兼容 `args[0]`。

### 12.8 动效与串行队列

- 出牌：`_on_card` → 展示卡牌 → 出手特效 / 飞牌 / 粒子 / 弹道 / 音效；
- 命中：`_on_hit` 只播音效 + 写日志，受击动画由玩家面板自己做；
- 伤害：`_on_hurt` 攻击/魔弹即时播，**法术进 `_法术待播` 队列**（0.25 秒一张，群伤逐个飘），`_on_hurt_float` 对法术跳过（避免双路叠加一个数字都不冒）；

- 日志是双字符串缓冲（`_日志` / `_日志简洁`）+ `AutoClearLog`，不是队列。

## 13. 扩展指南

### 13.1 加一个状态（什么时候需要）

先问三个问题：

1. **只是一次结算 + 可能等回复？** → 写进角色钩子，或复用 `SkillRun` / `SRequestDiscard` / `push_harm`；
2. **需要“压入后先跑、跑完再回来”？** → 用 `SUSPEND` + 新状态，别在钩子里递归；
3. **需要跨多个回合保存进度？** → 不要用 `step`，用角色自己的成员变量或新状态的字段。

新状态的写法：

```gdscript
class S新状态:
    var 参数: int = 0
    func _init(v: int) -> void:
        参数 = v
    func handle(e: BattleEngine) -> int:
        if e.has_reply():
            var r: Dictionary = e.take_reply()
            ...
            return BattleEngine.CONTINUE
        e.ask_respond(pid, GConst.RespondType.XXX, [...])
        e.wait_for(pid, GConst.Msg.Respond)
        return BattleEngine.WAIT
```

注意：`take_reply()` 只在等待归属的那个状态里有效；`push()` 在 `phase == Over` 后会被拒。

### 13.2 加一个技能

1. 设计表补技能行（技能号、类型、说明、提示列）；
2. 角色脚本覆写 `available_skills()` 或对应 `p_*` 钩子；
3. 需要在攻击/法术结束提供可选行动 → 实现 `action_end_options()` / `resolve_action_end_option()`，**不要自己开 `ask_skill` 选项循环**；
4. `p_*_skill` 里压了引擎状态（`push_draw` / `push_harm` / `push`）就返回 `URGENT`；
5. 借用别人独有技 → `preload` helper 并转发全部触发钩子；
6. 客户端要新提示/新指示器 → 加 `const.gd` 的 `角色特性` / `额外行动提示` / `技能指示器` 表；
7. 补自检用例，跑 `tests/runSelfCheck.ps1`。

### 13.3 加一个协议字段

顺序不能反：

```text
proto_schema.gd 字段表 → 服务端写入（battle_engine / local_server）
  → client_logic.gd 转发（如果是新消息类型）
  → battle_mobile.gd 真正使用
  → 自检用例覆盖
```

只在 `proto_schema` 里加字段、服务端也写了，但客户端没读 = 没接上；服务端写了、`proto_schema` 没写 = 客户端**永远收不到**（见 §11.4 和 §14 坑 6）。

### 13.4 加一张牌 / 一种牌型

1. 设计表「卡表」加行（类型、元素、命格、卡名、资源名、技能、说明）；
2. 若是新的“出牌效果”，在 `_do_magic` / `_do_attack` 里加分支；若是新卡名枚举，`GConst.CardName` 加值；
3. 客户端卡面按资源名查找（`Art.card_face()`），不需要改 UI 代码；
4. 补用例。

### 13.5 加一个角色

见 [AGENTS.md](../AGENTS.md) 8.4 的七步清单，核心是：设计表两行 + `role_*.gd` + 立绘 + 导表 + 用例。

### 13.6 检查清单

- [ ] 合法牌/目标/资源在服务端有校验，客户端只是置灰；
- [ ] 不可用选项 `enabled = false` 下发，没有删项；
- [ ] 新字段贯通 schema → 服务端 → client_logic → battle_mobile → 测试；
- [ ] 新状态/新钩子在 `run()` 语义下能正确 `CONTINUE / WAIT / SUSPEND`；
- [ ] 额外行动带 `uid`，代价在确认时付，结束在 `p_action_end` 记账；
- [ ] 没有在 `v_*` 里扣资源或置回合标记；
- [ ] `p_*_skill` 压状态后返回 `URGENT`；
- [ ] 跑过全量自检（当前 62 例），区分新增失败与原有失败。

## 14. 设计约束与历史坑

| # | 坑 | 结论 / 正确做法 |
| --- | --- | --- |
| 1 | 技能压了状态却返回 `SUCCESS` | `SkillRun` 会把“行动结束响应”压在这些状态上面，玩家先看到响应、响应完才结算（女武神【秩序之印】踩过）。压了状态就返回 `URGENT` |
| 2 | 用 `step` 跨钩子轮次 | 一轮结束进度就销毁。跨轮次流程用角色自己的成员变量（剑圣圣剑收尾、烈风技推进） |
| 3 | 按 `cause` 认额外行动 | 同一技能可以挂多份；身份是 `uid`。选项/切换/进入/提交全部按 `uid`，`cause` 只用于显示与技能侧逻辑 |
| 4 | 提前给基础效果行动取号 | `order` 只在“玩家真正拿到”时取；迅捷赐福确认时要重新取号，否则会排到自动获得的行动前面 |
| 5 | 客户端二次排序额外行动 | 排序只在 `额外行动序列` 一处；客户端照 `extra_attack_uids` / `option_uids` 原序渲染 |
| 6 | 字段没写进 `proto_schema` | 客户端永远收不到（`extra_order` 恒为 0 的教训）。现在 `TurnBegin` 的 `extra_turn` / `attack_bonus`、`Command` 的 `extra_element` / `has_extra_options` 都属于这一类 |
| 7 | `run` 期间直接发快照 | 一帧几十份全量快照，客户端重建界面卡到个位数帧率。走 `_broadcast_game()`，`_running` 期间只标脏、run 收尾发一次 |
| 8 | `WAIT` 期间补压状态 | `run` 特意在 `WAIT` 时不做边界检查；否则回复回来会被新状态错取。需要等回复就别在等待者之上压状态 |
| 9 | 超限掉士气不带伤害上下文 | `last_harm_cause` 是全局字段，连续两人受伤会被清零（【神之庇护】只结算一次）。摸牌超限走 `push_overload_with_harm` |
| 10 | 普通超限误挂“最近一次伤害” | `_from_damage` 只有 `push_overload_with_harm` 建出来的实例才为真；普通超限不能让【新月庇护】误触发 |
| 11 | 在 `v_*` 里扣费 | 校验会被预校验调用多次；扣费放 `resolve_action_end_option` / `p_additional_action`，回合标记放 `p_action_end` |
| 12 | 弃牌没走 `to_discard` | 弃牌前拦截（F6 / 4704）、日志、动效都在 `to_discard` 里；直接 `remove_hand_cards` 会绕过所有钩子 |
| 13 | 魔弹传递时改方向 | 方向只在“主动打出”那一步定；传递者只能沿当前方向传给下一个 |
| 14 | 把 `element` / `card_fate` 当提示 | 它们**是限制**：`cards` 为空时也只看该系 / 该命格的攻击牌 |
| 15 | 混用两套返回值 | 角色 `EMPTY_HANDLE = 1` 与引擎 `WAIT = 1` 数值相同、语义无关；`p_*_skill` 默认返回 `EMPTY_HANDLE`，别把它当“等待” |
| 16 | 在钩子流程里改 `tap` | `tap` setter 会无条件压一轮 `p_tap` 钩子，那一轮会把 `step` 归零（精灵射手在 `p_turn_end` 里改形态踩过）。跨轮次流程用角色自有变量 |
| 17 | 先扣牌再判断 | `take_from_hand` 是**全有或全无**：任一张不在手牌就整体失败、一张不扣。先过滤成合法牌再扣，否则再 `to_discard` 会把牌塞进弃牌堆造成牌张重复 |
| 18 | 不区分两次 `p_xin_yue` | 超限选牌时（`ctx.before_discard = true`）一次、掉士气链里一次；用这个字段区分 |
| 19 | 取消技能行动只返回 `SUCCESS` | 必须调 `engine.取消技能行动()`，否则“技能用完即结束行动”的收尾不会改回行动阶段，计数也会残留 |
| 20 | 技能行动的 `p_after_*` 直接读 `ctx.dst` | `SkillRun` 给 `p_after_attack/magic/special` 的 ctx 只有 `{player, kind, is_skill, action_id}`，没有 `dst` / `card_id`；要自己记 |
| 21 | 按 `cause` 撤回 / 改写额外行动 | `撤回额外行动(cause)` 会删掉**所有**同 cause 项，`改写额外行动(cause)` 只改最先找到的那份；同一技能挂多份时先用 `额外行动按ID()` 定位，或改用 `uid` 流程 |
| 22 | `set_meta` 用中文键 | Godot 只接受 ASCII 元数据键，中文键会静默失败（`has_meta` 永远 false），整段按钮过滤失效（`battle_mobile.gd:176-177`） |
| 23 | 直接引用服务端下发的 `commands` 数组 | `_清空待选` 会 clear 缓存；界面要复制一份（`_行动命令 = cmds.duplicate()`），否则重绘时命令已被清空 |
| 24 | 强制询问回空应答“取消” | `can_cancel = false` 时客户端必须真的挡住取消；回了空应答，服务端会替玩家随机选，等于“取消反而生效” |
