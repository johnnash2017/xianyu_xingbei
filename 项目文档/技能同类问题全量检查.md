# 技能同类问题全量检查（回复没人取）

> 范围：`scripts/battle/roles/*.gd`（54 个角色）、`scripts/battle/skills/*.gd`（6 份借用 helper）、
> `scripts/battle/battle_engine.gd` 的状态类。
> 目的：查「玩家答完一问，服务端却不结算」这类**静默失败**是否还有别处。
> 检查方式：静态扫描（按函数切分 + 阶段标记/询问/取回复的位置关系）+ 逐处读代码确认。
> 与 [英灵召唤回复丢失问题复盘](英灵召唤回复丢失问题复盘.md) 属同一族问题。

> **适用范围说明**：第 0 节列出的 4 个角色（39 / 43 / 82 / 95）属于**本轮仍在制作、尚未过测试与调整**
> 的第二批补录角色（39/40/43/79/82/84/95）。本清单是它们**完稿前要过的检查项**，不是线上缺陷记录；
> 已落地的角色（其余 50 个 + 6 份 helper）在本次检查中没有发现同类问题。

## 0. 结论

- **引擎层**：等待期插队、单槽回复这两种已经收敛（`_挂起回复`），同类不再复发。
- **已落地角色**：其余 50 个角色与 6 份 helper 逐一检查过，没有这族问题
  （含一批写法正确、容易被误判的同型代码，见第 4 节）。
- **制作中的角色**：39 / 43 / 82 / 95 里还有 **14 处**「先推进阶段、再询问」或「重入守卫写在推进之前」的写法，
  回复到达后钩子走不到 `take_*_reply()`，技能效果**静默不结算**，阶段标记还会卡在中间值、之后不再触发。
  这批角色还没过测试与调整，按**收尾清单**处理即可（40 / 79 / 84 未发现此类写法）。

> 这些位置此前没有被自检覆盖：`tests/cases/45_newroles.gd` 是「直接调钩子 + `on_message`」驱动的，
> 覆盖不到「钩子返回 WAIT 后由引擎重入」这条路径，所以那些用例的失败一直按“既有失败”处理。
> 这批角色完稿时，用例需要改成挂到真实状态栈上驱动（见第 5 节最后一条）。

## 1. 两种出错的写法

### 坏写法 A：分支里先把阶段推进，再询问、再取回复

```gdscript
if _步 == 1:
	_步 = 2                 # ← 询问前就推进
	if not engine.has_reply():
		询问(...); return WAIT
	var r = take_skill_reply_full()   # ← 重入时 _步 已是 2，进不来
```

回复回来时钩子重新进入，`_步 == 2`，这个分支不再匹配；函数里也没有 `_步 == 2` 的取回复分支
→ 回复没人取，`_步` 永远停在 2。

**正确写法**（二选一）：

```gdscript
# ① 不推进，重入时仍进同一分支
if _步 == 1:
	if not engine.has_reply():
		询问(...); return WAIT
	var r = take_skill_reply_full()
	_步 = 3

# ② 推进到「等待值」，并给等待值一个取回复分支（猎巫人 / 忌妒少女 / 战斗法师的写法）
if _步 == 0:
	_步 = 1
	if not engine.has_reply():
		询问(...); return WAIT
if _步 == 1:
	if not engine.has_reply(): return WAIT
	var r = take_skill_reply_full()
```

### 坏写法 B：重入守卫写在阶段推进之前

```gdscript
if _步 != 0: return SUCCESS   # ← 回复回来时 _步 已经是 1，直接返回
_步 = 1
if not engine.has_reply():
	询问(...); return WAIT
take...                        # ← 到不了
```

## 3. 影响与表现

> 这批角色还在制作中，玩家侧暂时看不到这些现象；以下是**完稿前必须确认**的行为。

- 玩家点「确定」后：界面收掉，服务端**既不播报也不结算**；日志里没有这一手。
- 阶段标记卡在中间值 → 该技能**本局后续也不再触发**（不是偶发）。
- 引擎侧新增的告警能帮上忙：这类状态出栈时会打印
  `[引擎] … 结束时还挂着一份没取走的回复`（调试版），可作为运行期复核手段。

## 5. 修复方案（建议一次做完，逐处一行级改动）

- **坏写法 A**：把「推进阶段」挪到 `take_*_reply()` 之后（或挪到 `询问(...)` 所在的 `if not engine.has_reply()`
  分支之外）；若该阶段值还被别处依赖，则改为给等待值补一个「有回复就取」的分支。
- **坏写法 B**：把守卫改成「没有回复才挡」——`if _步 != 0 and not engine.has_reply(): return SUCCESS`；
  或直接把守卫挪到「已经处理完、把 `_步` 清回 0」之后。
- **顺带**：`p_after_extract` / `p_harm_end` / `p_timeline_3` / `p_turn_end` 这类「重入守卫」在改动后
  要重新确认「取消 / 超时」分支仍把 `_步` 清回 0，避免下次不再触发。
- **验证**：`tests/cases/45_newroles.gd` 现在用「直连钩子 + `on_message`」覆盖不到 WAIT 重入；
  建议改成把钩子挂到真实状态栈（`引擎.push(SHook.new("钩子名", ctx))` + `run()` + `on_message`），
  这样一次就能覆盖本清单的 14 处。

## 6. 附：检查方法

1. 按函数切分角色脚本，统计 `询问/ask_skill` 与 `take_*_reply` 的位置；
2. 找出「分支内把阶段标记推进到新值 → 其后才有询问 → 取回复在同一分支」的函数，
   再检查函数里有没有「新值的取回复分支」——没有即为坏写法 A；
3. 找出「`if _步 != 0: return` 早于 `_步 = 1`」的函数——即为坏写法 B；
4. 对每个候选逐行读码确认（扫描会误报：有些函数的取回复在函数级、或用反查守卫）。
