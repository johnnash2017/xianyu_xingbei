# 技能维护约定

> 修改角色技能、配置表前先读这份约定。
> 配置表以设计表为唯一权威来源；改表统一用 DSH 的 excel-chat 工具，不再临时写脚本。

> 多步询问（一个技能分几次问玩家）统一走 `BattleRole.多步询问`：设计、段字段一览、施工记录与存量台账见
> [多步询问统一框架-设计与迁移](多步询问统一框架-设计与迁移.md)；本文「多步询问（分段询问）」小节是日常写法约定。

## 触发条件

**只要在修改角色技能，就按本约定执行。** 包括：

- 主动技能、被动技能、响应技能、额外行动
- 技能选项、二级选项、多步选项
- 选牌、选目标、盖牌/手牌混选
- 技能头像提示、伤害/治疗提示、技能指示器
- 技能相关协议字段、一次性状态、数据表

开始改代码或数据前，先按本约定的规范过一遍；改完后按检查清单自检。

## 技能描述：未经明确要求不得修改

- 技能表、卡表里的**技能描述 / 卡牌描述 / 提示文案**属于需求方原文。**除非用户明确要求改某一条，否则不要擅自修改、润色、补全或顺手统一口径。**
- 修 bug 时只改代码逻辑、数值和交互；如果发现描述与实现不一致，先说明不一致点并等确认，不要自行改描述。
- 确需修改描述时，只改用户点名的那一条；改前保留原文对照，改后在回复和提交信息里写清楚。
- 这条同样适用于技能表「说明」「提示」列、卡表说明、角色表文案等所有设计表里的玩家可见文案。

## 术语表（技能原文 → 代码怎么写）

技能表里的说法是**给玩家看的规则**，写代码时先按这张表把它翻译成交互：

| 术语 | 含义 | 代码里怎么落 |
| --- | --- | --- |
| **目标角色** | **玩家可以指定一名角色**（场上的角色都能选：自己、队友、对手都算），不是「固定成本次攻击 / 效果的目标」 | 先发一次「选 1 名角色」的询问（`need_target = 1`，`targets` 给场上全部角色），拿到 `dst_ids[0]` 再对那名角色结算；不可取消时超时由引擎从 `targets` 里代选（见 10701【醋意羞心】） |
| 目标队友 / 目标对手 | 只能指定队友 / 只能指定对手（不含自己，原文另写「含自己」才含） | `targets` 只给对应阵营，其余头像点不动 |
| 目标 / 该角色（已有默认对象时） | 固定为本次攻击目标、本次受伤者、询问里点名的那个人，玩家不能改 | 直接读 `ctx.dst` / 询问里的 `preview_ids`，不要再多问一次 |

> 判断口诀：原文写「目标角色」「指定一名角色」＝要选人；写「目标对手 / 目标队友」＝选人但限定阵营；
> 写「他 / 该角色」＝沿用本次已经定下的对象。拿不准时以设计表原文与需求方口径为准。

## 配置表约定（设计表是权威来源）

`Table/Design/设计表.xlsx` 是配置表数据的**唯一权威来源**。

任何表格数据的修改，都必须先改设计表，再通过导表生成后续文件；**禁止**把 `Table/Csv/*.csv` 或 `Table/TableScripts/DataTables.gd` 当作源文件直接修改。

### 技能 ID

- 补录角色统一用 `技能#<职业名>#<技能名>`，例如 `技能#神射手#精准射击`。
- 每个角色单独建技能行；不要复用其他角色或其他版本的**同名**技能行。
- 已有角色的旧 ID 保持不变；补录角色不要借用旧 ID。
- 代码里不要按「同名技能」写死一个技能号：技能播报、技能指示器、头像提示、测试都要按当前角色的技能行取。
  例：魔导师【魔弹融合】= 803，节日魔导【魔弹融合】= 7602；只写 803 会让节日魔导丢提示 / 播错号。

### 形态/状态

- **横置就是形态**：任何会让角色横置的技能/卡牌，都要在角色表「横置形态」配状态名、「状态底色」配底色；临时横置也照配。
- 状态名优先取技能/卡牌名，或文本里明确写出的【X形态】。

### 适用范围

- 卡表、技能表、角色表、词缀等所有由设计表导出的数据。
- 新增、删除、修改行/列、ID、文案、数值、引用字段。
- 只修改 GDScript 逻辑、不涉及表格数据时，不强制改设计表。

### 正确流程

1. 在 `设计表.xlsx` 中修改目标工作表。  
   只有名称以 `.csv` 结尾的工作表会被导出；当前包括：`卡表`、`技能表`、`角色表`、`词缀`、`文本表`。
2. 在 Godot 编辑器执行「检查并转换表格」，或按 `Ctrl + Shift + T` 重新导表。
3. 检查导出的：
   - `Table/Csv/*.csv`：供人工检查的中间态。
   - `Table/TableScripts/DataTables.gd`：自动生成、运行时真正读取的数据表。
4. 发现数据不一致时，回到设计表修正后重新导表，不要手改生成文件。
5. 提交时，设计表与导表产物一起提交，避免源表和生成结果不一致。

### 改表用插件工具，不要临时写脚本

修改 `设计表.xlsx` 统一用 DSH 的 `dsh-excel-chat` 插件（已装在本机 `web` profile，重启 DSH 后加载），不要再为每次改表现写 Python 脚本。

1. **定位**：先用 `excel_profile` 看表结构，或用 `excel_read` 的 `range` + `maxRows` 分页读目标区域。不要把整张表读进对话。
2. **修改**：用 `excel_operate` 原地写回，**必须显式把 `outPath` 设为原文件路径**：

   ```json
   {
	 "path": "D:/星杯传说工程/星杯传说2/xianyu_xingbei/Table/Design/设计表.xlsx",
	 "outPath": "D:/星杯传说工程/星杯传说2/xianyu_xingbei/Table/Design/设计表.xlsx",
	 "operations": [
	   { "op": "set", "cells": { "技能表.csv!H223": "请选择{n}张【手牌】弃掉" } }
	 ]
   }
   ```

   - 工作表名带 `.csv` 后缀：`技能表.csv`、`卡表.csv`、`角色表.csv`、`词缀.csv`、`文本表.csv`（是否参与导出以上面第 1 条为准）。
   - **不传 `outPath` 会写成 `设计表.edited.xlsx` 副本，原表不变**，这是最容易犯的错。
   - 正常结果：`warnings` 为空，`validation` 的 `anomalies`、`errors` 为空。出现 `warnings` 时先看清再继续。
   - 改单个单元格/文案/数值用 `set`；插行、填充、批量改等多步操作放在同一个 `operations` 数组里一次完成。
3. **清理**：原地写回会在同目录生成 `设计表.xlsx.bak`（改前快照，供 `excel_undo` 回滚）和 `设计表.xlsx.patch.json`（审计日志）。确认导表结果无误后删除这两个文件，不要提交。
4. **导表**：仍按上面的流程执行「检查并转换表格」，生成 CSV 与 `DataTables.gd`。

注意事项：

- 写回前确认 `设计表.xlsx` 没有被 Excel/WPS 打开占用，否则会写入失败或产生冲突。
- 插件首次保存会把 `xl/styles.xml` 默认字体槽的名字从 `等线` 改成 `Calibri`（两者都带 `scheme="minor"`，指向主题字体；单元格值、样式、合并、列宽不变）。如果发现设计表外观有肉眼可见的变化，先停下来确认，不要继续批量改。
- 插件不可用时（新机器未安装、或装了但还没重启 DSH），才退回内置 Python + openpyxl 的临时脚本；脚本和备份放 `.dsh/tmp`，用完删除。
- 重装插件时如果 `dsh plugin add` 报 `ERR_PNPM_VIRTUAL_STORE_DIR_MAX_LENGTH_DIFF`，说明 profile 的 lockfile 由 pnpm 8 生成、与当前 pnpm 11 不兼容；改用 `npx pnpm@8.15.9 add dsh-excel-chat`，再把 `dsh-excel-chat` 补进 profile `package.json` 的 `dsh.profile.bundles`。

### 禁止

- 只改 CSV 或 `DataTables.gd`，不改设计表。
- 直接编辑生成文件中的数值、文案或结构。
- 未经用户明确要求，修改技能 / 卡牌描述或提示文案（见「技能描述：未经明确要求不得修改」）。
- 改了设计表但不导表，导致运行时仍读取旧数据。
- 用临时 Python 脚本直接读写 `设计表.xlsx`（应使用 `excel_operate`）；`excel_operate` 不传 `outPath` 只生成副本，当成原表已改。

### 二级技能栏选项：完整下发，不可用只置灰

适用范围：服务端 `arg_choices`、二级技能栏里的固定分支、以及同一窗口里的固定效果选项。

- 固定选项集合必须**完整、稳定地下发**，不能因为当前条件不满足就用 `if` 少一项或整项消失。
- 当前做不了的项保留在数组里，并写 `"enabled": false`；客户端据此半透明置灰、点不动。
- 技能本体的 `enabled` 只在「至少有一个选项 `enabled`」时为 true。不能只写
  `not 选项.is_empty()`——选项现在始终存在，必须检查是否还有可选项。
- 客户端只负责显示和置灰，不要自行补项或删项；服务端仍要对硬提交的置灰项做兜底校验。
- 选项文案不要用括号包说明；需要补充说明时直接接「，弃 3 张」这种逗号形式。
- **选项按钮禁止纯数字**：数值档位必须写清这一项做什么，不能只把数值当按钮文字（如 `0` / `1` / `2`）。
  例：「摸 0~1 张」的两个选项要写「不摸牌 / 摸 1 张牌」（技能表「按钮」列），不能写「0 / 1」；
  档位类写「弃 %d 张」「移除 %d 点【裁决】」这种带动作和单位的文案。纯数字按钮玩家看不出效果差异，
  也过不了 52 号用例之外的人工检查，新增选项一律按这条写。
- **选项文案写成正式规则短句**：多个动作 / 条件用「，」分隔，不要用「+」把几个动作串起来，也不要用
  「放手牌」「摸0~1」这类口语缩写；术语按技能表写法用【】。
  例：群星启示 ① 写「将 1 张手牌作为【卢恩】，选择 1 个【律法】，你摸 0~1 张牌」，
  不写「放手牌作卢恩 + 选律法 + 摸 0~1」。
- **询问的 options 读 `label`，`arg_choices` 读 `text`，别把键写反**：写错不会报错——
  询问会退回用选项值当文案（于是按钮变成 `0` / `1` / `2`），`arg_choices` 会变成空白按钮。
  选项字典两个键都写最稳；只写一个时必须写对当前通道那个。
  （踩过：星坠女巫【群星启示】/【创刻律动】的摸 0~1 选项只写了 `text`，按钮一直显示 0/1。）
- 选项的系别配色只染卡名本身，不整段染色；卡名不要再用【】包起来。
- **每个选项自带后续选牌 / 选目标时，选牌 / 选目标要挂在选项上、在同一个询问里一次提交**：
  - 服务端给选项写 `need_card` / `need_target` / `targets`（响应询问里 `ask_skill` 下发成
	`option_need_cards` / `option_need_targets` / `option_targets`；发动技能走 `available_skills()` 的
	`arg_choices` 时原样下发）；客户端选中选项只**切换选中**，把该选项的需牌 / 需目标套上，
	玩家在同一步选好牌或目标后按一次「确定」，把「选项值 + 牌 / 目标」一起交上去。
  - **不要**先让玩家点选项、按一次确定，再单独发一条选牌 / 选目标询问 —— 这一层「多余的确定」是踩过的坑。
  - **发动技能（mode 4）优先把选项写进 `available_skills()` 的 `arg_choices`**（对照魔弓【魔眼】/
	【充能】、月女【苍白之月】）：点技能直接进二级技能栏，选中选项后同一步选牌 / 选角色，按一次「确定」
	随行动一起提交。指示器配 `"先弹选项": true`。例：矜贵之女【强予愿行】7804 的三档
	「仅调整自己手牌为 4 / 【战绩区】-1【水晶】调整其他角色手牌为 4 / 【战绩区】-1【宝石】调整其他角色手牌为 4」
	（每档自带 `need_card`＝弃到 4 张的张数，后两档再带 `need_target=1 + targets`）。
	服务端在 `v_special_skill` 里按 action 携带的 `args` / `card_ids` / `dst_ids` 校验后一次结算；
	取消 / 返回＝客户端本地退回行动阶段，不发行动、不扣费。
  - **响应技能也可以作为另一个技能的选项**（如 7802【魔法入门】的第 2 档＝响应 7805【友情羁绊】）：
	选项带 `skill_id`（7805），二级栏按钮按「响应」紫色显示、鼠标指向时弹它的技能说明；
	选项自带 `need_target=2 + targets`（我方有手牌的角色），选中后同一步点 2 名角色，随行动一次提交。
	服务端在 `v_magic_skill` 里按 `args`（1 普通 / 2 响应）与 `dst_ids` 校验，`p_magic_skill` 的 step 0
	直接结算宝石与 7805 播报。注意 `skill_id` 必须写进 [proto_schema.gd](../scripts/core/proto_schema.gd)
	的 `ArgChoice`，否则客户端收不到、按钮不会染响应色也不弹说明。
  - 响应询问（mode 3）这一路由 [const.gd](../scripts/core/const.gd) 的 `技能指示器` 配
	`"攻击结束二选一": true`，走 `battle_mobile._应用攻击结束选项需求`；选项本身就是全部可选项、
	不需要父技能按钮时再加 `"无父技能": true`（如 7803）。**不要**在 `_选中二级选项` 里加
	「点选即提交」的特判（那会把选项界面收掉、把选择拆成两问）。
  - 响应询问第一层的「取消」＝不发动：服务端对空应答按不发动处理（不扣费、不改手牌）。
  - 复查方式：在 [4_battleInteraction.gd](../tests/cases/4_battleInteraction.gd) 这类 UI 用例里喂一条
	带 `option_need_*` / `arg_choices` 的选项询问 —— 点选项后 `_mode` 不变、
	`_skill_ask_need_card / _skill_ask_need_target`（mode 3）或 `_skill_need_card / _skill_need_target`
	（mode 4）已按该项收紧；选满后按「确定」才提交。
  - **选项决定「哪些手牌能点」时，统一用「选项牌白名单」的通用置灰逻辑，不要各技能自己过滤**：
    - 服务端在选项里写 `cards`（牌面数组；空＝不限制；`[GConst.手牌白名单_全禁]`＝一张牌都不给点）。
      发动技能（`available_skills()` 的 `arg_choices`）由客户端 `_选项项` 直接读 `cards`；
      响应询问（mode 3）由引擎把每项的 `cards` 下发成 `CmdReq.option_cards`，客户端写进选项的 `牌白`。
    - 客户端通用规则：选中带 `牌白` 的选项后，名单外的牌置灰；已选的不合法牌由
      `_换选项后重校验` 收回；**选项带牌白但还没选任何一项时，手牌整片置灰**（可点集合还没确定），
      选完选项再放开对应牌。
    - 不要在角色脚本或 `battle_mobile` 里再写「按选项收紧可点牌」的专用函数；新技能只配 `cards` 即可。
    - 服务端仍要在 `v_*` / `p_*` 里复核每张牌（在手、属于该选项允许的系别/牌型、数量上限）；
      非超时非法提交一律 `ErrorInput` 重问，不要静默过滤、换牌或随机补齐。
    - 示例：异教徒 9507 / 9508 的四系选项各带「手里该系牌」的 `cards`（该系没牌就写
      `[GConst.手牌白名单_全禁]`）。旧式 `技能指示器.选项牌系` / `选项目牌型` 只留给没有
      `cards` 的少量老技能，新技能优先用 `cards`。
  - 只有选项要进入**另一层选项 / 另一类选择**、没法用同一问表达时，才点中即进入下一层（不再先按确定）。
  - 数值 / 构成参数（选几张、星石组合、点数分配）仍按「确定」提交，避免误触把数值定死。
  - 分多问的选项：**先选的那一档的代价要先结算完，再问下一档**。例：矜贵之女【Magic!】7803
	第 3 次先问「弃 2 张牌」、再问「战绩区 +2【宝石】」——选完弃牌就当场入弃牌堆并播报，
	然后才弹宝石询问；不能把弃牌拖到宝石确定之后一起结算。
  - 例：7803 的「额外+1【法术行动】」「我方【战绩区】+2【宝石】」没有后续选牌，选中后按一次确定即可；
	它们和「弃 2 张牌」摆在同一排，靠 `enabled` 区分当前能不能点。
  - 注意：`_攻击结束二选一` 这类「当前询问」标记在 `_清空待选` 里必须复位，否则下一次发动
	带 `arg_choices` 的技能（如【魔眼】）点选项会被误当成响应二选一处理，选项需求全部失效。
- 多级询问可以取消回到上一层时，父按钮右侧必须提供明确的「返回」按钮，不能只靠「取消」键
  或提示文字说明；服务端的空应答/取消语义要与该返回行为一致。
- 例外：选项本身就是随资源/牌数动态枚举的数值档位（如「移除 1..N 张」，N 是当前可用上限），
  可以只生成合法范围；但固定的档位、固定的分支（如“转移 / 转换”两选一）不得省略。

### 提示文本 / 按钮文本维护约定（技能表 / 文本表）

**先定位再动手 —— 文本分三层：**

| 层 | 放什么 | 取文接口 | 校验 |
| --- | --- | --- | --- |
| 技能表「提示」列 | 某一步的提示条文案（含默认步骤文案） | `提示原文` / `提示` / `提示文本` | 51 号 |
| 技能表「按钮」列 | 选项按钮上的字（`label` / `text`） | `按钮原文` / `按钮文本` | 51 号 + 52 号（禁止写死） |
| 文本表 | 没有唯一技能归属的公用句 | `GConst.文本(id)` | 51 号 |

#### 一、技能提示文本怎么维护

1. **位置**：设计表「技能表.csv」的 `提示 / 提示2 … 提示8`；按技能行填。
2. **「提示」（第 0 条）是默认步骤文案**：`询问()` 没给专门文案、或调用点传的序号是 0 时，
   客户端显示的就是它。所以给技能新增「某一步的专用文案」时，从 **「提示2」（idx1）** 起往后放、
   留空「提示」；只有确认该技能没有依赖默认文案的询问时，才从「提示」开始放。
   （异教徒 9502~9508 踩过：步骤文案填进「提示」后，发动询问的提示被顶掉了。）
3. **超过 8 条**：直接在 Excel 加 `提示9` 列，类型行写 `list(string)#distributed(提示)`，
   导表会自动并入同一个数组，不用改代码。
4. **取文接口**（角色脚本里）：
   - `提示原文(技能, 序号)` —— 按表原文取，**不加**数字前后空格；选项文案这种要精确控制空格时用；
   - `提示(技能, 序号, 张数, 收牌人id, 额外)` / `提示文本(...)` —— 会填 `{n}`/`{src}`/`{dst}`
     并按数字规则加空格，普通提示条用它。
5. **占位符**：`{src}`=发起者、`{dst}`=收牌人、`{n}`/`{n1}`=张数；一条文案要填多个值时，
   其余数字写 `{n2}`/`{n3}`…、其余文本写 `{s1}`/`{s2}`…，由调用方用 `额外` 字典传入。
6. **内部子询问号**：子步骤号（如 `技能_冰冻治疗`=11021）不占技能表行，`技能行()` 会折到母技能行，
   所以写 `提示原文(母技能, n)` 就行，文案登记在母技能行，**不要**为子步骤另开文本表条目。
7. **什么时候需要配**：有额外询问（选目标 / 选牌 / 选效果 / 是否发动）的技能大概率需要；
   没有额外询问的通常不配，客户端会退回显示技能「说明」列。

#### 二、按钮文本怎么维护

1. **位置**：设计表「技能表.csv」的 `按钮 / 按钮2 … 按钮8`（与提示列同结构，导表时合并成一个数组）。
   **按钮没有「第 0 条当默认」的语义**，序号只是地址，填第几条、取第几条都行。
2. **选项字典的两个键都要填**：`"label"`（`ask_skill` 下发成客户端按钮）
   和 `"text"`（`available_skills` 的 `arg_choices`），值都从表取，**不要写死**。
3. **取文接口**：
   - `GConst.按钮原文(技能, 序号, 额外)` —— 不加数字空格，**新代码默认用它**；
   - `GConst.按钮文本(技能, 序号, 额外)` —— 加数字空格，只有「迁移前用 `提示()` 取按钮」的地方才用；
   - 角色脚本里也可用 `按钮(...)` 包装。
4. **数字与占位符**：数字类写 `%d`/`%s` 在代码里格式化；需要命名占位符时写 `{n}`/`{n2}`/`{花费}`，
   用 `额外` 字典填。不要两种混着用同一个值。
5. **两个技能共用一条按钮**（3301/3306 阴阳转换三档、8806/8808 士气方向）：
   构造函数带一个「技能号」参数，**两行按钮列各配一份**，用哪个技能号取哪一行；
   不要放进文本表。改措辞时两行一起改。
6. **由数据拼出来的不进表**：系名（`%s系`）、卡名（`视为%s`）、数字档位这类拼接结果留在代码里。
7. **追加不插队**：新增按钮尽量往后追加；中间插入会让后面所有序号整体挪位，各调用点都要跟着改。
8. **改完导表**：`godot --headless --path . --script res://tests/tools/export_tables.gd`
   （等价编辑器 Ctrl+Shift+T），再跑自检。

#### 三、文本表怎么维护

- 只放**没有唯一技能归属**的句子：客户端通用兜底（如 `提示_选择一个选项`）、
  基础规则菜单（治疗抵挡 / 购买 / 合成 / 提炼 / 星石组合 / 基础效果牌面）。
- id 用中文：技能相关用 `提示_*`，基础规则菜单用 `通用_*`；`GConst.文本(id)` 取值。
- 能挂到某一行技能的就别进文本表。

#### 四、常见错误

| 现象 | 原因 | 正确做法 |
| --- | --- | --- |
| 发动询问的提示被步骤文案顶掉 | 把步骤文案填进了「提示」（idx0） | 从「提示2」起放 |
| 按钮文字缺空格（「摸1张牌」） | 原代码用 `提示()`（加空格）取按钮，换成 `按钮原文` 后少了空格 | 改用 `按钮文本` |
| 按钮取到空串 | 技能号 / 序号写错，或两行共用只配了一行 | 51 号用例会报；共用时两行都配 |
| 改了一句按钮，另一个角色没变 | 共用按钮各配一份，只改了一行 | 两处一起改（或改成读母技能行） |
| 新技能又写死了按钮字面量 | 没用取文接口 | 52 号用例会拦住，见下 |

#### 五、校验与工具

- **51 号用例**「提示文案 id 校验」：扫 `提示原文(技能, 序号)` / `按钮原文(技能, 序号)` / `文本("id")`，
  核对技能行 / 按钮列 / 文本表条目存在，按钮取到空串也报错。
  「提示」某一格留空是允许的（客户端回退到技能说明）。
- **52 号用例**「按钮文案禁止写死」：扫角色 / helper 与 `battle_mobile.gd`，
  发现选项字典里 `"label"`/`"text"` 后直接跟中文字面量就报错。
- **卡表「说明」列**：挂了技能（技能1/技能2 非空）的卡**不要填**——那份文字和技能表
  「说明」重复，代码也不读（`GCard.description` 目前没有任何消费方）；
  头像/提示里显示的是技能表说明。基础卡的说明也暂时没有显示入口。
- 导表可用无头工具：`godot --headless --path . --script res://tests/tools/export_tables.gd`
  （等价编辑器 Ctrl+Shift+T）。

## 修改流程

1. **定位完整改动链**
   - 数据：`Table/Design/设计表.xlsx` → `Table/Csv/*.csv` → `Table/TableScripts/DataTables.gd` → `scripts/data/*.gd`
   - 逻辑：`scripts/battle/roles/*.gd`、`scripts/battle/battle_engine.gd`
   - 界面：`scripts/ui/battle_mobile.gd`、`scripts/PlayerStatusMobile.gd`、`scripts/CardUI.gd`
   - 配置：`scripts/core/const.gd`、`scripts/core/proto_schema.gd`
   - 确认一条数据/字段从产生到显示/校验的每一层都接上。

2. **服务端权威，客户端只做体验过滤**
   - 合法牌、合法目标、选项可用性、资源扣除最终都由服务端校验。
   - 客户端过滤只负责让玩家少点错，不能替代服务端校验。
   - 需要精确区分来源时（手牌/盖牌），按实际来源分别校验，不能只数总张数。

3. **按下方规范设计技能交互**
   - 先把选项、选牌、目标、状态、提示和协议设计完整，再改实现。
   - 不要只改服务端，或只改客户端其中一层。

4. **同步协议、数据和测试**
   - 新字段要贯通 schema → 服务端下发 → 客户端读取 → UI 使用。
   - 数据表改动要同步 CSV、DataTables 和运行时代码。
   - 补对应边界测试。

5. **运行自检**
   - 按项目现有自检入口运行。
   - 区分新增失败和原有失败，不能把原有失败当成通过。

## 角色技能规范（场景 → 检查）

1. **不可选项也要下发，用 `enabled=false` 置灰，不要删除。**
   - 场景：技能有两档效果，一档缺资源、缺目标或缺手牌。
   - 检查：按钮仍在、半透明、点不动；玩家能看到技能的全部用法。

2. **每个选项独立配置需牌、需目标、白名单、盖牌数；全局字段只作基准。**
   - 场景：同一技能 A 档弃 1 张、无目标；B 档弃 2 张、要 1 名目标。
   - 检查：切换选项后，需牌数、目标数、可点目标都跟着该项变。

3. **多资源操作一次询问完成；服务端按来源精确校验，客户端只做过滤。**
   - 场景：技能代价是“1 张盖牌 + 1 张手牌 + 1 名目标”。
   - 检查：同一步选完再提交，不再多弹一次弃牌；服务端能区分哪张是盖牌、哪张是手牌。

4. **混合选牌必须区分手牌与盖牌，过滤按选项、按来源生效。**
   - 场景：手牌和盖牌都能点，但某一档要求其中几张必须来自盖牌。
   - 检查：选项切换后过滤规则跟着换；客户端挡明显非法组合，服务端仍做最终校验。

5. **无目标分支要同时清空 `need_target` 和 `target_max`。**
   - 场景：一个分支打目标，另一个分支只给自己加状态、摸牌或获得额外行动。
   - 检查：选到无目标分支后头像不再可点，直接按“确定”即可发动。

6. **本地多步选项到最后一步才提交；取消按层级回退上一层。**
   - 场景：先选效果，再选 X 点/档位，最后选牌和目标。
   - 检查：中途不发服务端请求；第二步取消回第一步，第一步取消才取消整个技能。

7. **固定目标由服务端下发，客户端自动选中并锁死。**
   - 场景：响应技能的目标就是“本次攻击目标”“攻击者”或“自己被攻击时固定的人”。
   - 检查：`targets` 随询问下发，客户端进场自动选中，头像亮起且点不动。
   - 发动技能（mode 4，如启动技能）没有询问、拿不到 `targets`，由指示器配 `自动选目标`（`询问目标` / `他人` / `全体` / `自己`）达到同样效果；
     **只作用于自己的技能**（如【裁决者】）再配 `锁定不可取消`，锁定自己后「取消」直接置灰。

8. **头像提示区分静态值/现算值、自身/目标；算不出的基准由服务端下发。**
   - 场景：提示数值取决于弃牌数、选项档位、原伤害或角色被动。
   - 检查：静态部分写配置，动态部分用 `preview_base` 等基准现算；自己身上的效果不要画到目标身上。

9. **攻击伤害、法术伤害、治疗的文案、颜色、数值口径分开。**
   - 场景：同一技能或同一角色同时有攻击加伤、法术伤害和治疗。
   - 检查：三种提示分别使用对应关键词和颜色，数值不要互相套用。
   - 头像提示 / 伤害预览的固定写法（**不写「点」**）：`%d 攻击伤害`、`%d 法术伤害`、`+%d 治疗`
	 —— 如「2 法术伤害」「+1 治疗」。写成「2 点法术伤害」是踩过的错
	 （`技能指示器` 表里所有条目都是这个口径，新增文案照抄即可）。
   - 全部现有写法（伤害 / 治疗 / 牌 / 资源 / 多行 / 特殊模式）见下方「头像指示器文案表」。

10. **一次性状态要明确置位与清除时机；跳过常规询问的分支要随最终命令传递来源。**
	- 场景：一次性无法应战、额外行动、临时加伤、本回合限定效果。
	- 检查：在正确钩子置位/清除；`direct` 等跳过前置询问的分支，来源 `cause` 要随最终命令下发。

11. **涉及的协议字段、数据、客户端读取和边界测试要同步更新。**
12. **「弃牌」必须走统一弃牌入口 `engine.to_discard(cards, ctx)`，ctx 里写清 `owner`（真正弃牌的人）
	和 `source: "hand"`。** 不要 `take_from_hand` 之后直接记日志 / 塞进别的区域：
	F6「弃牌前拦截」（噬神者【渗蚀】、暴食少女【三秒原则】等）只在 `to_discard` 里分发，
	绕过它会让这些被动完全不触发；`owner` 写错则伤害/代价会落到错误的人身上。
	牌若随后还要交给别人 / 放进【预言】堆，按「先弃置、再从弃牌堆取回」处理。
	自查：角色脚本里 `_log_discard(` 附近没有 `to_discard(`、或 `take_from_hand(` 的玩家
	与 `to_discard` 的 `owner` 不是同一个人，都是漏 triggers 的信号。
13. **「移除」的牌进引擎的 `移除牌堆`；不在移除牌堆里才算「在场」。**
	- 要拿一张牌的实例做选项 / 结算前，先用 `engine.牌在场(inst)` 过一遍：被移除的牌
	  不能出现在后续选项里、也不参与分配（如审判把队友弃牌列成选项时）。
	- 从 `移除牌堆` 里取用（噬神者【御刃】【共振】【侵刻】等）必须先调
	  `engine.从移除牌堆取出(inst)`（刃专用别名 `刃从移除牌堆取出`），取出来再加回手牌 /
	  交给别人；**不要**直接 `add_hand_cards`，否则它在移除牌堆里仍算「不在场」。
	- 牌被移除后不进弃牌堆 / 牌库，弃牌堆洗回牌库等逻辑碰不到它。
	- 场景：新增选项参数、选牌来源、额外行动来源、标记字段。
	- 检查：schema 有字段 → 服务端下发 → 客户端读取 → UI 真正使用 → 测试覆盖置灰、取消回退、不提前提交、固定目标等边界。

12. **`v_*` 校验钩子只做校验：不扣资源、不置结算标记。**
	- 场景：在 `v_attack` 里顺手扣能量、记「本回合已用 / 已发动」。
	- 检查：引擎在「响应里点红色额外攻击按钮」时也会先用 `v_attack` 做一次预校验（`BattleEngine._选择额外攻击响应`）；校验里改了资源或回合标记，这份行动就会当场失效 —— 点了剑影却进了疾风技、剑影留在队列里，之后弹出一张置灰只能取消的询问。
	- 正确位置：扣费在 `resolve_action_end_option` / `p_additional_action`，回合限定与形态标记在 `p_*` 钩子（如 `p_action_end`）里置位。

13. **`p_*_skill` / `resolve_action_end_option` 压入引擎状态后必须返回 `URGENT`。**
	- 场景：技能本体或聚合器的选项结算里用 `engine.push_draw` / `push_harm` / `push(SAttackCard…)` / `push(SHook…)` 压入摸牌、伤害、攻击、钩子等状态。
	- 检查：返回 `SUCCESS` 时聚合器会继续问剩余的响应选项，玩家先看到「是否发动迅捷赐福」，伤害 / 攻击还没结算（猎巫人【偷袭】选完追加目标、魔弓【多重射击】都踩过）；技能本体里返回 `SUCCESS` 则 `SkillRun` 会继续把「行动结束响应」压在这些状态上面（女武神【秩序之印】：响应完才摸 2 张）。
	- 正确写法：压了状态就返回 `URGENT`；聚合器的角色选项是 `terminal=false`，会记成「待决」，`SUSPEND` 先跑完压入的状态，再回来重入一次（重入时把本轮步骤标记为已完成，例如把参数清零 / `STEP_DONE`，避免重复结算）。
	- **普通时机钩子返回 `URGENT` 同样会回栈重跑同一个钩子**（`SHook` 不推进本轮迭代）。一次性效果必须用唯一序号 / 步骤标记去重：如 `p_cover_change` 的 `ctx.seq`，处理过的 seq 直接 `SUCCESS`；否则「盖牌渗蚀：伤害 → 移除 → 回栈再伤害」会无限循环（猎巫人【法术剥离】把【异刃】放进盖牌区时踩过）。
	- **`engine.add_cover` / `remove_cover` 也会压入 `p_cover_change` 钩子**：引擎在 `SHook` 中检测到未处理的盖牌变动，会自动让出一次执行权，先跑 `p_cover_change` 再继续当前钩子；**不需要每个放盖牌的技能自己 `return URGENT`**。统一入口是引擎的 `_盖牌变动待处理`，所有 `add_cover` 调用点自动生效（猎巫人【法术剥离】/【狩魔刺】踩过等整轮钩子跑完才结算的延迟）。
	- 只 `add_action` / 改标记、没压状态的（剑影、剑残影、技之剑意、神圣追击、不屈意志、戒骄戒躁）返回 `SUCCESS` 即可 —— 那些行动由响应结束后的额外行动阶段进入。

14. **行动聚合器里的选项要自带目标 / 牌需求；提交不成立要驳回重问。**
	- 场景：一次攻击 / 法术结束后，聚合器把好几颗技能塞进**同一条**询问，`respond_id` 只是列表第一项（如剑之子 10804 剑残影 + 4504 剑影*断念）。
	- 检查：每个选项都写全 `need_target` / `need_card` / `targets`（如剑残影只给 `enemy_ids()`）。客户端按选中项自己的 `skill_id` 取指示器 / 头像提示，按该项自己的 `targets` 收窄可点头像 —— 少写 `targets`，自己 / 队友头像也会亮，点了必被服务端拒。
	- 检查：玩家提交的目标 / 弃牌不成立时回 `ErrorInput`，并清掉「本次已用」标记让聚合器重新问；不要静默 `STEP_DONE` —— 那样选项会直接消失、技能也没发动（剑之子 10804 / 4504 踩过）。
	- **「攻击行动结束时」的选项要按 `ctx.kind` 过滤**：聚合器在攻击 / 法术行动结束时都会调 `action_end_options()`，直接返回选项会让法术结束也冒出红色按钮（风之剑圣【剑影】踩过，猎巫人【偷袭】、魔弓【多重射击】、剑之魔女 / 剑之子的 4504 也是同一处）。用 `BattleRole.是攻击行动结束(ctx)` 挡一下；原文写「攻击或法术行动结束时」的才不加（忌妒少女【嫉妒追放】、星坠女巫【星刻】）。

15. **技能摸牌一律走「摸牌状态」，不要同步发牌。**
	- 场景：技能让玩家摸牌（如剑圣【圣剑】104 的「摸 X 张牌」、7804 的「手牌补到 4 张」）。
	- **普通摸牌**：`engine.push_draw(pid, n, cause)`，然后 `return URGENT`。它会压入「摸牌前」响应（【水影】等）+ 摸牌状态，摸完由状态边界统一结算手牌超限 / 盖牌超限 / 手牌变化等。
	- **【强制】摸牌**（不走 `p_before_draw`）：`engine.push_强制摸牌(pid, n, cause)`，然后 `return URGENT`。同样是「状态」版，摸完回状态边界结算。
	  - 摸完还要用那几张牌（如 7802 亮出摸到的牌）：传 `after_hook` / `after_ctx`，回调钩子的 `ctx["cards"]` 就是本次摸到的牌。
	  - **角色脚本里禁止直接调同步版 `engine.强制摸牌()`**：它只给 `S强制摸牌` 状态内部用。同步发牌 + 紧接着 `return WAIT` 会整段跳过边界检查（引擎在 `WAIT` 时不做 `_check_hand_overflow`，避免在等待者之上补压状态、回复被错取）。
	- **不要再手动补压** `engine.push(BattleEngine.SHandOverflow.new())`：`push_draw` / `push_强制摸牌` 结束时边界本来就会结算超限。旧的「同步强制摸牌 + 手压超限」写法已全部淘汰（10601 / 7802 / 封印师 407 踩过）。
	- **手牌补 / 弃到 N 张**：用 `engine.调整手牌到(pid, N, cause, 随机弃牌)`（不足走 `push_draw`、超出压 `SHandAdjust` 让牌主自己选弃）；返回 `true` 表示压了需要挂起的流程，调用方必须 `return URGENT`。参考圣弓【圣煌辉光炮】的写法。
	- **从牌库顶取牌放进盖牌区**：`engine.draw_cover(...)`（不是手牌，盖牌超限由边界结算）。
	- **改手牌上限**（`player.hand_cards_max = ...`）：改完直接走完当前分支返回即可，边界会重新判超限；不要改完上限紧接着 `return WAIT`。
	- 技能本体（`p_*_skill`）返回 `URGENT` 后引擎默认按「技能已执行完」收尾，**不会**重入本体。这类「摸完还要接着选目标 / 结算」的技能要覆写 `技能URGENT后重入(action)`：按 `action_id` 精确放行，并且只在「确实需要回来继续」的那一步返回 true（如 10601 只在 `_bie_fan_step == 2` 为真，否则惩罚的 `URGENT` 会把整个技能从 `STEP_DONE` 重置再发动一遍）。返回 `URGENT` 前把当前步骤推进到下一步，否则重入会重复执行刚做过的事。
	- 参考实现：弓女 / EX魔弓【狙击】（`push_draw` + `URGENT`）、审判 9502 / 10601 / 7802 / 7805 / 7804（状态版强制摸牌 / `调整手牌到`）。

16. **强制弃牌：目标超时 / 空回复要按手牌顺序补满，不能静默跳过。**
	- 判定：原文写「目标弃 N 张牌」「各弃 N 张牌」「他弃 1 张牌」且没有「可」「否则」的，就是强制；写了「可弃…，否则…」的是二选一，超时按「不弃」结算（罚则照走）。
	- 写法：空回复时从目标 `hand_cards` 按顺序补一张（`_pick_cards` / `_回复里的一张牌` / `_request_discard(..., 必须弃=true)` 都已内建），不要只写 `if 有牌: 处理` 就完事 —— 目标掉线 / 超时会白少一张牌，后续数值（展示张数、瓶子数、陷阱数）全跟着错。
	- 踩过：猎巫人【狩魔刺】/【法术剥离】、兽灵【兽魂警戒】/【兽返】、矜贵之女【友情羁绊】；剑之子【剑残影】、剑之魔女【臆想剑】、精灵射手【动物伙伴】、圣弓/时刃/天使的请弃牌一直是对的，按它们的写法来。
	- 让**别人**弃牌时用标准弃牌应答（`engine.ask_respond(pid, GConst.RespondType.Discard, [pid, cause, 张数], [pid])`
	  ＋ `engine.wait_for(pid, GConst.Msg.Respond)`），客户端提示条会自动写成「【X】：请选择 N 张牌弃掉」；
	  不要用 `询问(pid, 技能号, ...)` 把发动者的「选择 2 名我方角色各弃 1 张牌」丢给被弃牌的人
	  （矜贵之女【友情羁绊】踩过）。弃牌后还有附带效果时，在技能指示器里配 `"弃牌提示后缀"`
	  （如 7805 的「，魔法入门效果结束摸 1 张牌」），提示条会接在默认句后面。

17. **卡牌身份用实例号，规则比较用牌面（`GConst.牌号`）。**
	- 场景：技能从 `action["card_ids"]` / `hand_ids_where()` / `hand_cards` 拿到牌 id，拿去比牌名、系别、白名单或塞进另一个区域。
	- 现状：服务端手牌 / 盖牌 / 牌堆 / 弃牌堆 / 基础效果区存的都是**实例号**（`序号×10000+牌号`，正常牌实例号==牌号，
	  测试指令会克隆同牌面）；上行提交带的是实例号，下行白名单与 `Card` 消息是牌面。
	- 检查：比牌面用 `Data.get_card(id)` 或 `GConst.牌号(id)`，不要拿实例号直接和牌号常量比；
		把牌**移进另一个区域**（交给别人 / 放进盖牌区 / 挂成基础效果）必须用
		`player.取出一张手牌(id)` / `player.取出实例(列, id)` / `deck.取出实例(id)` 拿到实际实例号再放，
		不要「删一张、再 `add_hand_cards(牌号)`」——那样会凭空补一张同牌面的新牌，和场上原件撞号。
	- 检查：`available_skills()` 的 `cards` 可以填实例号（引擎下发前会 `_牌面表()` 折面）；
		基础效果牌要按 `GPlayer.BasicStatus.实例号` 认人，别只用 `card.id`。
	- **`0` 是合法牌、`-1` 才是「没有牌」**：判有效性、批量筛牌、选项 `card_id`、客户端手牌节点
		的完整口径见第 21 条，改牌相关代码前先看那一节。
	- 详见 [AGENTS.md](../AGENTS.md) 第 8.6 节与 [战斗系统架构](战斗系统架构.md) 第 2.7 节。

18. **「这一手没有目标、但要指出某名角色」用 `highlight_ids`，不要塞进 `targets` / `dst_ids`。**
	- 场景：技能的效果落在不受玩家选择的角色身上（由队友代选目标、某名队友会加治疗…），
	  但玩家需要**看见**是哪名角色（如怠惰少女【别烦我……】10601：发动时指出替她发动的右手边队友，
	  目标被问「弃 1 张法术牌」时指出「不弃就 +1 治疗」的那名队友）。
	- 写法：角色侧 `available_skills()` 写 `"highlight": [pid...]`（→ 引擎下发 `highlight_ids`），
	  或询问时给 `询问(..., 高亮目标=[pid...])` / `engine.ask_skill(..., 高亮目标=[...])`；
	  客户端只把它并进 `_高亮目标`（黄框 + 头像提示），**不参与选择、不随行动提交**。
	- 检查：不要把这类角色写进 `targets` —— 那表示「可点选的目标白名单」，`need_target = 0` 时虽点不动，
	  但会被当成「本手唯一合法目标」自动选中并随行动提交，语义上是错的；
	  也不要让客户端按座位自己算（服务端叫谁发动、界面就亮谁，见 10601 修高亮偶发不亮的经过）。
	- 头像提示文案仍照「头像指示器文案表」的口径；`highlight_ids` 只决定**画在谁头上**。

19. **改形态（`player.tap` / `engine.set_tap`）不要放在「同一流程里还要问玩家」的询问之前。**
	- 场景：技能发动时先横置进入形态，紧接着再问玩家「弃不弃牌 / 选谁」（女武神【英灵召唤】2505 就是先横置、再问第二问）。
	- 原因：`tap` 的 setter 会压入一轮 `p_tap` 钩子，那一轮跑在本状态**之上**；里面别的角色一旦开询问
	  （兽灵【兽魂警戒】3604 就会），`wait_for` 会清掉本次询问还没处理的回复 —— 玩家选了牌也当没选。
	  表现为「弃了法术牌、也点了目标，结果既没弃牌也没加治疗」。
	- 正确写法：把改形态放到这次询问的回复取走之后（本次询问已结算完）再改；要「先记下、稍后落形态」时
	  用角色自己的成员变量（如 2505 的 `_英灵_待横置`），并在行动结束 / 钩子收尾时清回默认值。
	- 只改形态、后面不开询问的技能（`p_*_skill` 里横置完直接 `return URGENT`）不受影响。
	- **引擎已兜底**：`wait_for` 会把「已收到、还没取走」的回复按归属状态暂存到 `_挂起回复`，
	  那个状态回到栈顶时自动恢复（见 [战斗系统架构](战斗系统架构.md) §4.5）。所以这类先后顺序不再是硬性要求，
	  但仍建议按上面的写法来：少一层「回复要靠引擎抢救」的心智负担。

20. **钩子顶部的资源门槛只在「还没发动」时判，不能在已付过代价的后续步骤上再判一次。**
	- 场景：技能分两问 —— 第 1 问问「是否发动」，发动时先扣费（能量 / 治疗 / 指示物 / 手牌），第 2 问再选牌选目标。
	- 踩过：女武神【英灵召唤】2505 顶部原来写 `if player.get_energy() == 0: return SUCCESS`。玩家只有 1 能量时
	  付完正好 0，第二问的回复回来、钩子重新进入时被这条门槛直接跳出：`take_reply()` 没被调用，
	  牌不弃、治疗也不加，界面上那一问却已经被收掉了。测试里给了 2 能量，所以一直没暴露。
	- 写法：把门槛收进第 0 步（`if _阶段 == 0 and 能量 == 0: return SUCCESS`），或者用「已在流程中」的标记绕过它；
	  后续步骤只按自己的阶段标记推进（如 2505 的 `_英灵_阶段`）。
	- **引擎会点名**：状态出栈时如果还挂着没取走的回复，`run()` 会清掉它并在调试期打印
	  `[引擎] … 结束时还挂着一份没取走的回复`。调试时看到这条，先查这一条。
	- 反过来，`has_reply()` 现在会把暂存的回复先恢复再判断，所以「先判断有没有回复、没有才发问」的写法
	  （如 `if not engine.has_reply(): 询问…; return WAIT`）在插队之后也仍然正确。

21. **`0` 是合法值，`-1` 才是「没有」—— 牌 / 座位的哨兵约定（踩过多次）。**
	- **为什么**：牌库原牌的实例号 == 牌号，**卡表#0 就是【圣盾】，牌号 / 实例号都是 0**；
	  玩家座位也从 0 开始（`GConst.GUEST = 9`）。0 是合法值，「没有 / 取不到 / 不适用」
	  一律用 `-1`。把 0 当空值不会报错，只会静默漏牌，极难查。
	- **判断**：取牌类 API 的返回值（`取出实例` / `取出一张手牌` / `牌在场` / `从移除牌堆取出` /
	  `_认一张` 等）、批量筛牌、选项与白名单过滤、客户端节点遍历，一律 `>= 0` 有效、`< 0` 失败；
	  **禁止 `> 0` / `<= 0`**，也禁止 `if cid:` 这类真值判断。
	- **哨兵字段**：凡「没有值」的牌 / 目标字段，默认 `-1`、重置写 `-1`、判断 `>= 0` ——
	  如选项 `card_id`、`as_card_id`（不视为别的牌）、额外行动的卡与目标、攻击锁、
	  客户端 `CardUI.实例号`（默认 -1＝没填，退回按牌号）。`basic_effects.card` 可以是 0，不能当空。
	- **协议**：可能带 `-1` 的牌 / 目标数组与单值字段用 `i32`，不能用 `u32`（u32 会把 -1
	  编成 4294967295）；现状：`Command.card_ids` / `dst_ids` / `option_card_ids`、
	  `OptionTargets.ids`、`ArgChoice.cards`、`Card.as_card_id`、`SinglePlayerInfo.attack_lock`。
	  编码层不会因为值是 0 就省略（没有「默认值省略」）；上行数组只放 ≥ 0。
	- **换算**：`GConst.牌号()` 对负数原样返回，`-1` 折面后仍是 -1，不会和 0 号牌混淆。
	- **玩家座位同理**：座位号也从 0 开始，`-1` 才是「没有」。凡是临时存「待处理的座位号」
	  （如审判 `_审判待摸` 存队友座位）也必须 `>= 0` 判断 —— 踩过：`_审判待摸 > 0`
	  把 0 号座位的摸牌吞掉，表现为「0 号弃完牌不摸牌」。
	- **自查**：搜 `取出实例(` / `取出一张手牌(` / `牌在场(` / `card_id", 0)` / `实例号 <= 0`
	  / 座位号字段 附近的 `> 0` / `<= 0`；「刚取完牌就判 `> 0`」直接当 bug。
	- **已踩过的同类点（改到这些地方先看一眼）**：审判 `_审判待摸`（座位）、`_展示对手`（座位）；
	  结界师 `_琉璃待放`（牌）、`_琉璃弃牌人`（座位）；引擎「额外攻击响应」的
	  `攻击牌` / `攻击目标`（0 号牌 / 0 号座位）；客户端「别烦我」兜底提示的 `队友` / `队友2`。

22. **一次能提交的，就不要拆成多次确认（多余步骤算 bug，不是“体验问题”）。**
	- 技能的「选档位 / 选牌 / 选目标」只要是同一时刻决定的，就挂在**同一条**行动 / 回复里：
	  选项带 `need_target` / `need_card` / `target_max` / `card_max`（`available_skills` 的
	  `arg_choices` 和 `ask_skill` 的 options 都认这些键），客户端选完一次「确定」提交，
	  服务端一次校验、一次结算。
	- 禁止的写法：先单独问一次「选 X」→ 再一名一名问目标 → 最后再问弃牌。
	- **极端案例（新技能按这个反推自查）**：【神圣鞭策】= 选档位（X 决定要选几名目标）
	  + 同一次选 X 名目标 + 同一次选要弃的 X 张牌，**一次提交**；并且**手牌为 0 也必须能发动**
	  （弃牌数 = `min(X, 手牌数)`，为 0 时选项的 `need_card` 就是 0，不要求选牌）。
	  踩过：2026-11 先做成「选 X → 逐名问目标 → 再问弃牌」被要求重做。
	- 拆成多次的唯一正当理由：前一步的结果会**改变后一步的规则本身**（如先看牌库顶再决定改不改），
	  且要写清为什么不能一次问完。

23. **「目标数随 X」的技能：目标数 = min(名额, 合法目标数)，有可选目标必须选满；代价可以溢出。**
	- 名额由 X 推出来时（`X 名` / `X-1 名` / `最多 X 名`），不能因为「场上合法角色不够」就禁止发动或缩小 X：
	  超出的名额就是**溢出**，代价照付、不补目标。
	- 有可选目标时**不能少选、更不能不选**：客户端把 `need_target` / `target_max` 收紧到
	  `min(名额, 合法目标数)`（`target_max_from_cards` + `need_target=0` 的走 `_随牌目标需求()`），
	  服务端 `v_*` 用同一口径复核（数量对不上直接 `ErrorInput`，不要静默少结算）。
	- 现有实现（改过 / 对齐过的）：星环 4002、圣洁法典 1703、圣光爆裂 3704 / 8804、神圣鞭策 3907、
	  偷袭 4205、魔法入门 7802；固定名额的多目标技能用 `min(名额, 候选)`（如怒潮荒涛 4605）。
	- 角色 86 / 94 / 109 等**没有脚本**的禁用角色（神秘伏笔 8603、Surprise! 8606、秘境万象 9406、
	  天平 10905）实现时必须按本条做，不能沿用「要求正好 X 名 / 允许随便少选」的旧写法。

### 弃牌拦截里再弃牌

技能在「弃牌前拦截」（`p_before_discard` 及其引发的伤害链）过程中还要弃牌时
（典型：噬神者【共振】弃刃作代价），必须调 `engine.to_discard(牌, ctx, true)`
——第三个参数 `允许嵌套=true` 才会照常走 F6 拦截。默认的 `false` 是为了避免拦截钩子
递归，会把牌直接塞进弃牌堆：刃不触发【渗蚀】、也不进移除牌堆，后续「从移除堆取回」的
技能就取不到。

## 公开亮牌：只走引擎的三个入口

「牌面给别人看到」这件事统一由 `battle_engine.gd` 提供，**角色脚本不要再手写
`broadcast(GConst.Msg.Card, {type: GConst.CardMsgType.Show ...})`**：

| 入口 | 什么时候用 | 客户端 | 服务端 |
| --- | --- | --- | --- |
| `engine.展示牌(pid, cards, 持久=false)` | 牌**不是从他手里**拿出来的：牌库顶 / 盖牌区 / 弃牌堆 / 场上 | 摊牌 | 不压钩子 |
| `engine.展示手牌(pid, cards)` | 牌**是从他手里**公开亮出来的：打出 / 展示 / 公开弃牌 | 摊牌 | 压 `p_show_hand`（封印师五系封印的触发点） |
| `engine.私下看牌(pid, cards)` | 查看类技能，只给本人看 | 只发给他 | 不发全场、不压钩子 |

亮完还要顺手移动，用封装（顺序固定：亮 → 离手 → 进区域）：

- `engine.展示手牌并弃(pid, cards, ctx)` —— 手牌 → 弃牌堆（已亮过，不再播弃牌特效，只写文字日志）；
- `engine.展示手牌进盖牌(pid, cards, cause)` —— 手牌 → 面朝上盖牌区（【言灵】/【遗迹】这类）。

规则口径（封印类原文是「直到他**从手中打出或展示出**某系牌时」）：

- 触发归属看「这张牌是谁的手牌」——谁的手牌被亮出来，就触发谁身上的封印；
- 别人的弃牌、盖牌区的牌、牌库顶的牌、只给本人看的查看，都**不算**「从手中展示出」，
  走 `展示牌` / `私下看牌`，不要压钩子（压了会误触发封印）。

时机：钩子是压栈，谁先压谁后跑。希望展示响应排在后面的结算之前，就把 `展示手牌`
放在那几处 `push` 之后再调（例：先 `push_强制摸牌`、再 `展示手牌`＝先结算封印、再摸牌）。

客户端的展示区**按批叠加**：一条 Show 是一批，新的一批不会清掉旧的。
同一批内部挨着叠一点摆，**批与批之间空开 10px**（一眼能分出这是几次不同的丢弃 / 展示）。
每批牌停留 **9 秒**（`展示停留秒数`），最后 **3 秒**（`展示淡出秒数`）里逐渐变透明到 0：
· 变透明**不腾位置**：那张牌继续占着格子（空白占位），新牌照样从右边进来、把老的往左挤；
· 空白占位被挤出展示区左边界（x = 0）才移除；
· 整排放得下时居中，放不下就靠右；老的牌让位是**滑过去**的（`展示挪位时长` tween），不是瞬间跳；
· 全部牌都成了空白占位时整片清掉，下一批新牌重新从中间开始摆。
透明度由 `_更新展示透明度` 每帧现算（进场淡入 × 停留时间 × 左边淡出带 `展示淡出宽度`），不用 tween。
另外 `Pick`（选走展示牌）会把整片清空。想让几张牌明显是一组（并排、一起进场），
仍然合成一条消息最省事（`engine.展示牌(pid, [牌1, 牌2])`）。

巡检：`powershell -ExecutionPolicy Bypass -File tests\查展示钩子.ps1`
（列出还在手写广播的位置；「未带钩子」的按上面的牌源口径逐个确认）。

## 盖牌当手牌用（【祝福】/【言灵】这类）

某张盖牌此刻能不能点，要**两件事同时成立**，缺一不可：

1. 这一步确实放行它当手牌 —— `BattleRole.盖牌可当手牌()`（随快照 `cover_as_hand` 下发，
   如精灵射手【精灵祝福形态】横置时），或技能自己声明了从盖牌区选牌（`card_source = Cover` + 白名单）；
2. **这张牌本身这会儿能不能打出去** —— 和普通出牌同一套判定（`_可主动使用牌`：攻击 / 法术是否放行、
   行动阶段禁法术、【圣光】不能主动打出、圣盾 / 虚弱 / 中毒 / 魔弹有没有合法目标……）。

典型反例：场上所有人都已有【圣盾】时，手牌里的【圣盾】本来会置灰（没有合法目标），
那么**盖牌区里的【圣盾】也必须一起置灰**，不能因为它是「盖牌」就漏判。

技能指示器里配 `{"当作卡牌": true}` 表示「这一手选出来的牌是要真打出去的」（神秘学者【真言术】），
客户端对这类技能会按上面第 2 条判可点性；以后新增「选中某张牌才显示 / 才成立」的界面逻辑，
一律用 `_当作出牌()`（普通行动阶段 **或** 当作卡牌的发动技能）判断，不要只写 `_mode == 1`。

## 兜底与报错

- **不要写“假兜底”。** 正常流程有前置保证、规则上不可能出现的分支，不要为了“看起来稳”加默认值、随机选择、自动补牌、静默改目标之类的死代码——只会提高维护成本，还会把真 bug 掩盖掉。
- **取值范围由自己保证的，就别写兜底。** 选项值、档位、常量、枚举是自己下发 / 自己算出来的，
  在自己手里就是确定的（如【神圣鞭策】选 X 只下发 1..N），不要再写 `x <= 0`、`x > N`、负数之类的判断。
  判据只有一句：**先问“这个值有没有可能真的出现”**——不会出现就不写。
  只有这些地方才需要兜底并报错收尾：外部输入（客户端上行、协议字段、旧存档）、
  跨状态残留（`-1` 哨兵）、异步重入（ctx 标记）这类真正可能异常的情况。
  反例：神圣鞭策曾在选 X 后写 `if x <= 0 ... return`，被明确要求删掉（2026-11）。
- 确实提前意识到可能出错（数据缺失、旧存档、外部输入绕过前置校验）时：**在战斗日志输出一条 `[报错]`，然后按“什么都不做 / 结束当前步骤”处理**，不要替玩家改选。
- 服务端统一用 `engine.报错("说明", 可选玩家id)`（`GConst.GossipType.Error`，客户端日志标签 `[报错]`、红色）。正常对局不应出现；出现就说明代码或数据有 bug，应该修而不是兜。
- **代码要简洁，死路径不要写。** 除了上面说的无用兜底，这些也算死路径，一律不留：
  - 永远是 true / false 的条件，和只有它才进得去的分支；
  - 建了却没人用的变量、常量、步骤标记、参数（如 _鞭策下标 这种「写了就没读过」的）；
  - 复制粘贴带过来、与当前技能无关的字段（如本体不需要却挂了 `targets`）；
  - 为一个调用点预留、实际只有一个取值的开关；
  - 注释掉的旧实现、留着「以后可能用」的备用分支。
  - **自查方式**：写完一段回头删一遍——删掉之后行为不变的就是死路径，删。
- 例：【末日预言】翻面只认【放逐】时写在场卡的 `front`；没有 `front` 就报 `[报错]` 并停下，不询问二选一、不随机翻面。

## 询问文案约定（ask 文本）

> 客户端提示条对**技能询问的默认文案**是技能表里该技能的「说明」
> （`battle_mobile` 在 `_pending_is_skill` 时走 `_技能效果提示(_skill_ask_id)`）；
> 询问标题本身已经显示技能名 / 询问号。所以**只有默认说明不够用时才自己写 ask 文本**。

1. **发动 / 可选发动询问（是 / 否）不要写 ask 文本**：传空串，让提示条显示技能表说明。
   不要写「是否发动【X】：…」——技能名标题上已经有了，效果也已经在技能说明里，
   再抄一遍只会把提示条撑长。
   - 反例：`"是否发动【审判】：我方所有角色各弃 1 张牌【展示】、各摸 1 张牌，然后把其中 1 张弃牌交给目标对手？"`
   - 正例：`询问(player.id, SHEN_PAN, 0, 0, Hand, [], 0, "", [], true, …, "")`

2. **技能表「提示」列的首条提示（提示1）统一写 `【技能名】：…`**，不再写「发动【技能名】：」。
   技能名以技能表「技能名」列为准；即使提示条标题已经显示技能名，这一句也保留。
   2026-11 已把 135 条首条提示全部统一。
   - 正例：`【圣光祈愈】：【宝石】，你+2【治疗】，无视上限、最高到5，并额外+1攻击行动`
   - 正例：`【治疗术】：点头像选择1名角色+2【治疗】，选好后点「确定」`
   - 反例：`发动【圣光祈愈】：…`、`【宝石】，你+2【治疗】…`（缺技能名前缀）

3. **后续步骤提示（提示2~8）写这一步的短句，禁止写「发动【」**。需要点明技能名时同样用
   `【技能名】：` 开头；不需要点名的步骤（如「请选择 1 张手牌弃掉」）保持短句即可。
   2026-11 已清掉提示2~8 里残留的「发动【」。
   - 反例：`发动【元素射击】：请选择 1 张法术牌`
   - 正例：`请选择 1 张手牌弃掉`、`【元素射击】：请选择 1 张法术牌`

4. **选择类询问（选系别 / 选牌 / 选目标 / 选档位）写一句短的动态补充**，只写这一步需要的
   数量、对象或代价。不复述技能说明，也不要把选项的文字 / 序号再写进文案 —— 选项按钮自己会显示。
   - 正例：`"弃最多 %d 张%s系牌【展示】"`、`"指定 1 名目标对手（他弃牌后你造成 %d 点法术伤害）"`
   - 反例：选项已经写着「天雷劫火 / 地裂波涛」时，文案里再写 `（1=天雷劫火 / 2=地裂波涛）`

5. **选中选项后替换提示条的本步文案，以 `【技能名】：` 开头**（如【三秒原则】、
   【圣光爆裂】、天雷/地裂的系别效果）。这与第 2 条的提示列格式一致；
   第 1 条的「是否发动」询问仍然不写技能名。

6. 点名对象按术语表口径（目标角色 / 该角色 / 目标对手），不要另造称呼。
7. 文案不写「点」、数字用阿拉伯数字（与头像指示器同一口径，见下一节）。
8. **代码里拼的提示也按同一格式**：`battle_mobile` 的 `_指令提示` / `询问文案` 用
   `"【%s】：…"`，不要用 `"发动【%s】"`；2026-11 已统一。
9. **选项级开关要走到客户端并保留下来**：服务端 options 里的键（`skill_id` / `card_id` /
   `no_prompt_change` / `need_card` / `说明` …）会经过三层——引擎组装命令、协议编解码、
   客户端 `_进入二级技能栏` 归一化成 `_二级选项`。加新开关时三处都要过一遍：
   - 协议字段必须登记进 `proto_schema.gd` 的 `Command`，否则真实联机直接丢；
   - 客户端归一化 `_归一化二级选项()` 已改成「白名单字段 + 其余键原样拷贝」，
     但新增的**读法**仍要在这里（或更早的 `_进入技能询问`）接上。
   - 症状特征：服务端测试/日志里能看到字段，客户端表现却完全没变 —— 优先查这两处。
10. **提示文案禁止用（）补充说明**：括号只允许出现在技能「说明」列里表示条件的约束范围
   （如「（若该伤害仅为 1 点）」）；提示条 / ask 文本 / 指令提示等**一般提示一律不用括号**
   包裹补充信息，要补就接在句子里，用「，」「；」或句号。
   - 反例：`【影月】：请（需选目标）（本次必须执行，不能取消）`、
     `攻击请点敌方头像出手（选好攻击牌后直接点要打的人）`
   - 正例：`【影月】：请选 1 名目标，本次必须执行，不能取消`、
     `攻击请点敌方头像出手，选好攻击牌后直接点要打的人`
   - 2026-11 已按这条清理技能表「提示」列里带括号的文案；新增 / 修改时照此写，
     不要为了统一去改技能「说明」列里作为条件范围的括号。

## 多步询问（分段询问）

> 2026-11-10 起：一个技能要分几次问玩家，统一走 `BattleRole.多步询问`。
> 设计/现状/迁移进度见 [多步询问统一框架-设计与迁移](多步询问统一框架-设计与迁移.md)。

1. **写法**：`多步询问(链号, 段表, 结算回调, 收尾回调 = 省略)`，链号一般用技能号；每段一次询问，
   `p_*` 重入时再调一次即可，段进度由框架保存 —— **不要再在角色里手写 `_xxx阶段` 状态机**。
   一个函数里跑多件互不相干的技能时（分发器），**每件技能一条链**（链号＝技能号），不要合成一条。
2. **副作用放在结算里**：段内只收集答案，扣费 / 弃牌 / 摸牌 / 落形态都在结算回调里做。
   这样「返回上一段」天然不用撤账；跨段依赖（第二段的选项要看第一段拿了什么）用段字段 `答完`
   在这一段答完时先做，段号已推进，重入会从下一段继续。
3. **回退、条件、循环**：`{"可返回": true}`（客户端摆「返回」，点它＝空应答＝退回上一段）；
   `{"跳过": Callable}`（条件段）；`{"重复": Callable(回, 答案)}`（循环段：对每个目标各问一次；
   答完压了状态时框架会延后到重入后再判）。
4. **超时与取消**：超时优先 `{"超时": Callable}`，其次 `{"超时默认": 值}`（当作已经这样答了，照常走 `答完` / `重复` / 结算，不跑段级校验）；
   可取消的段两者都没有＝按「不发动」取消整条链；**不可取消的段（`可取消=false`）空应答（含超时）＝按「没选」继续走 `答完` / 结算**，
   强制弃牌 / 强制取牌由角色自己的兜底补完，不能静默不发生；段里配了 `校验` 的仍会先驳回重问。
   **超时与手动取消都会走 `{"取消": Callable}`**，所以「不这么做也要结算」的技能（醋意休心）用它表达。
   想让「取消」只少做一部分（异教徒展示的贪婪），在取消回调里改标记后重开一条跳过该段的链。
5. **段内校验**：`{"校验": Callable(回), "校验失败回退": bool}`；不合法回一条 `Gossip` 报错日志 + 给被问的人一条
   `ErrorInput`（客户端「操作无效」并恢复待选），然后重问本段（或退回上一段），重问沿用本链的截止时刻。
   要自定义文案用 `{"校验失败文案": "..."}`。
6. **问别人 / 换技能号 / 标准应答**：`{"问谁": pid 或 Callable}`、`{"技能号": id 或 Callable}`、
   `{"响应": {"type": RespondType.Discard, "args": [...]}}`（让别人按标准应答弃牌，而不是技能询问）。
7. **压了状态要收尾**：结算（或答完）里 `push_*` 后返回 `URGENT` 时，框架重入会先跑**收尾回调**；
   收尾可以再压状态并返回 URGENT，会一直被重入到返回 SUCCESS。没有收尾的技能仍要自己挡重入（如 `step = STEP_DONE`）。
8. **超时兜底要看 `timeout`**：答案项带 `{"timeout": bool}`，段里按「伤害补敌人 / 治疗补友方」这类规则代打时要判断它
   （矜贵之女【魔法入门】是例子）。
9. **加字段要登记协议**：往询问命令里加任何新键（如 `allow_back`）必须同时登记
   `scripts/core/proto_schema.gd` 的 `Command` 表，否则单机能跑、真实联机会被编解码静默丢掉。
10. **存量已清扫完**：全仓手写多段询问已经迁完（见设计文档 5.5 台账）；**新增/改动的多步技能一律按上面写**。
11. **`答完` 返回 SUCCESS 不会中止整条链**（框架事实）：它只表示「这一段处理完了，继续下一段」。
    所以「玩家选了不发动 / 条件不满足」必须让**后续段的 `跳过` 读一个标记**，不能只把标记清掉就 `return SUCCESS`
    —— 否则「不发动」照样会逼目标弃牌、加伤、送牌（异象剑、英灵召唤、收魔术 / 法术剥离、白二羯磨、圣剑都踩过）。
    同理，判断「发不发动」不要用「`args` 非空」，按旧 `take_skill_reply` 口径显式判 `args[0] == 1`。
12. **`跳过` / `问前` 会被重复求值**：同一次重入里它们可能跑好几遍，里面的一次性副作用（打伤害、播报、记标记）
    必须自带幂等标记（异象剑的 `_异象判定` 是写法样板）。反过来，**被跳过的段不会跑它的 `答完`**：
    「不管对手有没有牌都要打的伤害」要么放进 `跳过` 并保证只打一次，要么单列一段必答段（异教徒展示就这么改的）。
13. **`答案[i]` 不等于「第 i 段」**：框架只给**真正问过**的段记答案，被 `跳过` 的段不占槽位。
    只有「前面所有段必问」或被 `答案.size()` 判断保护时才可写死下标；取最后答的那段用 `答案[答案.size() - 1]`。
14. **倒计时只在「同一个人接着答」时沿用**：换人问（循环段逐个问、问目标弃牌）框架会重新计时，
    别再把「整条链一个截止时刻」理解成「所有人都共用一个 60 秒」。

**多行与特殊模式**

| 规则 | 说明 |
| --- | --- |
| 多行 | 用 `\n` 分行；某行开头放 `[zwj]` ＝给该行画加粗删除线（`_铺粗删除线`），用于「原值被划掉」 |
| `反选` | 配置 `"反选": true`：提示画在**没被选中**的角色身上（如百鬼夜行展示火系妖力） |
| `自身` | 配置 `"自身"`：同一技能对自己另写一句（如血之哀伤、猩红十字） |
| `分目标` | 配置 `"分目标"`：按已选目标的顺序逐人一句（如冰冻第 1 人吃伤害、第 2 人 +1 治疗） |
| `目标随牌` | 选够若干张牌后才需要选目标（如英灵召唤弃了法术牌才给治疗） |
| 固定目标 | 服务端下发 `targets`，客户端自动选中并锁死，提示照常画在目标头像上（如瘟疫、毒粉） |
| `自动选目标` | 发动技能（mode 4）时由指示器直接把目标选中并锁死：`询问目标` / `他人` / `全体` / `自己`；`队友` 只高亮不锁 |
| `锁定不可取消` | 配合 `自动选目标`：只作用于自己的技能（如【裁决者】）锁定自己后把「取消」和二级栏的「返回」一起置灰，避免误点重来 |
| 自己技能的效果分行写 | 「只作用于自己的技能」在头像上按「立即效果一行一项」写（如【圣光祈愈】「+2 治疗」「+1 攻击行动」两行）；数值相同走静态 `文案`，数值不同走动态（`battle_mobile._自锁技能头像提示`） |
| 选目标询问的预览 | `need_target > 0` 的询问里，`preview` 只画在**已点选**的目标头像上，不给所有候选人画一遍 |

**配在哪 / 怎么取值**

| 情况 | 写在哪 | 怎么取值 |
| --- | --- | --- |
| 数值固定（每名目标固定值 / 总数均分） | `const.gd` 的 `技能指示器` 表：`文案`＋`每目标` / `总数` | 客户端选完目标直接算 |
| 数值随牌数 / 星石数变化 | 同上：`每牌` / `每能量`＋`偏移` | 客户端按已选牌 / 当前能量现算 |
| 服务端才算得出的基准（原伤害、选项档位、本次伤害） | 询问里带 `preview_base` / `preview_kind` / `preview_ids` | 客户端读 `_预览伤害头像提示` 现算，**不要自己猜** |
| 一个技能多种效果 | 同上：`选项提示`（按 `args[0]` 分支）或 `分目标` | 选中项 / 目标顺序决定用哪句 |

**新增头像文案检查清单**

1. 先在上表找到同类型，**照抄模板**（不要新造词，不要加「点」）；
2. 数值算不出来的，走 `preview_base`（服务端算），不要硬编码；
3. 多行用 `\n`，要划掉的行前缀 `[zwj]`；
4. 自己 / 目标 / 反选 / 分目标先确认画在谁头上；
5. 加完跑自检，并在用例里断言文案原文（防止关键字写错导致颜色不对）。

## 公共能力与借用技约定（13 名 3★/3.5★ 角色落地时新增）

> 38/41/45/46/47/75/78/87/93/97/106/107/108（59 颗技能）新增的公共能力，后续加角色、改技能都按这里接入。
> 逐角色实现要点、口径与遗留见 [禁用3星与3.5星角色开发计划](禁用3星与3.5星角色开发计划.md) 第 0 节；公共能力编号沿用该计划的 F1~F9。

### 1. 角色特性集中配置（不要在客户端散落角色号）

- 客户端与服务端共用 [const.gd](../scripts/core/const.gd) 的 `角色特性` 表，现支持：`魔弹系别`、`魔弹掌控`、`临时掌控来源`、`基础效果免疫`、`双张魔弹`、`魔弹全禁`、`行动阶段禁用法术牌`。
- 「某些系别的牌当【魔弹】」「不能成为基础效果目标」「魔弹传递可选 2 张」这类能力先改这张表，不要在 `battle_mobile.gd` 里再写 `[8, 76]` 之类名单；新增键时同时补 `GConst` 的读取函数与默认值。
- 额外行动的指令条限制文案在 `额外行动提示`（key = 发起额外行动的技能号）；新增额外行动限制时同步加，否则客户端只会显示通用文案。

### 2. 魔弹融合与传递

- 角色侧覆写 `BattleRole.missile_fusion_elements()`（默认火/地）、`can_use_as_missile(card)`，牌表用 `missile_fusion_hand_ids()`；能当魔弹的系别与「临时逆向」都从 `角色特性` 读。
- 传递响应的多牌路径（10603「弃 2 张同系牌视为【魔弹】」）：
  - 角色覆写 `missile_relay_card_max()` 返回 2、`v_remissile_multi(cards)`（恰好 2 张、彼此同系、都在手牌、非虚拟）、`remissile_multi_skill()`（播报技能号）；
  - 引擎 `SMissileAsk` 负责放宽选牌上限、双牌校验失败重问、按多牌结算继续传递并补技能通知；
  - 客户端按「1 张真【魔弹】继续传递 / 1 张【圣光】抵挡 / 10603 恰好 2 张同系视为魔弹」判定提交与取消；单张同系牌不能按普通 Attack 提交（服务端会当放弃）。
- 播报与询问按当前角色自己的技能行取号：4703/8703/10703 不写 803；7503 播 301/302；4606 播源技能号。

### 3. 额外行动与行动计数

- 每回合计数走 `BattlePlayer.action_count()/action_count_of()`；行动结束统一用 `BattleRole.p_action_end`（ctx 带 `action_count`、`is_extra`、`extra_cause`），不要各角色私设计数。
- **额外行动本身是通用工具**：`player.add_action(种类, 来源, direct, skip_notice, spec)` 只描述「哪种行动 + 来源」。出牌白名单 / 目标白名单 / 系别 / 能否切换 / 是否作为行动结束响应，全部由授予它的技能在 `spec` 里一次写清：
  `{"cards": [...], "targets": [...], "element": 系别, "switchable": true, "in_end_response": false}`。
  空表＝不限制，`[GConst.手牌白名单_全禁]` / `[GConst.目标白名单_无]` ＝ 一张牌 / 一个目标都不给。
- **规格里的牌表（`cards` / `skill_cards`）按「牌面」存**：引擎校验是拿提交牌的牌面去比（见 `校验额外行动限制`）。
  角色脚本直接把走手牌拿到的实例号塞进去也行 —— `add_action` / `改写额外行动` 会统一折成牌面；
  但**不要**自己再按实例号另存一份（克隆牌实例号 ≠ 牌面，白名单会对不上、点了就「操作无效」，10702 踩过）。
- **授予时按手牌算出来的白名单会过期**：手牌/双方手牌数在授予之后可能变过（摸牌、弃牌、别人给牌）。
  引擎在「进入这份额外行动」和「本地切换到它」时都会回调 `BattleRole.额外行动规格(cause)`，
  返回非空表就按它把规格重算掉；这类技能覆写它即可（10702 虚荣掌握 / 10704 嫉妒追放都覆写了）。
  不重算的后果：切过去那一手只能用「授予那一刻手里的牌」，之后才拿到的【魔弹】会被旧白名单挡住，
  点不出来 / 硬提交被驳回（玩家看到的就是「这份额外行动有时候打不出魔弹」）。
- 引擎只照单执行（下发 `card_ids` / `dst_ids` / `extra_element`，落牌与选目标按同一份规格兜底），**不再按 `cause` 回问角色**。旧接口 `extra_action_card_ids` / `extra_action_targets` / `extra_action_element` / `额外行动限定系` / `extra_action_switchable` / `v_additional_action` / `额外行动属于结束响应` 已删除，新角色不要再用。
- **回合级 / 玩家级限制不要写进行动规格**：像 10804 剑残影「本回合你的下次主动攻击只能攻击该目标对手」，限制做成玩家身上的标记 `player.set_attack_lock(目标)`（快照字段 `attack_lock` 随之下发）——服务端 `base_v_attack` 校验、引擎在主动攻击打出时消费、回合开始清零，客户端 `_玩家可选` 读同一份标记把其余敌方头像置灰。它给的额外行动就是最普通的攻击行动（`add_action` 不带 `targets`）。否则限制被别的主动攻击消费掉之后，这份行动还会一直锁着那个目标；需要「进入时重算」的、属于这份行动自己的限制才用 `p_additional_action` + `改写额外行动`。
- 技能要按「进入那一刻」的状态重算限制（手牌变过、双方手牌数变了），在 `p_additional_action` 里 `player.改写额外行动(cause, spec)`；这份行动不再可用时 `player.撤回额外行动(cause)`。
- 跳过前置询问的 `direct` 分支必须把 `cause` 随最终命令下发，否则计数、提示都取不到来源。
- **按来源找「队列里那份」用 `额外行动队列数据(cause)`，不要用 `额外行动数据(cause)`**：后者优先返回引擎的「当前额外行动数据」—— 上一个同来源的行动用完后那份数据还留着，会把新入队的一份顶掉：确认时标 direct / 已付费落到旧那份上，新那份保持非 direct，响应结束后又被当成选项问一遍（血色剑灵【赤色一闪】连续两次踩过）。「是否已经排着一份」的判断同样要用队列版本，否则用完一次就再也不授予（女武神【神圣追击】/ 剑帝【不屈意志】/ 祈祷师【迅捷赐福】）。
- **确认「本次响应里没确认的那一份」要传 `未确认=true`**：同一来源可以同时排着好几份——已经确认过、还没轮到的旧份可能排在前面（如一次响应里先确认【迅捷赐福】的行动、再确认【赤色一闪】，迅捷赐福的行动先用掉后，赤色一闪那份还排着；下一次攻击结束又入队一份新的）。按 cause 取第一份会标到旧份上，新的永远确认不了、响应反复问（血色剑灵赤色一闪 + 迅捷赐福连招踩过）。
- **响应阶段不能使用额外行动**：当前正在消耗的额外行动按钮（二级栏最左那颗）和红色额外行动按钮一律置灰、不选中，并排在响应选项左边；只有响应选项（剑影 / 神圣追击 / 迅捷赐福等）可点。行动真正在响应结束后的额外行动阶段使用。
- **代价点选即付**：响应里点选额外行动时走 `行动结束确认代价` 扣代价；取消响应只结束响应：已确认 / 已获得的额外行动保留，**本次响应里还没确认的选项**（`in_end_response` 且未 `direct`）以及**基础效果授予的行动占位**（祈祷师【迅捷赐福】等提前垫进队列、确认时才换成 direct 真行动的那份）由聚合器出栈时撤回（`BattleEngine._撤回未确认额外行动`），否则会漏到额外行动阶段、弹出玩家从没确认过的红色按钮（女武神【神圣追击】/ 剑帝【不屈意志】/ 迅捷赐福踩过）。取消后想用迅捷赐福，等下一次行动结束再确认即可（赐福牌仍在身上）。已确认（direct）的行动在真正进入时补扣一次代价。

### 4. 基础效果目标与触发

- 目标资格：`BattleRole.v_basic_effect_target(dst, card)`（默认成功）；`add_basic_effect` 与圣盾/虚弱/中毒/封印/赐福统一走它，4601 返回失败。
- **放基础效果的技能要把目标资格前移**：`available_skills` 的目标白名单和 `v_magic_skill` 校验都用
  `BattleRole.目标可接收基础效果(dst_id, 技能号)`（它去问目标角色的 `v_basic_effect_target`），
  客户端的可点目标就来自这份白名单 —— 否则 46 灵熙之潮这类「无法成为基础效果的目标」会在界面上被点亮，
  点了却挂不上（封印 401~405 / 赐福 1601~1602 / 天使之墙 701 都这样踩过）。别只靠 `add_basic_effect` 兜底。
- 触发与移除要分开：`p_basic_effect_triggered`（结算完成后）与 `p_basic_effect_change(triggered=...)`；4602/4604 按这个口径。
- 技能行动批量放置用 `basic_effect_placements(action)` 声明目标，`SkillRun` 执行前统一校验。

## 通用补充约定（响应方式 / 费用 / 固定目标 / 提示）

> 以下几条是**跨角色的通用约定**，所有角色、所有新增/改动的技能都按这个来。

1. **响应技能必须先让施法者决定是否响应。**
   - 不能默认发动，也不能先替玩家选目标、选牌或扣资源。
   - 先问“发不发动”，确认后才进入选牌、选目标、选盖牌等步骤。
   - 不发动统一走右下角“取消”，不要再单独摆“不发动”选项。
   - **例外：代价本身就是选牌/选目标时，不要再拆两问。** 如【净化之术】的代价是「弃 1 张法术牌」：
     直接问「弃哪张法术牌」，选牌 + 按「确定」就是发动（一次提交）；想放弃点「取消」＝不发动。
     同理，代价是「选 1 名角色」的响应技也直接问目标，不要先问一次再问目标。
     原因：这类技能的选牌/选目标本身就是发动的确认，先问一次只是白点一次；
     【净化之术】就因为拆两问被反复反馈（2026-11）。

2. **费用写【水晶】时，宝石可以顶水晶；用现成方法判断和支付。**
   - 判断够不够：用 `player.get_energy()`，它是水晶 + 宝石的总数。
   - 支付：用 `player.remove_energy(1)`，内部会先扣水晶，没水晶再扣宝石。
   - 不要自己写 `crystal > 0` 再手动 `set_crystal / set_gem`，容易漏掉宝石替代或扣错顺序。

3. **固定目标也要有头像提示。**
   - 目标即使不能点、不是玩家手动选出来的，只要是本次伤害/治疗的实际对象，也要通过 `targets` / `preview_ids` 下发给客户端。
   - 客户端不能只给 `_sel_players` 画提示；固定目标要单独画。
   - 例：本次攻击目标、本次受伤目标、攻击者，都属于固定目标。

4. **伤害/治疗发生变化时，要显示“原值划掉 → 新值”。**
   - 减伤：目标头像显示“原伤害划掉，下面写减后的伤害”。
   - 加伤：同理显示原值和新值。
   - 同时给自己加治疗/造成反伤时，自己头像也要画对应一句。
   - 服务端下发 `preview_base`（原值）、`preview_kind`（伤害类型）、`preview_ids`（目标）；客户端用 `[zwj]` 标旧值那一行。

5. **提示文案要分清“默认技能说明”和“特殊步骤提示”。**
   - 响应技能发动时默认显示技能说明，不要随便改成自定义短句。
   - 选目标、选牌等特殊步骤需要专用文案时，必须单独配置，并确认不会被响应技能的技能说明覆盖。
   - **整段重写别人技能的效果/提示时用 `ask_prompt`**（`询问(..., ask_prompt)` / `ask_skill(..., ask_prompt)`）：
	 客户端提示条直接显示它，不再套技能表说明。例：萝莉番长 9703【爱死天流】把借来的【血腥咆哮】
	 整段换成「目标拥有【治疗】→ 无法用【暗灭】应战 / 无法用【圣光】抵挡」。不要动技能表里原技能的那一行。
   - **整段重写别人技能的「说明」时配 `GConst.角色技能说明覆盖`**（角色号 → {技能号: 正文}）：
	 技能按钮自带说明 / 鼠标悬停提示（`角色技能提示.单个技能`）/ 角色说明的「独有技」正文都按它取；
	 询问提示条另走上一条 `ask_prompt`。例：萝莉番长 9703 覆盖【血腥咆哮】的说明；
	 见习制片 9304 把借来的元素师【雷击】1105 改成「你 +1 元子」也走这张表。
   - **改写同时要给技能改名时配 `GConst.角色技能改名`**（角色号 → {技能号: 新名}）：
	 技能栏按钮 / 鼠标悬停的技能名 / 角色说明的「独有技」标题都按它取。
	 命名口径：原技能名 + 「*」 + 该角色的**姓名**（角色表「姓名」列，不是职业名；不加颜色）。
	 例：【血腥咆哮*柠歌】（柠歌是萝莉番长的姓名）、【雷击*惕惕子】（惕惕子是见习制片的姓名）。
	 **不再**把原版技能整段列出来划掉。
   - **禁某张牌应战**：攻击 ctx 写「禁应战牌名」＝卡名枚举数组（如 9703 的 `[GConst.CardName.DarkSlash]`）；
	 引擎 `SAttackedAsk` 用 `_禁应战` 复核，并通过 `ban_reattack_card_names` 随应战询问下发，
	 客户端据此把那张牌置灰（服务端仍以复核为准）。
   - 技能表“提示”列按 0 基索引读取；改完设计表后要重新导表并核对 CSV、DataTables。
