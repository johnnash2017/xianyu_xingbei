# 技能维护约定

> 修改角色技能、配置表前先读这份约定。
> 配置表以设计表为唯一权威来源；改表统一用 DSH 的 excel-chat 工具，不再临时写脚本。

## 触发条件

**只要在修改角色技能，就按本约定执行。** 包括：

- 主动技能、被动技能、响应技能、额外行动
- 技能选项、二级选项、多步选项
- 选牌、选目标、盖牌/手牌混选
- 技能头像提示、伤害/治疗提示、技能指示器
- 技能相关协议字段、一次性状态、数据表

开始改代码或数据前，先按本约定的规范过一遍；改完后按检查清单自检。

## 配置表约定（设计表是权威来源）

`Table/Design/设计表.xlsx` 是配置表数据的**唯一权威来源**。

任何表格数据的修改，都必须先改设计表，再通过导表生成后续文件；**禁止**把 `Table/Csv/*.csv` 或 `Table/TableScripts/DataTables.gd` 当作源文件直接修改。

### 适用范围

- 卡表、技能表、角色表、词缀等所有由设计表导出的数据。
- 新增、删除、修改行/列、ID、文案、数值、引用字段。
- 只修改 GDScript 逻辑、不涉及表格数据时，不强制改设计表。

### 正确流程

1. 在 `设计表.xlsx` 中修改目标工作表。  
   只有名称以 `.csv` 结尾的工作表会被导出；当前包括：`卡表`、`技能表`、`角色表`、`词缀`。
2. 在 Godot 编辑器执行「检查并转换表格」，或按 `Ctrl + Shift + T` 重新导表。
3. 检查导出的：
   - `Table/Csv/*.csv`：供人工检查的中间态。
   - `Table/TableScripts/DataTables.gd`：自动生成、运行时真正读取的数据表。
4. 发现数据不一致时，回到设计表修正后重新导表，不要手改生成文件。
5. 提交时，设计表与导表产物一起提交，避免源表和生成结果不一致。

### 改表用插件工具，不要临时写脚本

修改 `设计表.xlsx` 统一用 DSH 的 `dsh-excel-chat` 插件（已装在本机 `web` profile，重启 DSH 后加载），不要再为每次改表现写 Python 脚本。

1. **定位**：先用 `excel_profile` 看表结构，或用 `excel_read` 的 `range` + `maxRows` 分页读目标区域。不要把整张表读进对话。
2. **修改**：用 `excel_operate` 原地写回，**必须显式把 `outPath` 设为原文件路径**：

   ```json
   {
	 "path": "D:/星杯传说工程/星杯传说2/xianyu_xingbei/Table/Design/设计表.xlsx",
	 "outPath": "D:/星杯传说工程/星杯传说2/xianyu_xingbei/Table/Design/设计表.xlsx",
	 "operations": [
	   { "op": "set", "cells": { "技能表.csv!H223": "请选择{n}张【手牌】弃掉" } }
	 ]
   }
   ```

   - 工作表名带 `.csv` 后缀：`技能表.csv`、`卡表.csv`、`角色表.csv`、`词缀.csv`、`文本表.csv`（是否参与导出以上面第 1 条为准）。
   - **不传 `outPath` 会写成 `设计表.edited.xlsx` 副本，原表不变**，这是最容易犯的错。
   - 正常结果：`warnings` 为空，`validation` 的 `anomalies`、`errors` 为空。出现 `warnings` 时先看清再继续。
   - 改单个单元格/文案/数值用 `set`；插行、填充、批量改等多步操作放在同一个 `operations` 数组里一次完成。
3. **清理**：原地写回会在同目录生成 `设计表.xlsx.bak`（改前快照，供 `excel_undo` 回滚）和 `设计表.xlsx.patch.json`（审计日志）。确认导表结果无误后删除这两个文件，不要提交。
4. **导表**：仍按上面的流程执行「检查并转换表格」，生成 CSV 与 `DataTables.gd`。

注意事项：

- 写回前确认 `设计表.xlsx` 没有被 Excel/WPS 打开占用，否则会写入失败或产生冲突。
- 插件首次保存会把 `xl/styles.xml` 默认字体槽的名字从 `等线` 改成 `Calibri`（两者都带 `scheme="minor"`，指向主题字体；单元格值、样式、合并、列宽不变）。如果发现设计表外观有肉眼可见的变化，先停下来确认，不要继续批量改。
- 插件不可用时（新机器未安装、或装了但还没重启 DSH），才退回内置 Python + openpyxl 的临时脚本；脚本和备份放 `.dsh/tmp`，用完删除。
- 重装插件时如果 `dsh plugin add` 报 `ERR_PNPM_VIRTUAL_STORE_DIR_MAX_LENGTH_DIFF`，说明 profile 的 lockfile 由 pnpm 8 生成、与当前 pnpm 11 不兼容；改用 `npx pnpm@8.15.9 add dsh-excel-chat`，再把 `dsh-excel-chat` 补进 profile `package.json` 的 `dsh.profile.bundles`。

### 禁止

- 只改 CSV 或 `DataTables.gd`，不改设计表。
- 直接编辑生成文件中的数值、文案或结构。
- 改了设计表但不导表，导致运行时仍读取旧数据。
- 用临时 Python 脚本直接读写 `设计表.xlsx`（应使用 `excel_operate`）；`excel_operate` 不传 `outPath` 只生成副本，当成原表已改。

### 二级技能栏选项：完整下发，不可用只置灰

适用范围：服务端 `arg_choices`、二级技能栏里的固定分支、以及同一窗口里的固定效果选项。

- 固定选项集合必须**完整、稳定地下发**，不能因为当前条件不满足就用 `if` 少一项或整项消失。
- 当前做不了的项保留在数组里，并写 `"enabled": false`；客户端据此半透明置灰、点不动。
- 技能本体的 `enabled` 只在「至少有一个选项 `enabled`」时为 true。不能只写
  `not 选项.is_empty()`——选项现在始终存在，必须检查是否还有可选项。
- 客户端只负责显示和置灰，不要自行补项或删项；服务端仍要对硬提交的置灰项做兜底校验。
- 选项文案不要用括号包说明；需要补充说明时直接接「，弃 3 张」这种逗号形式。
- 选项的系别配色只染卡名本身，不整段染色；卡名不要再用【】包起来。
- 选项只是进入下一层（本身不是最终参数）时，点中选项立即进入下一层，不再要求先点一次「确定」；
  最终参数/构成选择仍按「确定」提交。
- 多级询问可以取消回到上一层时，父按钮右侧必须提供明确的「返回」按钮，不能只靠「取消」键
  或提示文字说明；服务端的空应答/取消语义要与该返回行为一致。
- 例外：选项本身就是随资源/牌数动态枚举的数值档位（如「移除 1..N 张」，N 是当前可用上限），
  可以只生成合法范围；但固定的档位、固定的分支（如“转移 / 转换”两选一）不得省略。

### 完成检查

- [ ] `.bak` / `.patch.json` 已清理，没有混进提交。
- [ ] 已重新导表。

## 修改流程

1. **定位完整改动链**
   - 数据：`Table/Design/设计表.xlsx` → `Table/Csv/*.csv` → `Table/TableScripts/DataTables.gd` → `scripts/data/*.gd`
   - 逻辑：`scripts/battle/roles/*.gd`、`scripts/battle/battle_engine.gd`
   - 界面：`scripts/ui/battle_mobile.gd`、`scripts/PlayerStatusMobile.gd`、`scripts/CardUI.gd`
   - 配置：`scripts/core/const.gd`、`scripts/core/proto_schema.gd`
   - 确认一条数据/字段从产生到显示/校验的每一层都接上。

2. **服务端权威，客户端只做体验过滤**
   - 合法牌、合法目标、选项可用性、资源扣除最终都由服务端校验。
   - 客户端过滤只负责让玩家少点错，不能替代服务端校验。
   - 需要精确区分来源时（手牌/盖牌），按实际来源分别校验，不能只数总张数。

3. **按下方规范设计技能交互**
   - 先把选项、选牌、目标、状态、提示和协议设计完整，再改实现。
   - 不要只改服务端，或只改客户端其中一层。

4. **同步协议、数据和测试**
   - 新字段要贯通 schema → 服务端下发 → 客户端读取 → UI 使用。
   - 数据表改动要同步 CSV、DataTables 和运行时代码。
   - 补对应边界测试。

5. **运行自检**
   - 按项目现有自检入口运行。
   - 区分新增失败和原有失败，不能把原有失败当成通过。

## 角色技能规范（场景 → 检查）

1. **不可选项也要下发，用 `enabled=false` 置灰，不要删除。**
   - 场景：技能有两档效果，一档缺资源、缺目标或缺手牌。
   - 检查：按钮仍在、半透明、点不动；玩家能看到技能的全部用法。

2. **每个选项独立配置需牌、需目标、白名单、盖牌数；全局字段只作基准。**
   - 场景：同一技能 A 档弃 1 张、无目标；B 档弃 2 张、要 1 名目标。
   - 检查：切换选项后，需牌数、目标数、可点目标都跟着该项变。

3. **多资源操作一次询问完成；服务端按来源精确校验，客户端只做过滤。**
   - 场景：技能代价是“1 张盖牌 + 1 张手牌 + 1 名目标”。
   - 检查：同一步选完再提交，不再多弹一次弃牌；服务端能区分哪张是盖牌、哪张是手牌。

4. **混合选牌必须区分手牌与盖牌，过滤按选项、按来源生效。**
   - 场景：手牌和盖牌都能点，但某一档要求其中几张必须来自盖牌。
   - 检查：选项切换后过滤规则跟着换；客户端挡明显非法组合，服务端仍做最终校验。

5. **无目标分支要同时清空 `need_target` 和 `target_max`。**
   - 场景：一个分支打目标，另一个分支只给自己加状态、摸牌或获得额外行动。
   - 检查：选到无目标分支后头像不再可点，直接按“确定”即可发动。

6. **本地多步选项到最后一步才提交；取消按层级回退上一层。**
   - 场景：先选效果，再选 X 点/档位，最后选牌和目标。
   - 检查：中途不发服务端请求；第二步取消回第一步，第一步取消才取消整个技能。

7. **固定目标由服务端下发，客户端自动选中并锁死。**
   - 场景：响应技能的目标就是“本次攻击目标”“攻击者”或“自己被攻击时固定的人”。
   - 检查：`targets` 随询问下发，客户端进场自动选中，头像亮起且点不动。

8. **头像提示区分静态值/现算值、自身/目标；算不出的基准由服务端下发。**
   - 场景：提示数值取决于弃牌数、选项档位、原伤害或角色被动。
   - 检查：静态部分写配置，动态部分用 `preview_base` 等基准现算；自己身上的效果不要画到目标身上。

9. **攻击伤害、法术伤害、治疗的文案、颜色、数值口径分开。**
   - 场景：同一技能或同一角色同时有攻击加伤、法术伤害和治疗。
   - 检查：三种提示分别使用对应关键词和颜色，数值不要互相套用。

10. **一次性状态要明确置位与清除时机；跳过常规询问的分支要随最终命令传递来源。**
	- 场景：一次性无法应战、额外行动、临时加伤、本回合限定效果。
	- 检查：在正确钩子置位/清除；`direct` 等跳过前置询问的分支，来源 `cause` 要随最终命令下发。

11. **涉及的协议字段、数据、客户端读取和边界测试要同步更新。**
	- 场景：新增选项参数、选牌来源、额外行动来源、标记字段。
	- 检查：schema 有字段 → 服务端下发 → 客户端读取 → UI 真正使用 → 测试覆盖置灰、取消回退、不提前提交、固定目标等边界。

## 提交前检查

- [ ] 表格数据改动已从设计表发起并重新导表，没有手改 CSV / `DataTables.gd`。
- [ ] 固定选项完整下发，不可用项仍存在且 `enabled=false`；技能本体在至少一个选项可用时才可点。
- [ ] 选项文案没有用括号包说明；系别色只染卡名，卡名没有【】。
- [ ] 多级选项进入下一层不用先点「确定」；最终参数才需要确定；能取消回上一层时有「返回」按钮。
- [ ] 每个选项的需牌、目标、白名单、盖牌需求都已配置。
- [ ] 多资源操作一次提交，服务端按来源精确校验。
- [ ] 混合选牌能区分手牌与盖牌，过滤规则按选项生效。
- [ ] 无目标分支的 `need_target` 和 `target_max` 都已清零。
- [ ] 本地多步选项没有提前发请求，取消能回上一层。
- [ ] 固定目标由服务端下发，客户端自动选中并锁死。
- [ ] 头像提示的数值、文案、颜色和对象（自己/目标）正确。
- [ ] 一次性状态有明确的置位和清除时机，跳步分支的 cause 已传递。
- [ ] 协议字段、数据、客户端读取和 UI 行为全部接上。
- [ ] 关键边界已测试，并区分新增失败与原有失败。

## 完成标准

- 行为符合服务端规则，客户端只做体验层过滤。
- 玩家能看见技能的完整用法，不可用项有明确置灰反馈。
- 目标、选牌、提示、状态和协议形成闭环，没有只改一半的链路。
- 关键边界有测试或可复现的验证步骤。
