# 英灵召唤回复丢失问题复盘

> 面向：要改引擎「等待 / 回复」机制、或写多步询问技能的人。
> 记录 2026-11-03 ~ 11-04 的四次提交：`797a327`（形态与询问的先后）、`0831ab0`（能量门槛）、
> `f4cfe78`（引擎回复归属）、`e2cf4c2`（用例与口径补充）。
> 单条技能写法规范见 [技能维护约定](技能维护约定.md) 第 19、20 条；引擎等待机制见 [战斗系统架构](战斗系统架构.md) §4.5。

## 0. 结论先说

同一句症状 —— **「玩家在界面上答完了一问，服务端却什么都没做」** —— 底下叠着两个独立原因：

| # | 原因 | 层面 | 修复 |
| --- | --- | --- | --- |
| 1 | 等待槽只有一份，等待期间被压到栈上的状态先问了别人，把上一位等待者的回复冲掉 | 引擎 | `f4cfe78`：回复按归属状态暂存，回到栈顶再恢复 |
| 2 | 多步询问的钩子顶部留了「资源门槛」，第 2 步重入时资源刚好用光，钩子提前 `return`，回复没人取 | 角色 | `0831ab0`：门槛只在第 0 步判 |
| 3 | 形态变更（`player.tap`）压在询问之前，制造了原因 1 的触发条件 | 角色 | `797a327`：先取回复，再改形态 |

第 1 条是**结构性缺陷**（本次已收敛到引擎层），第 2、3 条是**写法缺陷**（已定成规范）。
三者都不报错、不写日志，客户端界面照常收掉那一问 —— 所以从外面看永远是「点了没反应」。

## 1. 现象与定位过程

**现象**：女武神攻击命中后发动【英灵召唤】。第 1 问（是否发动）确认 → 第 2 问选 1 张法术牌 + 1 名治疗目标 → 按「确定」后：
法术牌没弃、目标没加治疗。第一次使用更容易出现；有些局里又能正常结算。

**定位顺序**（供以后排查同类问题参考）：

1. **先排除客户端**：把服务端真实下发的第 2 问原样喂给战斗界面，点牌 + 点头像 + 确定，
   发出的应答是 `{respond_id: 25051, dst_ids:[3], card_ids:[法术牌], args:[1]}` —— 提交内容完全正确。
2. **再排除服务端结算**：用真实引擎状态栈跑「行动 → 攻击 → 放弃应战 → 命中 → 两问」，正常局里弃牌与治疗都能落地。
3. **差异只在「等待期间有没有别的东西插进来」**：第 2 问是在钩子（`p_timeline_2_hit`）里问的，
   而钩子返回 `WAIT` 之后，任何被压到栈上的状态都会在回复到达时先跑。
4. 顺着这条线找到 `player.tap = true`（会压入一轮 `p_tap` 钩子）与钩子顶部的能量门槛两处。

> 结论：**「回复有没有被消费」要单独查**。症状是「静默不结算」时，先画「谁在等 → 谁取走 → 谁清空」这条链，
> 再谈具体技能逻辑；只盯着角色脚本会漏掉引擎那半。

## 2. 原因一：等待槽只有一份，插队询问会顶掉回复

### 2.1 机制

引擎的等待态是**单槽**：`_await_id` / `_await_kind` / `_await_state` / `_reply` / `_has_reply`。
`wait_for()` 每被调用一次就整体覆盖；`on_message()` 收到回复后写进这一槽，`take_reply()` 取走。

`player.tap = true` 的 setter 会压入一轮 `p_tap` 钩子（[battle_engine.gd:3669](../scripts/battle/battle_engine.gd#L3669)）。
如果这一轮排在「正等第 2 问」的状态之上，那么第 2 问的回复一到，引擎先跑的是 `p_tap`：

- 兽灵【兽魂警戒】3604 就在 `p_tap` 里开询问（[role_shouling.gd:440](../scripts/battle/roles/role_shouling.gd#L440)）；
- 它的 `wait_for()` 重置等待槽，女武神那份「已收到、还没被取走」的回复被冲掉；
- 女武神重入时 `take_reply()` 拿到空字典 → `card_ids` 为空 → 既不弃牌也不加治疗，`_英灵_阶段` 直接置 2 收尾。

### 2.2 角色侧规避（`797a327`）

- 第 1 问确认时**只记** `_英灵_待横置`，真正 `player.tap = true` 挪到第 2 问的回复取走之后
  （[role_nvwushen.gd:254](../scripts/battle/roles/role_nvwushen.gd#L254)、[L268](../scripts/battle/roles/role_nvwushen.gd#L268)）；
- 行动结束（`p_after_attack` / `p_after_magic`）一并清这个标记；
- 取消第 2 问时同样横置（英灵召唤已经发动，形态该落）。

### 2.3 引擎侧根治（`f4cfe78`）

角色侧规避只解决了「这一个技能」。真正的缺陷在引擎：**等待槽只有一份，且覆盖时不保留已收到的回复**。
改法是「按归属状态暂存」：

- 新增 `_挂起回复: Dictionary`（状态实例 → `{reply, kind}`，[battle_engine.gd:194](../scripts/battle/battle_engine.gd#L194)）；
- `wait_for()` 覆盖等待槽之前，如果槽里躺着一份「已收到、还没被取走」的回复，且等待归属是**别的状态**，
  先把它存进 `_挂起回复`（[L1165](../scripts/battle/battle_engine.gd#L1165)）；
- `has_reply()` / `take_reply()` 先调 `_恢复挂起回复()`：当前状态在暂存区里有货、且等待槽空着，就把它放回槽里再判断
  （[L1197](../scripts/battle/battle_engine.gd#L1197)、[L1216](../scripts/battle/battle_engine.gd#L1216)、[L1222](../scripts/battle/battle_engine.gd#L1222)）；
- `_清空等待()` 一并清空暂存区（[L1254](../scripts/battle/battle_engine.gd#L1254)）；
- 行动聚合器原来直接读 `_reply` 的那条私有路径，也改成先恢复再取（[L4098](../scripts/battle/battle_engine.gd#L4098)）。

时序（原来会丢的那种）：

```text
外层状态问 1 号  ──WAIT──────────────┐
  1 号回复到达（进等待槽）            │
  run()：栈顶是内层状态               │
    内层状态问 2 号 ─ wait_for ──► 覆盖前把「1 号的回复」按外层状态暂存
  2 号回复 → 内层取走 → 内层出栈
  外层回到栈顶 → has_reply() 恢复 → take_reply() 取到 1 号的回复 ✓
```

### 2.4 兜底告警（同一提交）

`run()` 在状态出栈前会调 `_清理状态遗留回复()`（[L820](../scripts/battle/battle_engine.gd#L820)、[L1276](../scripts/battle/battle_engine.gd#L1276)）：
状态都结束了，回复还挂着（活槽或暂存区），说明没人要它 —— 清掉，并在调试期打印：

```text
[引擎] SHook(p_timeline_2_hit) 结束时还挂着一份没取走的回复：入口守卫多半在重入时提前 return 了
```

这把「静默失败」变成「看得见的一条日志」，原因二那种毛病以后不用靠人肉复现才能发现。

## 3. 原因二：入口守卫在「重入」时提前 return

`p_timeline_2_hit` 顶部原来写：

```gdscript
if player.get_energy() == 0 or _英灵_阶段 >= 2:
    return SUCCESS
```

拆成两问之后，这句**每次重入都会判一遍**：

1. 第 1 问确认 → 扣 1 能量（玩家通常只有 1 点，付完正好 0）；
2. 第 2 问发出，玩家选牌选目标；
3. 回复到达 → 钩子重新进入 → 第 1 句就把「能量为 0」判成「不发动」→ 直接 `SUCCESS`，
   `take_reply()` 没有被调用 → 回复没人要，弃牌与治疗都不发生。

**测试没抓到的原因**：用例里给了 `set_crystal(2)`，付完还剩 1 点，门槛正好通过。

**改法**（`0831ab0`，[role_nvwushen.gd:229](../scripts/battle/roles/role_nvwushen.gd#L229)）：
能量门槛只放在「还没发动」这一步判，后续步骤只看阶段标记：

```gdscript
if _英灵_阶段 >= 2:
    return SUCCESS
if _英灵_阶段 == 0 and player.get_energy() == 0:
    return SUCCESS
```

## 5. 影响面与兼容性

| 项 | 结论 |
| --- | --- |
| 协议 / 客户端 | **无改动**。没有新字段，等待条、超时提示、重连补发都按原字段工作 |
| 等待语义 | 活动等待仍是「最近一次 `wait_for`」；暂存的只是**已经答复过**的回复，不参与 `tick()` 超时 |
| 超时兜底 | `_提交默认回复` 写当前活动等待；内层超时只清内层，外层暂存的回复不受影响 |
| 断线重连 | `重发当前询问` 只看 `_await_id`；已答复的回复不需要重发 |
| 既有用例的直连写法 | 测试直接 `引擎._has_reply = true`（`_当前状态`、`_await_state` 都是 null）时，恢复逻辑直接跳过，行为不变 |
| 生命周期 | 暂存条目在「取走 / 状态出栈 / 开局 / 终局」四处清理，不会累积 |

## 7. 遗留与后续建议

1. **告警不是全覆盖**：如果同一个状态里前一位把回复留着不取、后一位又发了新询问，覆盖发生在「同状态重问」判定上，
   不会进暂存区，也就不会打印告警（行为与改造前一致）。
2. **归属仍按状态实例，不按座位**：同一个 `SHook` 轮次里所有角色共用一个归属，钩子必须先确认「这一问在问我」
   再 `take_reply()`。要按座位细化，需要引擎在调用钩子时带上当前座位，属另一层改造。
3. **多步询问建议收成显式阶段机**：阶段值 + 待办，入口守卫只对第 0 步生效；本次 2505 已经是这个形态，
   新角色照抄即可（见技能维护约定第 20 条）。
4. **测试构造建议**：多步技能的用例要按「付完代价之后」的瞬间状态构造（能量归零、治疗归零、最后一张牌），
   而不是只看「够不够发动」。
