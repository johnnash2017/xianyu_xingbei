> **一句话**：现在「一个技能怎么问玩家」有三套写法，我们要收成一套。
> **当前进度**：阶段 2 完成（规格类已落地、未接线）+ 阶段 8 已清 3 项死代码。**玩家可见行为零变化。**
> **最后更新**：2026-11-06
> **维护方式**：每做完一步回填 §5；踩到坑回填 §6；§4 的「实际变化」实施后按真实结果改。

## 1. 问题归类（现状体检）

> 归类的目的：同一类问题一次改完，不要一个一个技能修。

### A. 三个询问入口各写一遍

| 入口 | 位置 | 问题 |
| --- | --- | --- |
| 行动询问 | `battle_engine.gd:2341–2380` | 技能按钮字段在这里抄了一遍 |
| 额外行动 | `battle_engine.gd:2408–2433` | 白名单 / 目标 / 系别 / 命格又抄一遍 |
| 技能询问 | `ask_skill`，`battle_engine.gd:2499` | **25 个参数**，字段语义靠注释 |
| 普通应答 | `ask_respond`，`battle_engine.gd:2437` | 11 个参数，另一套 |

结果：同一个「可点牌白名单」有三种下发口径（`card_ids` / `extra_attack_cards[].ids` / `option_cards[].ids`），三条都存三种结构。

> **更隐蔽的一条**：两条通道的 `args` 布局**不同名同序**——
> - 行动询问（技能栏按钮）：`args = [技能号, 需牌, 需目标, 最多目标, 选牌来源]`
> - 技能询问（`ask_skill`）：`args = [需牌, 需目标, 选牌来源, 选项数, 选项值…]`
>
> 客户端靠 `is_skill` 标记走不同解析（`_构建技能按钮` vs `_进入技能询问`）。看代码时极易串位，
> 属于阶段 5「协议统一」要收掉的东西。

> **已做（阶段 3）**：行动询问里那段 45 行的技能按钮字段映射，已抽成 `_技能按钮命令(pl, sk, action_type)`。

### B. 选项属性用 13 个平行数组

服务端（`battle_engine.gd:2541–2570`）按下标拼 13 个数组：
`option_skill_ids / option_enabled / option_need_cards / option_targets / option_card_ids / option_no_prompt_change / option_prompts / option_switch_desc / option_need_targets / option_preview_cards / option_elements / option_skill_groups / option_cards`

客户端（`battle_mobile.gd:2620–2677`）再按下标读回来拼字典。每个数组还有各自不同的下发条件（`.max()>0` / `.has(true)` / 字符串非空），少写一个条件的后果是「字段永远收不到、恒为默认值」。

客户端这边同样有**三种选项形状**，同一个选项被翻译三遍：

| 形状 | 产生处 | 说明 |
| --- | --- | --- |
| 服务端原始键 | 角色脚本 `options` 里的 `value/label/enabled/need_card...` | `_选项项`（`3934`）翻成中文键 |
| 内联拼装 | `_进入技能询问`（`2644–2677`）逐字段 `if` 追加 | 从 13 个平行数组拼 |
| 二级栏内部结构 | `_归一化二级选项`（`4055`） | 白名单式再抄一遍字段 |

`_归一化二级选项` 的注释自己写着：「新增的选项开关很容易漏抄…表现就是服务端已经下发了，客户端完全没反应」。这就是三形状的直接代价。

> **已修（阶段 3 第一片）**：三种形状现在都过同一个 `_规整选项`，键集与默认值只在这里定义一次；未知键仍原样透传，以后加开关不用再改三处。
> **已修（阶段 3 第十二片）**：读取侧也表驱动了 —— 13 个平行数组的逐项 `if i < 数组.size()` 换成 `_第i项(数组, i, 默认)` + `_子id()`，58 行塌成 26 行，少读一个数组就是「落回默认」而不是「静默丢能力」。

**同一个概念存了三份**：
- 「选项要不要牌」= `option_need_cards` + 指示器 `选项目标数` + 指示器里选中项 `需牌`，最后 `maxi()` 合并（`battle_mobile.gd:2892`）；
- 「选项能点谁」= `option_targets` + 指示器 `选项目标数` + 客户端 `_参数选项目标白名单()` 三处并集。

## 2. 目标模型：一份「询问规格」

> 不追求做成框架，只求「一个技能 = 一份数据」。

```gdscript
# 一次询问的全部内容（服务端产出，客户端消费）
{
  "类型": "行动 | 应答 | 技能",
  "发起人": pid,
  "选牌": {
	  "来源": 手牌 | 盖牌 | 两者 | 基础效果,
	  "需": 2, "最多": 3,
	  "白名单": [牌面...],          # 非空才限制
	  "约束": ["同系", "法术牌"],    # 现在的 card_rule / 槽位合并成约束列表
	  "逐张": [{...}],              # 只给元素师这类真要逐张的
  },
  "选目标": {
	  "需": 1, "最多": 1,
	  "白名单": [pid...],
	  "约束": ["敌方", "非自己"],
  },
  "选项": [                         # 每个选项自带自己的子规格，覆盖上面
	  {"值": 2, "文案": "...", "可用": true, "说明": "...",
	   "选牌": {...}, "选目标": {...}, "展示": {...}},
  ],
  "额外行动": [{"uid": 3, "来源": 2701, "放行": 攻击, "白名单": [...], "系别": 0, "命格": 0}],
  "展示": {"高亮": [pid...], "锁定目标": false, "预览": {...}},
  "提交": {"可取消": true, "默认项": -1},
}
```

配套三个判定函数，客户端只有这三个入口：

```
可点牌(规格, 牌实例) -> bool
可点目标(规格, pid) -> bool
可确认(规格, 已选) -> bool
```

**关键点**：规格里没有「技能号」。技能号只用来查文案和发光效，不再参与判定。

### 4.7 ⚠ 唯一必须拍板的可见变化：未选效果前的手牌置灰

**现象**：配了「先弹选项」的技能，在玩家还没点效果时，手牌亮不亮现在有三种表现。

| 情况 | 现在 | 例子 |
| --- | --- | --- |
| 选项带「牌白名单」 | 手牌**整片灰**（`_卡牌能点:5155`） | 灵熙之潮 4606、异教徒 9507/9508 |
| 选项只带「牌系 / 牌型」 | 手牌**全亮**，点了才被挡（`5064` 要求已选参数） | 百鬼夜行、美杜莎之眼 **(待核)** |
| 配了「允许先选牌」 | 手牌**全亮**（故意的） | 神圣领域 1506 |

**统合后规则**（只有一个）：没选效果前，凡是「效果会改变可点牌集合」的技能，手牌一律整片置灰；确实要放宽的，显式写「允许先选牌」。

**影响面**：百鬼夜行、剑气斩、死亡之触、神圣鞭策、熵变支付、魔法入门、亡女的金库、魔眼、魔纹融合、希望赋格曲、激昂狂想曲、动物伙伴、御魂流居合式、散华轮舞、美杜莎之眼、月之轮回、兽返（神圣领域配了「允许先选牌」，不变）。

**为什么要改**：现在同一件事三种表现，玩家学不会，我们每加一个技能都要重新决定一次。

**代价**：这些技能进询问后要先点效果才能点牌。如果你认为某几个技能「先选牌再说」更顺手，就在这条下面点名豁免，我会在规格里给它们加「允许先选牌」。
