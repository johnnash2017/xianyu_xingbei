## 0. 目标与红线

### 0.1 要达成

| # | 目标 | 判断标准 |
| --- | --- | --- |
| 1 | **整合** | 一个技能只在一处写「要选什么」，技能栏 / 二级栏 / 响应询问都读这一处 |
| 2 | **统一** | 「牌能不能点」「头像能不能点」「确定能不能按」各只有一个判断函数 |
| 3 | **简化** | 新增一个交互特性 = 改 1 处规格，不再同时动 4 个文件 |
| 4 | **去硬编码** | 客户端 119 处按技能号特判（73 个技能）降到接近 0（角色特性表保留） |
| 5 | **兼容** | 现有技能行为不变；必须变的，逐条列在 §4 让你拍板 |
| 6 | **减死代码** | 平行数组、双轨状态变量、没人读的协议字段清掉 |

### 0.2 红线

- 不跑测试（你跑）；不关任何已开的窗口；不改技能 / 卡牌描述；配置只改设计表。
- 每阶段结束我自己走一遍上下游（schema → 服务端 → 客户端 → UI），不靠测试兜底。
- 行为变化**只在 §4 明列的地方**发生，其余一律等价重构。

## 1. 问题归类（现状体检）

> 归类的目的：同一类问题一次改完，不要一个一个技能修。

### A. 三个询问入口各写一遍

| 入口 | 位置 | 问题 |
| --- | --- | --- |
| 行动询问 | `battle_engine.gd:2341–2380` | 技能按钮字段在这里抄了一遍 |
| 额外行动 | `battle_engine.gd:2408–2433` | 白名单 / 目标 / 系别 / 命格又抄一遍 |
| 技能询问 | `ask_skill`，`battle_engine.gd:2499` | **25 个参数**，字段语义靠注释 |
| 普通应答 | `ask_respond`，`battle_engine.gd:2437` | 11 个参数，另一套 |

结果：同一个「可点牌白名单」有三种下发口径（`card_ids` / `extra_attack_cards[].ids` / `option_cards[].ids`），三条都存三种结构。

> **更隐蔽的一条**：两条通道的 `args` 布局**不同名同序**——
> - 行动询问（技能栏按钮）：`args = [技能号, 需牌, 需目标, 最多目标, 选牌来源]`
> - 技能询问（`ask_skill`）：`args = [需牌, 需目标, 选牌来源, 选项数, 选项值…]`
>
> 客户端靠 `is_skill` 标记走不同解析（`_构建技能按钮` vs `_进入技能询问`）。看代码时极易串位，
> 属于阶段 5「协议统一」要收掉的东西。

> **已做（阶段 3）**：行动询问里那段 45 行的技能按钮字段映射，已抽成 `_技能按钮命令(pl, sk, action_type)`。

### B. 选项属性用 13 个平行数组

服务端（`battle_engine.gd:2541–2570`）按下标拼 13 个数组：
`option_skill_ids / option_enabled / option_need_cards / option_targets / option_card_ids / option_no_prompt_change / option_prompts / option_switch_desc / option_need_targets / option_preview_cards / option_elements / option_skill_groups / option_cards`

客户端（`battle_mobile.gd:2620–2677`）再按下标读回来拼字典。每个数组还有各自不同的下发条件（`.max()>0` / `.has(true)` / 字符串非空），少写一个条件的后果是「字段永远收不到、恒为默认值」。

客户端这边同样有**三种选项形状**，同一个选项被翻译三遍：

| 形状 | 产生处 | 说明 |
| --- | --- | --- |
| 服务端原始键 | 角色脚本 `options` 里的 `value/label/enabled/need_card...` | `_选项项`（`3934`）翻成中文键 |
| 内联拼装 | `_进入技能询问`（`2644–2677`）逐字段 `if` 追加 | 从 13 个平行数组拼 |
| 二级栏内部结构 | `_归一化二级选项`（`4055`） | 白名单式再抄一遍字段 |

`_归一化二级选项` 的注释自己写着：「新增的选项开关很容易漏抄…表现就是服务端已经下发了，客户端完全没反应」。这就是三形状的直接代价。

> **已修（阶段 3 第一片）**：三种形状现在都过同一个 `_规整选项`，键集与默认值只在这里定义一次；未知键仍原样透传，以后加开关不用再改三处。
> **已修（阶段 3 第十二片）**：读取侧也表驱动了 —— 13 个平行数组的逐项 `if i < 数组.size()` 换成 `_第i项(数组, i, 默认)` + `_子id()`，58 行塌成 26 行，少读一个数组就是「落回默认」而不是「静默丢能力」。

**同一个概念存了三份**：
- 「选项要不要牌」= `option_need_cards` + 指示器 `选项目标数` + 指示器里选中项 `需牌`，最后 `maxi()` 合并（`battle_mobile.gd:2892`）；
- 「选项能点谁」= `option_targets` + 指示器 `选项目标数` + 客户端 `_参数选项目标白名单()` 三处并集。

### C. 一级 / 二级技能栏是两条独立渲染路径

| 栏 | 函数 | 数据来源 |
| --- | --- | --- |
| 一级 | `_构建技能按钮`（`battle_mobile.gd:3670`） | 从 `args[0..4]` 按下标解包 |
| 二级 | `_进入二级技能栏`（`battle_mobile.gd:4086`） | 从 `_归一化二级选项` 读字典 |

## 2. 目标模型：一份「询问规格」

> 不追求做成框架，只求「一个技能 = 一份数据」。

```gdscript
# 一次询问的全部内容（服务端产出，客户端消费）
{
  "类型": "行动 | 应答 | 技能",
  "发起人": pid,
  "选牌": {
	  "来源": 手牌 | 盖牌 | 两者 | 基础效果,
	  "需": 2, "最多": 3,
	  "白名单": [牌面...],          # 非空才限制
	  "约束": ["同系", "法术牌"],    # 现在的 card_rule / 槽位合并成约束列表
	  "逐张": [{...}],              # 只给元素师这类真要逐张的
  },
  "选目标": {
	  "需": 1, "最多": 1,
	  "白名单": [pid...],
	  "约束": ["敌方", "非自己"],
  },
  "选项": [                         # 每个选项自带自己的子规格，覆盖上面
	  {"值": 2, "文案": "...", "可用": true, "说明": "...",
	   "选牌": {...}, "选目标": {...}, "展示": {...}},
  ],
  "额外行动": [{"uid": 3, "来源": 2701, "放行": 攻击, "白名单": [...], "系别": 0, "命格": 0}],
  "展示": {"高亮": [pid...], "锁定目标": false, "预览": {...}},
  "提交": {"可取消": true, "默认项": -1},
}
```

配套三个判定函数，客户端只有这三个入口：

```
可点牌(规格, 牌实例) -> bool
可点目标(规格, pid) -> bool
可确认(规格, 已选) -> bool
```

**关键点**：规格里没有「技能号」。技能号只用来查文案和发光效，不再参与判定。

## 3. 分阶段计划

> 顺序原则：先客户端只读收敛，再服务端下发，最后动协议。每一步都能单独停。
>
> **为什么停在阶段 3 / 6**：阶段 3 之后的三件事（把字段搬进 `_规格`、接 `options` 之后的删旧路径、阶段 5 后续）
> 都会碰到「没跑过测试就改、出错难定位」的边界。目前已积累近 20 个未测试提交，
> 继续叠加未验证改动只会让回溯成本变高，所以先停能静态核对的部分，把 §9 的验收清单交给你。

| 阶段 | 做什么 | 不动什么 | 验收方式 | 预估改动 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 1 | 盘点 + 本文档 | 全部 | 你审文档 | 0 行代码 | **完成** |
| 2 | 新增 `询问规格` 客户端类（纯新文件，不接线） | 现有任何调用 | 结构自检 + 你开编辑器确认无语法错 | +150 行新文件 | **完成**（`scripts/ui/ask_spec.gd`，未接线） |

### 4.7 ✅ 复核结论：这条「可见变化」不存在（我原先判断错了）

**我先前的说法**（已作废）：说「先弹选项」的技能在没选效果前，手牌亮不亮有三种表现。

**实际去读代码后发现**：两条通道在**进场时就把需牌 / 最多牌临时清零**，清零后手牌自然整片灰：

| 通道 | 清零位置 |
| --- | --- |
| 技能询问（mode 3） | `_技能询问_选项前置()`：`if _先弹选项: … if not 允许先选牌: _skill_need_card = 0 / _skill_card_max = 0 / _need_cards = 0` |
| 发动技能（mode 4） | `_选择技能()`：`if _先弹选项 and not 允许先选牌: _skill_need_card = 0 / _skill_card_max = 0 …` |

手牌可点的判定 `_牌过本步需牌数()`（mode 3）/ `_技能牌能点()` 开头（mode 4）都是「需牌和最多牌都是 0 → 整片灰」，
所以**当前行为已经是「没选效果就全灰」**，只有显式配了「允许先选牌」的技能（神官【神圣领域】1506）才保持点亮。

**结论**：

- 目标规则（未选效果前一律灰、要放宽就写「允许先选牌」）**就是现在的实现**，不需要改代码。
- 我原表里「选项只带牌系 / 牌型 → 手牌全亮」那一行是误读：牌系过滤（`_牌过选项牌系`）只在**选完效果之后**才起作用，
  选之前手牌早被需牌清零挡掉了。
- 所以 §7 的第 1 项**不再是待拍板项**，这一条可以直接划掉。

### 4.8 2588 行那处「读到旧字段」的复核（**待你点头**）

**代码**（`battle_mobile.gd`，`_技能询问_选项前置` 里）：

```gdscript
if not _目标锁死 and _skill_need_target <= 0 and _skill_target_max <= 0 \
		and _skill_targets.size() == 1 and not _sel_players.has(_skill_targets[0]):
	_sel_players = [_skill_targets[0]]      # 替玩家把这个唯一的目标选中
```

**问题**：这是「技能询问」通道，但它判断「这一手要不要目标」时读的是 `_skill_need_target` / `_skill_target_max` ——
那是**发动技能（mode 4）通道**的字段。而 `_on_command` 每次新询问只复位 `_skill_need_card` / `_skill_card_max`，
**不复位这两个**（已核：`_on_command` 里只有第 2251、2253 行两处复位）。

**后果**：同一个询问，上一手点过的技能不同，预选结果就不同：

| 上一手 | 这次询问要不要目标 | 结果 |
| --- | --- | --- |
| 刚点过「要 1 名目标」的技能 | 不要 | 不预选（本该预选） |
| 刚点过「不要目标」的技能 | 要 1 名 | 预选（本该不预选） |

**影响面**：只影响「**要不要替你预选**」，**不影响合法性、不影响提交**——预选只是让玩家少点一次头像。
触发条件很窄：mode 3 的询问里服务端只给了一个合法目标（`dst_ids` 只有一项）。

**两种改法**：

| 方案 | 改法 | 效果 |
| --- | --- | --- |
| A（推荐） | 换成 `_skill_ask_need_target <= 1` | 与注释原意一致：不需要目标（或最多 1 名）且有唯一合法目标时预选；需要多名时绝不预选 |
| B（更省事） | 直接判 `_skill_targets.size() == 1` | 只要唯一合法目标就预选，玩家永远少点一次；但「要 2 名目标」时预选 1 个属于越权 |

两个方案都会让「预选」不再依赖历史，差别只在「需要 1 名目标时要不要替你点好」。

> 需要你选 A / B / 保持现状。选定后一行改完，同时可以把 `_skill_ask_need_target` 与 `_skill_need_target` 合并（§6 那条遗留）。

### 8.4 5.5 的实际情况（比原计划更细）

`args` 不是「两种布局」，而是**一个通用位置桶**，不同通道各塞各的：

| 通道 | `args` 布局 | 谁在读 |
| --- | --- | --- |
| 行动询问·技能按钮 | `[技能号, 需牌, 需目标, 最多目标, 来源]` | `_构建技能按钮`、`_静默刷新技能可用` |
| 技能询问（`is_skill`） | `[需牌, 需目标, 来源, 选项数, 值…]` | `_技能询问_解析字段` |
| 额外行动 | `[uid]` 或整串 cause | `_进入额外行动` |
| 应战 | `[?, 攻击牌, 目标, 原攻击者, can_light, 伤害, 攻击系]` | `_进入待选` 等 |
| 弃牌 | `[目标, cause, 张数]` | 同上 |
| 虚弱 | `[目标, 强摸, 束缚, 虚弱]` | 同上 |
| 治疗抵挡 | `[目标, 伤害, 类型, 上限]` | 同上 |
| 魔弹 | `[持有者, 伤害]` | 同上 |

所以「统一布局」如果真去做，等于把 8 个应答协议全重排 —— 角色脚本里几十处 `询问(...)` 调用都要跟着改。

**因此 5.5 收敛成两半**：

- **5.5a（已做）**：只把「行动询问·技能按钮」那套规格搬进命名字段
  （`skill_id` / `need_card` / `need_target` / `target_max` / `card_source`，字段号 58~62），
  服务端双写、客户端优先读字段、读不到回退 `args`。这消掉了最容易串位的那一对。
- **5.5b（不做）**：应答类 `args` 保持原样。它们是「一通道一协议」，没有第二种解读方式，
  改它收益低、面太大（要动几十处角色调用 + 全部相关用例）。

### 8.7 阶段 7（配置表瘦身）能不能做：先看收益

`技能指示器` 的 51 个键里，有一部分**服务端本来就知道**，只是当年为了省事写在客户端配置里；
如果能随选项一起下发，客户端就不必按技能号查表。按附录 D 的条目数排一下：

| 键 | 条目数 | 服务端知道吗 | 能不能迁 |
| --- | ---: | --- | --- |
| `选项目标数` | 6 | 知道（`option_need_targets` 已经在发） | 能，但两边已经在重复表达，迁完删表键 |
| `选项牌系` | 1 | 知道（哪个效果要求哪一系，是技能自己的规则） | 能，加 `Option.card_element` |
| `选项目牌型` | 1 | 知道（「只收法术牌」这类） | 能，加 `Option.card_rule` |
| `先弹选项` | 19 | 不知道 —— 这是「客户端先摆选项再放牌」的交互选择 | 能，但要在引擎加询问级标记（19 条技能都要改调用） |
| `允许先选牌` | 1 | 同上 | 能，但只有 1 条，不值 |

**结论（建议）**：

- 真正值得迁的只有 **`选项目标数`（6 条）+ `选项牌系`（1 条）+ `选项目牌型`（1 条）**：
  都是「这一个选项自己的规矩」，服务端顺手就能带上，迁完客户端少三条查表分支。
- `先弹选项`（19 条）和 `自动选目标`（42 条）虽然条目多，但都属于**交互策略**，
  迁过去只是把「按技能号查表」换成「按询问字段判断」，代码量不减反增，且要动几十个角色调用。
- 所以阶段 7 **建议只做那 3 个键**，其余保持现状；这一条不影响任何现有行为，
  属于「将来顺手做」，不列为必做项。

**这套扫描的边界**（别当成绝对真理）：

- **`.tscn` 已经一起扫了**（信号按名字连到脚本方法也算引用）—— 上一版没扫，所以数会差几个。
- 名字是拼出来的（`call("p_" + x)`）扫不出来；不过本项目钩子都写的是字面量，所以影响不大。
- 一处同名的字符串（日志、注释）也会被算成「有引用」，所以这个扫描**偏保守**（只会漏报，不会误报为「无引用」）。
- 脚本本身要存成 **UTF-8 带 BOM**：Windows PowerShell 5.1 不认无 BOM 的 UTF-8，会把中文标识符读成乱码直接报语法错（本项目其它 `.ps1` 都带 BOM，照抄即可）。

> 本轮只做了普查，**没有删任何东西** —— 这类清理放在你跑完测试之后做最省事。
