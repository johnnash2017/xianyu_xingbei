# 多步询问（分段询问）统一框架 —— 现状盘点、需求与设计草案

> 状态：**设计草案（2026-11-10）**，只做盘点与设计，未改任何技能实现。
> 目的：把「一个技能要分几次问玩家」这件事收敛成一套写法，后续新增多步技能不再各写一套状态机，
> 客户端也不再为每个技能单独加「返回」分支。
> 相关文档：[技能维护约定](技能维护约定.md)、[新角色实现-进度与遗留](新角色实现-进度与遗留.md)。

---

## 0. 结论先行

1. **现状确实不统一**：仓库里同时存在 5 类写法（见第 1 节），同一个需求（「回退到上一步」）有 3 种表达方式
   （表里配键 / 客户端硬编码 / 角色自己重问）。
2. **不统一的部分只有一处是真乱**：**多步之间的「回退」**。其余差异（客户端本地 vs 服务端分段）是本质差异，
   不该合并。
3. **建议**：抽一层薄薄的「多步询问」框架（服务端段 + 本地段 + 统一回退 + 统一超时/重连），
   底层仍用现有 `ask_skill`；分 4 个阶段迁移，**存量技能不强制重写**。

## 1. 现有写法盘点

### 1.1 五类写法

| 类别 | 做法 | 数量（2026-11-10 扫描） | 代表 |
| --- | --- | --- | --- |
| **A. 客户端本地二级栏 `arg_choices`** | 技能按钮上一次下发全部选项，客户端本地切换；「确定」一次提交；「返回」＝不发动 | **31** 个角色脚本用到 | 魔弓【魔眼】2605、充能 2604、雷光散射 2602、异教徒【放逐】9505 |
| **B. 服务端分段询问 + 段号状态机** | 角色自己记 `_xxx阶段`，钩子重入时按段号推进，每段一次 `询问()` | **119** 个段号变量，分布在 **50** 个角色脚本；角色里共 **235** 处 `询问(` | 军神威光 2504、魑魅魍魉 8404（第二段复用 8401/8402 的技能号）、狂戾之心 8303、神智污染 8305、扭曲之爱 8306 |
| **C. 「回退到上一段」** | 空应答＝退回上一段重问 | **2** 条技能指示器键（配在 8401/8402）+ **8** 个客户端技能专属函数（见 1.3） | 魑魅魍魉 8404、军神威光 2504、魔纹融合 2701、苍白之月 3507、圣光爆裂 3704、自动填充 3707 |
| **D. 客户端纯本地分层** | 不经过服务端询问，纯 UI 分层 | `_本地选项阶段`(0~6)、`_提炼阶段`、`_苍白第二步`/`_自动填充第二步`/`_圣光爆裂第二步` | 购买/合成/提炼、恩典神授代价、冒险家天堂分配、苍白之月第二步 |
| **E. 引擎侧机制**（不是角色写法，是地基） | 状态栈、`保留倒计时`、`_挂起回复`、行动聚合器待决、重连补发 | — | `battle_engine.gd` 的 `SAskCross` / `SkillRun` / `S行动聚合器` |

补充：B 类内部还有两种代码组织风格，**行为等价、只是写法不同**：

- **B1**：同一个函数里 `if _阶段 == 0: ... if _阶段 == 1: ...`（多数角色）；
- **B2**：每段一个函数，入口按段号 `match` 分派（军神威光、放逐、扭曲之爱）。

### 1.2 一个真实的杂乱样本：扭曲之爱的三次返工

| 版本 | 写法 | 问题 |
| --- | --- | --- |
| 初版 | 一次询问 7 个平铺选项（形态 × 弃/摸 × 戾气） | 十几个选项糊成一片，需求方要求拆段 |
| 第二版 | 第一段 `arg_choices`（本地）+ 后两段服务端询问 | 本地段与服务端段混用：返回时服务端要重问第一段，两条通道不一致；闪屏、选项被抹掉 |
| 第三版（当前） | 三段全部服务端询问（B2）+ `可返回` 参数 | 结构统一了，但角色里仍有 3 个段函数 + 段号 + 「已完成」态 |

也就是说：**同一个技能，三次实现三种结构**——这正是「缺乏统一」最直接的证据。

### 1.3 客户端里跟多步相关的技能专属代码

`battle_mobile.gd` 里按技能号写的多步专用函数（8 个）：

| 客户端函数 | 对应技能 | 现在怎么回退 |
| --- | --- | --- |
| `_军神威光返回()` | 军神威光 2504 | 函数里自己重发第一段的应答逻辑 |
| `_魔纹本体返回()` | 魔纹融合 2701 | 同上 |
| `_进入苍白月第二段()` / `_返回苍白月第一层()` | 苍白之月 3507 | 本地 `_苍白第二步` 标志 |
| `_进入圣光爆裂第二层()` / `_返回圣光爆裂第一层()` | 圣光爆裂 3704 | 本地 `_圣光爆裂第二步` 标志 |
| `_进入自动填充第二层()` / `_返回自动填充第一层()` | 自动填充 3707 | 本地 `_自动填充第二步` 标志 |

另有 **93** 处客户端 `GConst.技能_*` 判断（`_选项选中立刻处理`、`_确定_*`、提示文案、播报等），
其中一部分就是「这个技能点选项要不要立刻提交」「返回退到哪一层」这类**流程性**特判。

### 1.4 为什么会有这么多写法（历史原因，不是谁写歪了）

1. **A 与 B 的差别是本质的**：选系别、选摸几张这类不需要服务端校验的，做成客户端本地（A）最快；
   选牌是否合法、随机数、状态变化必须服务端算（B）。
2. **`arg_choices` 只能支撑一段**：需要「选完这一段再选下一段」时，只能回落到服务端分段询问（B）。
3. **「回退」当初没有通用说法**：每个技能第一次需要回退时，就在客户端加一个函数 / 在表里加一条键，
   于是 C 变成「一个技能一套」。
4. **引擎的 `step` 不能跨询问**：钩子轮次开始会清零 `step`，所以分段只能靠角色自己的变量 → 119 个段号变量。
   这是规则决定的，不是设计冗余。

## 2. 需求清单（从现有技能倒推）

把现有 50 个多步技能的诉求归纳成 12 条，框架必须能容纳：

| # | 需求 | 现有例子 | 现在的实现方式 |
| --- | --- | --- | --- |
| R1 | 顺序多段，每段只问一件事 | 扭曲之爱（形态→弃/摸→戾气） | 段号 + 逐段询问 |
| R2 | 段间有服务端副作用（扣费、弃牌、摸牌、形态变化） | 扭曲之爱扣宝石、狂戾之心弃牌 | 角色自己按顺序做 |
| R3 | 能退回上一段，且**已发生的副作用不能白吃** | 扭曲之爱（弃牌推迟到结算） | 角色自己把副作用推迟 |
| R4 | 整条链共用一个倒计时 / 或每段独立计时 | 军神威光（`保留倒计时`） | 询问参数 |
| R5 | 超时默认值（放弃 / 默认选项 / 最保守结算） | 军神威光超时＝选项① | 角色在空应答分支里判 `is_timeout` |
| R6 | 每段各自的选牌白名单、张数、来源（手牌/盖牌）、系别/命格限制 | 狂戾之心（弃 1 + 选目标同段） | `ask_skill` 参数 |
| R7 | 同一段内「选牌 + 选目标」合并问 | 狂戾之心、军神威光第二段 | `need_card` + `need_target` |
| R8 | 选项决定后续需牌/需目标数 | 魔眼、放逐 | 选项自带 `need_card`/`need_target` |
| R9 | 同一个技能里既有服务端段又有纯本地段 | 圣光爆裂（选群体 → 本地选 X） | 客户端本地分层（D） |
| R10 | 断线重连后能继续当前段 | 所有分段技能 | 引擎重发「正等他的那份询问」 |
| R11 | 非法提交要能重问当前段而不是整条链作废 | 扭曲之爱（弃牌张数不对） | 角色 `报错` + 结束 / 或重问 |
| R12 | 预览数值（本段会打多少伤害 / 加多少治疗） | 神智污染、撕裂、军神威光 | `预览基准` / `预览类型` / `预览目标` |

## 3. 统一框架设计（草案）

### 3.1 分层

```text
┌──────────────────────────────────────────────┐
│ 角色脚本：只声明「一条多步询问」+ 结算回调        │  ← 新增的薄封装
├──────────────────────────────────────────────┤
│ BattleRole.多步询问（框架层）                    │
│   · 段进度（不再每个技能一个 _xxx阶段 变量）      │
│   · 回退（空应答 → 上一段重问）                  │
│   · 超时（链级 deadline + 每段默认值）           │
│   · 副作用（统一在结算回调里做，回退不撤账）      │
├──────────────────────────────────────────────┤
│ ask_skill / 询问（现有底层，不动）                │
├──────────────────────────────────────────────┤
│ 客户端：按「段类型 + 选项 + 可返回」渲染，        │
│         不再按技能号写返回分支                   │
└──────────────────────────────────────────────┘
```

### 3.2 角色侧 API 草案

```gdscript
## 声明一条多步询问。返回 WAIT 表示正在问；链走完后回调「结算」。
## 段类型：
##   选项：{「选项」: [...], 「可返回」: bool, 「超时默认」: value}
##   选牌：{「张数」: int, 「白名单」: [...], 「来源」: CardSource, 「可返回」: bool}
##   选目标：{「数量」: int, 「白名单」: [...], 「可返回」: bool}
##   本地：{「选项」: [...]}            # 只在客户端展开，不占服务端段
func 多步询问(链号: int, 段列表: Array, 结算: Callable) -> int
```

角色实现示例（改造后的扭曲之爱，约 20 行）：

```gdscript
func p_special_skill(_action: Dictionary) -> int:
	return 多步询问(NIU_QU_ZHI_AI, [
		{"类型": "选项", "选项": _形态选项(), "超时默认": 0},
		{"类型": "选牌", "张数": 2, "来源": CardSource.Hand, "可返回": true,
		 "选项": _弃摸选项()},                      # 选项 + 选牌同段
		{"类型": "选项", "选项": _戾气选项(), "可返回": true},
	], _结算扭曲之爱)

func _结算扭曲之爱(答案: Array) -> int:
	# 只在这里做副作用：扣宝石、调戾气、落形态、弃牌/摸牌
	...
```

### 3.3 框架内部的规则

| 事项 | 规则 |
| --- | --- |
| 段进度 | 存在角色对象上的一张通用表：`{链号: 当前段}`，不再每个技能一个变量 |
| 回退 | 客户端「返回」→ 空应答 → 框架退到**上一个带 `可返回` 的段**并重问；第一段取消＝整条链不发动 |
| 副作用 | **一律放在结算回调**；段内只收集答案（所以回退天然不用撤账） |
| 超时 | 链级 `保留倒计时`（默认开）；某段超时按该段 `超时默认`，没有默认值＝按「取消」处理 |
| 非法提交 | 框架重问当前段（不整条作废），并回一条 `ErrorInput` 提示 |
| 断线重连 | 进度在服务端内存，沿用现有「重发正等他的那份询问」机制即可 |
| 本地段 | 服务端照常下发（标记 `本地`），客户端展开后把结果**并进下一次应答**提交，不单独发网络包 |
| 与 `arg_choices` 的关系 | `arg_choices` 视为「只有一段、且是本地段」的特例，可保留；迁移时逐步转成单步链 |

### 3.4 客户端侧改动

服务端询问消息增加三个字段（沿用现有 `allow_back` 的思路）：

| 字段 | 含义 |
| --- | --- |
| `chain_id` | 这条询问属于哪条链（同一技能的不同段共用） |
| `step_index` | 第几段（只用于显示「第 2/3 步」，不参与逻辑） |
| `allow_back` | 这段能不能返回（已实现） |

客户端规则变成一句话：**`allow_back` 就摆「返回」，点了回空应答；有多段就在提示条写「第 N/M 步」。**
不再按技能号判断，可以删掉 1.3 表里的 8 个函数。

| **不做** | 存量 119 个段号变量强制重写 | — | — | 纯风格改造，行为风险大、收益低 |

**新技能要求**（写进技能维护约定即可，不需要等框架）：

1. 多步一律用 B2 写法（每段一个函数、入口按段号分派、段号放在角色自己的变量里）；
2. 需要回退就传 `可返回=true`，不要再配指示器、不要写客户端函数；
3. 副作用一律推迟到结算（段内只收集答案）。

### 5.2 问题与决定

1. **`while true` 的返回值**：框架主循环每个分支都是 `return` / `continue`，GDScript 仍报
   「Not all code paths return a value」→ 函数末尾补一个不可达的 `return SUCCESS`，只为过解析。
2. **超时策略（第一版写错，已改）**：初版是「空应答且这一段不可取消 → 重问这一段」，
   但掉线 / 挂机玩家的默认回复就是空应答，强制询问（如狂戾之心）会无限重问、把整局卡死。
   改成：**超时优先用这一段的 `超时默认`，没有就按「不发动」收尾**；只有「非超时却给了空应答、
   又不能取消」这种异常才重问本段。
3. **军神威光挪到 P2**：它现在的「返回」是客户端 `_军神威光返回` 硬编码；而且第二段「非法星石组合」
   目前是退回第一段重问。搬进框架前要先定「非法提交＝重问本段还是退回上一段」的口径
   （框架现在只提供「空应答＝回退」，没有「校验失败＝回退」）。为了 P1 保持「行为完全一致」，先不迁。
4. **神智污染**：单段「确认」用框架收益不大，但验证了两件事 ——「预览基准 / 预览类型」能原样透传，
   以及结算回调里能直接改 `harm`。原来靠引擎每轮的 `step` 防重问，现在改成 `harm["神智污染已处理"]`
   标记（跨询问更可靠，不会被钩子轮次清零影响）。
5. **「空应答」的判定口径**：框架里「空」=`args` / `card_ids` / `dst_ids` 全空。
   注意选项值 **0** 是合法答案（如戾气调为 0），因为 `args` 非空，不会被误判成「取消」。
6. **弃牌合法性**：扭曲之爱把「弃几张」的校验放在结算里（`min(2, 手牌数)`），
   框架不替它校验 —— 框架只负责「问」和「回退」，业务校验仍归角色（与设计一致：副作用和校验都在结算）。
7. **框架能力是迁移逼出来的**：迁军神威光时才发现三个真实需求 ——「选①就不用问第二段」（→`跳过`）、
   「第二段超时按①结算」（→`超时` 回调）、「非法星石组合退回第一段」（→`校验` + `校验失败回退`）。
   这三个能力最后都做进了框架（`7eec202`），没有留在角色里各写一遍。
8. **军神威光口径保持不变**：非法组合仍然「退回第一段」，没有顺手改成「重问第二段」；
   要改属于交互优化，得单独提需求（记在第 8 节）。
9. **魔纹融合**：框架不管引擎的 `step`，所以结算里仍自己置 `step = STEP_DONE`，
   挡住「返回 URGENT 后引擎重入钩子」那一下（这是引擎层的规矩，框架不接管）。
10. **魑魅魍魉收尾**：`选项可返回` 指示器键彻底删除，客户端只认 `allow_back` ——
   至此「多步回退」全仓只剩一套机制（`f1d1429`）。
11. **踩坑：新增的询问字段必须登记进 `proto_schema.gd`**。`allow_back` 一开始只塞进了询问命令的字典，
   字段表里没有它 —— 单机（进程内直连）能跑，真实联机会被编解码静默丢掉，客户端永远摆不出「返回」。
   已补 `Command` 表 `65: allow_back`（`96f86b2`）。**以后往询问命令里加任何键，都要同时加字段表。**

## 6. 非目标与风险

- **不做全量重写**：存量 50 个多步技能保持现状，只在被改动时才迁移。
- **不合并 A 与 B**：客户端本地（A/D）与服务端分段（B/C）是两类需求，框架只在「需要回退的分段」上统一。
- **不改既有行为**：P1 的验收标准是「行为与现在完全一致」，不是「顺手优化体验」。
- **网络包体**：多步链每段一条 `CmdReq`，与现在相同；不引入新的长连接状态。
- **重连**：进度在房主进程内存里，房主掉线本局就结束（与现有规则一致），不需要持久化。
