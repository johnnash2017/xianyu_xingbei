# 对局埋点上报

> 本文只写**当前工程里已经落地的实现**。改这套东西之前先读一遍，尤其是「统计口径」和「改字段的连锁反应」两节。
> 相关代码：[telemetry.gd](../scripts/net/telemetry.gd)、[battle_engine.gd](../scripts/battle/battle_engine.gd)（文件末尾「对局埋点」段）、[local_server.gd](../scripts/net/local_server.gd)。

## 1. 这是什么

把每场战斗的三条事件上报到 ThinkingAI（TA）项目「星杯传说」（项目 ID 352957），用于看对局面貌、双方士气/星杯/星石、每个角色的资源与每回合输出/治疗。

| 项 | 值 |
| --- | --- |
| 上报方式 | RESTful API raw 方式：`POST https://ae-receiver.thinkingai.cn/sync_json` |
| APPID | `33862e75ba494708b864ade41165d7fc` |
| 事件数 | 3 个：`battle_start` / `round_end` / `battle_end` |
| 事件属性 | 15 个（三个事件共用） |
| 角色明细 | `character_details` 对象数组，每名角色一行，16 个字段 |

## 2. 链路

```text
LocalServer._建房间
  └─ battle.telemetry_cb = Telemetry.记录对局事件        // 引擎不碰网络，和 send_cb 同一套注入

BattleEngine（唯一权威状态）
  ├─ start_with_roles      → _上报事件("battle_start", 0)
  ├─ SNextPlayer（轮到先手）→ _回合结束埋点() → _上报事件("round_end", round_id)
  └─ _game_over            → _上报事件("battle_end", round_id)
		│  每次现算 12 个对局属性
		▼
Telemetry.记录对局事件（autoload）
  ├─ 补 3 个上报侧属性（game_version / report_time / is_test_data）
  ├─ 入队 + 落盘 user://telemetry_pending.json
  └─ 每 3 秒或攒满 200 条 → HTTPRequest POST
		├─ {"code":0}        → 出队
		├─ 网络/非 200/非 JSON → 5 秒后重试
		└─ {"code":非0}       → 数据被拒，丢掉这批并 push_warning（重发也不会好）
```

**只由房主进程上报。** 一局战斗的权威状态只在房主的 `BattleEngine` 里；客户端各报一份会重复，而且数据可被改。`telemetry_cb` 只在 `LocalServer._建房间` 注入，客户端侧根本不存在这个回调。

## 4. 三个事件

| 事件 | 触发点 | `current_round` |
| --- | --- | --- |
| `battle_start` | `start_with_roles` 发完牌、广播首份快照之后 | `0`（还没进入回合） |
| `round_end` | `SNextPlayer` 里「轮到先手、`round_id` 还没 +1」那一刻 | 刚结束的那一回合 |
| `battle_end` | `_game_over`：清空状态栈、广播终局快照之后 | 结束时的回合号 |

- 「回合」= 所有人各行动一次；额外回合（月女【苍白之月】、剑守誓言等）不增加回合数，统计算进当前回合。
- `round_end` 每轮只发一次，发完清空该轮统计。

## 6. `character_details` 每行 16 个字段

按 `order`（座位顺序）逐人一行。

| 字段 | 类型 | 来源 / 口径 |
| --- | --- | --- |

| `steam_id` | string | `玩家标识[座位]`：登录包 `client_id`，Steam 模式 = SteamID，本地/局域网 = 昵称；取不到退回昵称 |
| `team` | number | `0` = 红，`1` = 蓝 |

| `attack_damage` | number | 本回合对敌方的攻击伤害 |

## 7. 统计口径（改之前务必看）

### 7.1 伤害（6 项里的 4 项）

- **记录时机**：`SHarmTimeline6`，即治疗抵挡已结算完、⑥ 伤害转移已改好最终目标之后 —— 记的是**真正落地**的点数。
- **攻击 / 法术**：按 `HarmType` 分。普通攻击、应战反击、按攻击结算的技能牌算攻击；其余（含【魔弹】）算法术。
- **敌方 / 自残**：发起者与承受者**同阵营**算 `_self_damage`，不同算 `_damage`。打自己、打队友都算自残。
- **归属**：记在**发起者**（`harm.src`）头上；被治疗抵成 0 点的伤害不计。

### 7.2 士气（2 项）

- **记录时机**：`SApplyOverloadMorale`，手牌超限掉士气真正扣下去的时候。
- **归属**：归给「最近一次伤害的发起者」`_最后伤害来源`；扣的是发起者同阵营的士气 → `morale_self_damage`，否则 `morale_damage`。
- **不计**：非伤害来源的掉士气（合成星杯扣对方 1 点、技能惩罚等）没有“哪个角色的伤害”可归属，不记。

### 7.3 治疗（2 项）

- **入口**：`add_cross` / `add_cross_pierce`（角色统一走 `BattleRole.施加治疗` / `施加治疗_突破`）。
- **记给施加者**：谁加的记在谁头上。
- **友方 / 敌方**：受益者与施加者同阵营 → `heal_amount`，不同 → `heal_enemy`。
- **含溢出**：按传进来的 `amount`（打算加几点）记，不是实际加进去几点；目标满治疗也照记。
- **不计**：整笔被禁疗作废的（【神威】、【神弃之裔】），守卫在记账之前就 return 了。

### 7.4 清零

`_回合统计` 在**开局**（角色 setup 之后）和**每回合结束**（`round_end` 发完）各清一次。所以三个事件里的“本回合”字段分别是：开局全 0、该轮累计、最后一轮累计。

## 8. 阵营与红蓝

- **埋点编号**：`team_0` = 红，`team_1` = 蓝；行内 `team` 同一套编号（红 0 / 蓝 1）。
- **引擎内部**：`GConst.RED = 1`、`GConst.BLUE = 0`，正好相反，转换在 `_埋点阵营()`，别混。
- **红 = 宝石**：`gem` / `team_gem`；**蓝 = 水晶**：`crystal` / `team_crystal`。

## 9. 什么时候上报

| 环境 | 上报 | `is_test_data` |
| --- | --- | --- |
| Steam 正式对局 | ✅ | `false` |
| 本地调试（F9/F10/F11、`--slot` / `--auto`） | ✅ | `true` |
| 局域网模式（`--lan`） | ✅ | `true` |
| headless（自检 / CI） | ❌ | — |

headless 直接跳过：自动化用例不碰网络。判断在 `Telemetry._应上报()`。

## 10. 可靠性

| 项 | 值 |
| --- | --- |
| 攒批间隔 | 3 秒 |
| 单批上限 | 200 条 |
| 失败重试 | 5 秒后重发同一批（不做指数退避） |
| 待发落盘 | 每条事件入队即写 `user://telemetry_pending.json`，下次启动续传 |
| 队列上限 | 2000 条，满了丢最旧的 |
| 数据被拒 | 返回 `code ≠ 0` 视为数据问题：丢掉这批 + `push_warning`，不阻塞后面的数据 |
| 返回体不是 JSON | 当临时故障（代理/网关错误页）重试 |

事件包外层：`appid` + `data{#type, #event_name, #time, #account_id, #distinct_id, properties}`；`#account_id` / `#distinct_id` 都取**房主**的身份标识（一场战斗算一个“用户”，全员名单在 `character_details` 里）。`#time` 带毫秒，`report_time` 只到秒。

## 11. 已知边界

1. **最后一轮不满就结束对局时没有 `round_end`**：终局会清空状态栈，轮转不执行；那一轮的统计只出现在 `battle_end`。
2. **非伤害掉士气不计**：见 7.2。
3. **同机多个房主**：待发缓存是同一个 `user://telemetry_pending.json`，只在发送失败落盘时才可能互相覆盖；正常玩不到。
4. **没有 `#uuid`**：进程在发送途中被杀，重发可能产生重复事件（后台只对几小时内同 `#uuid` 去重）。事件量很小，暂未加。

## 12. 怎么验证

1. 起一个本地窗口开一局：

   ```powershell
   godot --path "<工程目录>" -- --slot=0
   ```

2. 打一局（至少打完一轮），3 秒内后台应出现 `battle_start`、若干 `round_end`、`battle_end`，且 `is_test_data = true`。
3. 后台没数据时：
   - 看控制台有没有 `[Telemetry] 上报被拒（code=...）`；
   - 看 `user://telemetry_pending.json` 是否在积压（有就是网络/地址问题）；
   - 临时在记录里加 `"debug": 1`（`telemetry.gd` 的 `记录对局事件` 组包处）单独打一条，返回会逐条说明哪个属性不对。
4. 自检（headless）不会产生上报，属正常。

## 13. 改这个功能时的约定

1. **属性名 / 字段名只能 ASCII**，且必须和平台埋点方案逐字一致；类型在第一次上报时就被后台定死，之后同类事件必须传同样的类型（数值别一会儿 int 一会儿 float）。
2. **改字段要三处同步**：引擎 `_埋点属性` → 平台埋点方案 → 本文第 5、6 节。
3. **新增属性先想清楚归谁出**：对局状态放引擎，和“何时/怎么报”相关的（时间、版本、环境标记）放 `telemetry.gd`。
4. **不要用 `_rng` 或全局 `randi()` 取号**：前者是战斗判定随机源（`tests/diffProbe` 固定种子），后者被牌库洗牌使用。`battle_id` 用的是独立的 `_埋点rng`。
5. **别在引擎里直接发网络请求**：引擎只调注入的 `telemetry_cb`，组包/重试都在 `telemetry.gd`。
6. 属性数量与平台事件/属性上限无关（当前 3 个事件、15 个属性，远低于上限），但不要为了“顺手多记点”往里塞临时的调试字段。
